# 5. Intranet 주요 기능

현재 계획된 주요 기능은 다음과 같다.

## 5.1 회원 기능

- 회원가입
- 회원정보 관리
- 마이페이지
- 관리자 회원관리
- 사용자 상태 관리
- 권한 관리

주요 Entity (컬럼 상세는 `backend/prisma/schema.prisma` 기준):

```text
Users            회원 (role: UserRole enum, status: UserStatus enum, positionId: 직급은 사람 단위로 관리)
Department       부서 (parentDepartmentId 자기 참조 트리)
JobTitle         직책 (팀장, 본부장 등)
Position         직급 (sortOrder로 직급 순위 비교)
UserDepartment   회원 소속 (회원-부서-직책, 겸직 시 여러 행, isPrimary로 주 소속 구분)
```

- 회원가입 필수 동의(2026-11-19, 사용자 결정): 가입 정보 입력 전에 이용약관·개인정보 수집·이용에 모두 동의해야 한다. `UserConsent`(`userId`, `type`, `action`, `version`, `createdAt`)에 동의·철회를 행 추가로만 기록하고, 가입과 같은 트랜잭션으로 저장한다. 서버는 요청의 버전이 현재 버전(`users/const/consent.const.ts`)과 다르면 400으로 거부한다. 화면·본문은 [fe-18-register-consent.md](../frontend/fe-18-register-consent.md).
- 프로필 사진(2026-11-19, 사용자 결정): 마이페이지에서 등록·변경·삭제한다. 이미지를 `POST /common/files/images`로 먼저 올리고 `PUT /users/me/profile-image { fileId }`로 연결한다(`Files.targetType = USER_PROFILE`, `targetId = 회원 id`, 회원당 1장 - 교체하면 이전 사진 soft delete, 내가 올린 미연결 이미지만). 삭제는 `DELETE /users/me/profile-image`. 둘 다 USER 이상(업로드가 USER 이상이라 승인 대기는 등록 불가). 게시판 본문 이미지와 같은 추측하기 어려운 uuid 공개 주소이며, 응답 `profileImageUrl`(썸네일 주소)은 `GET /users/me`와 채팅 회원(`ChatUserView`)에 포함한다. 개인정보 수집 선택 항목에 사진을 넣고 `PRIVACY_COLLECTION`을 1.1로 올렸다(기존 회원 재동의는 받지 않음). 화면은 [fe-19-profile-image.md](../frontend/fe-19-profile-image.md).
- 조직도·사원 검색(2026-11-19, 사용자 결정): 일반 직원용 API는 관리자용 `/departments`·`/users`와 따로 둔다(`organization/org-chart.controller.ts`, 모두 USER 이상). 대상은 재직(ACTIVE)·승인(GUEST 제외)·삭제되지 않은 회원. 조직도는 부서 트리 + 부서별 구성원 수, 부서를 누르면 그 부서에 직접 소속된 사람만(하위 부서 제외, 겸직 포함) 직책 → 직급 순위 → 이름 순으로 보여 준다. 사원 검색은 이름·사번·부서명(겸직 포함) 부분 일치, 이름순 페이지. 사원 한 명 조회(`GET /organization/directory/:userId`, 재직 중이 아니면 404)는 채팅 메시지의 보낸 사람 창이 쓴다. 다른 직원에게 공개하는 값은 사진·사번·이름·직급·소속 전체(직책·겸직)·이메일·회사 전화이고, 휴대폰·생일은 내보내지 않는다. 화면은 [fe-20-org-chart.md](../frontend/fe-20-org-chart.md).
- 소속은 관리자가 추가·수정·삭제한다. 첫 소속은 자동으로 대표 소속이 되고, 대표 소속은 관리자와 본인(마이페이지) 모두 변경할 수 있다.

- 권한은 별도 테이블이 아닌 `Users.role` enum(`GUEST / USER / ADMIN / SUPER_ADMIN`)으로 관리한다.

- 가입 승인(GUEST → USER/ADMIN)은 입사일(`joinAt`, 연차 계산에 필요)이 먼저 등록된 회원만 가능하다. 승인된 회원은 입사일을 비울 수 없다(수정은 가능).
- 관리자의 권한·상태 변경과 삭제는 단건·일괄이 같은 서비스(`ids` 배열)를 쓰며, 한 명이라도 처리할 수 없으면 전체가 실패한다(트랜잭션).

### 관리자 기능 권한 (2026-11-14, 사용자 결정)

ADMIN이 쓸 수 있는 관리자 기능을 슈퍼관리자가 회원별로 지정한다.

| 권한 | 관리자 기능 |
|---|---|
| `SUPER_ADMIN` | 모든 관리자 기능 + ADMIN 승격·관리자 기능 지정 + 관리자 계정 관리 |
| `ADMIN` | `Users.adminPermissions`(enum 배열)에 있는 기능만 |

`AdminPermission` 값과 화면·서버 동작:

| 값 | 화면 | 서버에서 함께 바뀌는 판단 |
|---|---|---|
| `USERS` | 회원 관리 (가입 승인·정보·소속·상태·비밀번호 초기화·잠금 해제) | 가입 신청 알림을 받는다 |
| `ORGANIZATION` | 조직 관리 (부서·직급·직책) | - |
| `BOARDS` | 게시판 관리 (게시판·게시판 권한) | 권한 규칙과 관계없이 모든 게시판을 읽는다(규칙 없는 게시판 포함) |
| `FACILITIES` | 시설 관리 (분류·시설·사용 불가 기간) | - |
| `RESERVATIONS` | 예약 관리 | 남의 예약 수정·취소, 지난 예약 삭제 |
| `APPROVAL_LINES` | 결재라인 관리자 | 위임 없이 모든 결재라인 관리, 모든 결재 문서 열람(전체 문서함), 결재자 교체 |
| `LEAVES` | 연차 관리 | - |
| `AUDIT` | 감사 로그, 관리자 대시보드의 최근 관리 활동 (2026-11-18 사용자 결정) | 감사 로그 조회(`GET /common/audit-logs`). 꺼진 애드온의 로그는 제외 |

- **저장**: `Users.adminPermissions AdminPermission[]`(기본 빈 배열). ADMIN만 값이 있고, 다른 권한으로 바뀌면 비운다. 애드온 기능 값(시설·예약·결재라인·연차)도 핵심 enum에 둔다(10.1 허용한 타협).
- **판단 위치**: 권한은 access token payload(`perms`)에 넣는다. `RolesGuard`가 `@RequireAdmin(AdminPermission.X)`를 보고 판단한다(DB 조회 없음). 여러 관리자 화면이 같이 쓰는 조회(부서·직급·직책 목록, 시설 분류·시설 목록)는 `@RequireAdmin()`으로 ADMIN이면 기능과 관계없이 허용한다. 서비스 안의 판단은 `hasAdminPermission(user, X)`(`src/auth/util/admin-permission.util.ts`).
- **반영 시점**: 기능 추가는 다음 재발급(최대 10분) 때 반영된다. 회수·강등(ADMIN → USER, SUPER_ADMIN → 아래, 기능 해제)은 `tokenVersion`을 올려 재발급을 막는다. 그래서 그 회원은 다시 로그인해야 한다. access token은 stateless라 남은 유효시간(최대 10분)은 막지 못한다.
- **지정 화면**: 회원 목록 ⋯ 메뉴의 계정 섹션. 권한을 ADMIN으로 고르면 기능 체크박스가 나오고 함께 저장한다(슈퍼관리자에게만 보인다). 일괄 변경으로 ADMIN이 된 회원은 기능 없이 시작한다.
- **슈퍼관리자만 할 수 있는 일**
  - ADMIN·SUPER_ADMIN으로 바꾸기, 관리자 기능 지정. 회원 관리 기능을 가진 ADMIN은 GUEST·USER를 USER로만 바꾼다(가입 승인).
  - 관리자 계정(ADMIN·SUPER_ADMIN)의 권한·상태 변경, 삭제·복구, 비밀번호 초기화, 잠금 해제(`UsersService.assertCanManageAccount`). 회원 관리 기능만 받은 ADMIN이 슈퍼관리자를 정지·삭제하는 것을 막는다.
- **마지막 슈퍼관리자 보호**: 재직 중인 슈퍼관리자가 한 명도 남지 않게 되는 강등·정지(재직 외 상태)·삭제는 400. 두 슈퍼관리자가 동시에 서로를 강등하는 경우를 막으려고 슈퍼관리자 행을 `FOR UPDATE`로 잠근 뒤 센다. 본인 계정 변경은 원래 막혀 있다(`checkNotSelf`).
- **첫 슈퍼관리자**: 화면으로는 만들 수 없으므로 스크립트로 지정한다. `npx tsx prisma/seed-super-admin.ts <사번>`(슈퍼관리자가 이미 있으면 아무것도 하지 않음, `--dry-run` 지원). 두 번째부터는 화면에서 지정한다.

## 5.2 인증 기능

- 로그인
- 로그아웃
- Basic 인증
- Bearer Token 인증
- JWT Access Token
- JWT Refresh Token
- 사용자 권한 확인
- 관리자 권한 확인

NestJS의 Guard / Decorator 기반 인증 및 권한 관리를 활용한다.

토큰 전달 방식:

| 토큰 | 유효시간 | 발급 | 전달 | 검증 |
|---|---|---|---|---|
| Access Token | 10분 | 응답 본문 | `Authorization: Bearer` 헤더 (프론트는 메모리에만 보관) | `AccessTokenGuard` (전역, **payload만 검증 - DB 조회 없음**) |
| Refresh Token | 1일 (재발급마다 교체·연장, 로그인 후 최대 7일) | NestJS가 HttpOnly 쿠키로 직접 `Set-Cookie` | 쿠키 (`Path=/api/auth`, 브라우저가 자동 전송) | `RefreshTokenGuard` (쿠키에서 꺼냄) + `AuthSessionsService` (세션 확인·교체) |

- 로그인은 `Authorization: Basic` (사번:비밀번호)으로 받는다.
- **로그인 실패 잠금 (2026-11-09 사용자 결정)**: 계정(사번) 기준, `LoginHistory`(사번별 현재 상태 1행)
  - 5회 연속 실패마다 단계 상승: 10분 → 30분 → 1시간(최대). 최대를 짧게 둔 이유는 남이 일부러 틀려서 잠글 수 있기 때문
  - 잠긴 동안은 비밀번호를 확인하지 않고 429. 로그인 성공·관리자 해제(`PATCH /auth/unlock/:userId`)·관리자 비밀번호 초기화 시 초기화
  - 없는 사번도 같은 방식으로 세고(하루 지난 행은 배치로 정리), 응답 메시지는 원인과 무관하게 "사번 또는 비밀번호가 올바르지 않습니다." 없는 사번도 가짜 해시와 비교해 응답 시간으로 등록 여부를 알 수 없게 한다
  - 감사 로그: 실패마다 `LOGIN_FAILED`, 잠길 때 `LOGIN_LOCKED`, 해제 `LOGIN_UNLOCKED`. 잠긴 동안의 시도는 기록하지 않는다
- **IP 요청 수 제한**: `@nestjs/throttler`, 로그인·가입 라우트에만 1분 200회(429, 회사 NAT 뒤 직원들이 IP 하나를 함께 쓰므로 넉넉하게, 2026-11-27 10 → 200). 여러 사번에 한 번씩 시도하는 공격(계정 잠금으로 못 막음)과 감사 로그 폭증을 막는다. 카운터는 서버 메모리(서버 1대 기준)
- 쿠키 옵션은 `auth/const/refresh-cookie-const.ts`의 `refreshTokenCookieOptions()`로 모은다. `secure`는 `PROTOCOL=https`일 때만 켠다.
- **로그인 유지 (2026-11-18 사용자 결정)**: 로그인 화면의 체크박스, 기본 해제
  - 체크: refresh 쿠키에 `Max-Age`를 넣는다(기존 동작). 미체크: `Max-Age` 없는 세션 쿠키로 발급해 브라우저를 완전히 닫으면 로그아웃된다
  - 선택은 `AuthSession.rememberMe`에 저장해 재발급·비밀번호 변경·모든 기기 로그아웃에서도 유지한다. 서버 쪽 만료(유휴 1일, 절대 7일)는 체크 여부와 무관하게 같다
  - 회원가입 직후 자동 로그인은 유지로 처리한다. `POST /auth/login/emp` 본문에 `rememberMe`가 없어도 유지로 처리한다
  - 한계: 브라우저의 이전 세션 복원·백그라운드 실행을 켜면 세션 쿠키가 남을 수 있다
- **access는 stateless, refresh는 stateful**: 로그인 1번마다 `AuthSession` 행(기기별 세션)을 만들고, refresh token payload에 `sid`(세션 id)·`jti`(토큰 id)를 넣는다.
  - **access 검증은 회원·세션 DB를 보지 않는다.** payload에 `role`을 넣고 `req.user`는 payload(`id`·`empNo`·`role`·`tokenVersion`)로 채운다. 회원 정보가 필요하면 서비스가 조회한다(`GET /users/me` → `getMyInfo`).
  - 회원 조회(`tokenVersion` 비교·상태 확인)는 **재발급(`RefreshTokenGuard`)에서만** 한다. 그래서 권한 변경·퇴사·비활성·비밀번호 변경·모든 기기 로그아웃은 access 만료까지 **최대 10분 늦게** 반영된다(사용자 결정: 허용).
  - **rotation**: 재발급(`/token/access`)할 때마다 refresh token도 새 `jti`로 교체한다.
  - **재사용 감지**: 이미 교체된 `jti`가 다시 들어오면 탈취로 보고 그 세션을 폐기한다. 단 교체 후 1분 안의 직전 `jti`는 다른 탭의 동시 요청으로 보고 허용한다(유예 시간).
  - 만료: 유휴 1일(마지막 재발급 기준), 절대 7일(로그인 기준). 끝난 세션은 로그인할 때 그 사용자 것만 지운다.
- 로그아웃(`POST /auth/logout`)은 refresh 쿠키를 삭제하고 **이 기기의 세션만** 폐기한다. 쿠키가 없거나 무효여도 로그아웃은 성공한다.
- 모든 기기 로그아웃(`POST /auth/logout/all`)과 비밀번호 변경은 `tokenVersion`을 올려 다른 기기의 refresh를 즉시 막고(access는 만료까지 유효), **지금 기기의 세션만** 새 버전으로 갱신해 새 토큰을 준다. 기기 목록 `GET /auth/sessions`, 기기별 로그아웃 `DELETE /auth/sessions/:sessionId`.
- 시간 값은 `auth/const/token-const.ts`, 상세 구조는 [docs/backend/jwt-auth.md](../backend/jwt-auth.md) 참고.
- 비밀번호 변경 시 `tokenVersion`을 올려 기존 토큰의 재발급을 막고, 상태(퇴사·비활성)는 재발급 때 확인한다(403).
- **GUEST(승인 전) 차단은 API마다 `@Roles`로 명시한다** (2026-11-07 사용자 결정, A안). `RolesGuard`는 `@Roles`가 없으면 통과시키므로, **새 API는 반드시 `@Roles(UserRole.USER)` 이상을 붙인다**(애드온 포함). `@Roles` 없이 두는 것은 본인 계정용(마이페이지·비밀번호 변경·기기 세션·내 소속)뿐이고, 로그인 없이 쓰는 API는 `@IsPublic()`. 기본값을 USER 이상으로 바꾸는 방식(B안)은 현재 빠진 API가 없어 채택하지 않음.
- 프론트 연동 상세는 [docs/frontend/fe-01-auth.md](../frontend/fe-01-auth.md) 참고.

## 5.3 게시판

네이버 카페와 비슷하게 관리자가 게시판 자체를 생성할 수 있는 방식으로 구현한다.

예:

```text
Board
├── 자유게시판
├── 공지사항
├── 일정게시판
└── 기타 사용자 생성 게시판
```

게시판 타입을 컬럼으로 관리한다.

예:

```prisma
enum BoardType {
  CATEGORY  // 카테고리 (게시판을 묶는 용도)
  NORMAL    // 일반 게시판
  NOTICE    // 공지 게시판
  CALENDAR  // 캘린더
  ALBUM     // 앨범 (썸네일 그리드, 파일 기능 이후 구현)
}
```

기본 관계:

```text
Board (parentBoardId 자기 참조 → 카테고리 아래 게시판)
├── Post
│   └── Comment (parentCommentId 자기 참조 → 대댓글)
└── BoardAuth (게시판 접근 권한)
    └── BoardAuthJobTitle (허용 직책, N:M 중간 테이블)
```

- `Post`, `Comment`의 `createdId`는 `Users`와 작성자 관계(FK)를 맺는다.
- `BoardAuth` 조건: 부서(`includeSubDepartment`로 하위 부서 포함 여부), 최소 직급(`positionId` - 이 직급 이상 허용, `Position.sortOrder` 기준), 허용 직책 목록. 각 조건이 NULL/비어 있으면 해당 조건 없음.
- `BoardAuth` 규칙이 하나도 없는 게시판은 **관리자만 볼 수 있다**(기본 거부). 모든 조건이 비어 있는 규칙 하나가 "전체 허용"이다. 카테고리는 볼 수 있는 하위 게시판이 하나라도 있으면 표시한다.
- 게시판 계층: 상위 게시판은 `CATEGORY`만, `CATEGORY`는 최상위에만 둔다(최대 2단계). 부서별 게시판은 공용 게시판 + 글 단위 부서 범위 대신 **게시판마다 `BoardAuth` 부서 조건**으로 만든다(권한 검사를 게시판 단위로 유지).
- 대댓글 깊이는 제한하지 않는다. 댓글은 평면으로 조회해 메모리에서 트리로 만들고, 화면에서 들여쓰기 깊이만 제한한다. (공용 `toTreeList`에 정렬 기준 `createdAt`을 넘겨 사용)
- 부모 댓글이 삭제되어도 대댓글은 그대로 둔다. 삭제된 부모 댓글은 자리를 남기고 "(삭제된 댓글입니다)"를 회색 글씨로 표시한다(내용·작성자는 응답에서 제외).
- 댓글 권한: 조회는 게시판 읽기 권한, 작성·수정·삭제는 댓글 권한(`checkPost(…, 'comment')`). 수정은 작성자만, 삭제는 작성자 또는 게시판 관리자.
- 캘린더 통합 조회: 볼 수 있는 캘린더 게시판들의 일정을 한 화면에 모은다. 단일 캘린더 게시판은 같은 서비스에 `boardIds=[id]`를 넘긴 경우로 처리하고, 요청한 `boardIds`는 볼 수 있는 게시판과 교집합만 쓴다. 기간은 겹침 조건(`start < 조회 끝 && end >= 조회 시작`)으로 조회한다.
- **휴가자 표시 옵션** (2026-11-12 사용자 결정): 캘린더 게시판에만 `Board.showLeaves`(게시판 관리 화면 옵션 "휴가자 표시")를 켤 수 있다(다른 타입에 true면 400, 캘린더가 아닌 타입으로 바꾸면 자동 해제). 켜진 캘린더 게시판 화면은 휴가 애드온이 켜져 있을 때 휴가 API(`GET /approvals/leaves/calendar`)를 함께 불러 날짜마다 "휴가 N명" + 명단을 그린다(7.4 "휴가 화면 구성"). 통합 캘린더는 **보고 있는 게시판 중 하나라도 켜져 있으면 한 번만** 표시(일정 조회 응답의 `showLeaves`). 게시판(핵심)은 값만 저장하고 휴가를 모른다(10.1 허용한 타협 - 스키마만). 휴가 애드온이 꺼지면 옵션을 숨기고 값은 유지
- **일정 색** (2026-11-12 사용자 결정): 캘린더 게시판 글마다 작성자가 정해진 색 중 하나를 고른다(`Post.eventColor` enum `CalendarEventColor`: 빨강·주황·노랑·파랑·보라·회색, NULL = 기본 포인트색, 마이그레이션 `20261112210000_post_event_color`). 초록은 "휴가 N명" 항목 색이라 선택지에서 뺀다. 수정에서 생략하면 기존 색 유지, 일반 게시판은 무시(NULL). 라이트/다크 실제 색은 화면(`features/board/calendar-colors.ts`)이 정한다
- 캘린더 게시판 화면: 월간 달력(일~토, 앞뒤 달은 그 주만 흐리게, 일요일 빨강·토요일 파랑)이 기본이고 [목록]으로 그달 일정 목록을 본다. 여러 날 일정은 걸친 날마다 표시한다. API는 `GET /boards/events`(통합) / `GET /boards/:boardId/events`(단일), 한 번에 최대 62일.
- 캘린더 비밀 일정은 **달력·일정 목록에서 작성자 본인만** 본다(게시판 관리자·시스템 관리자도 제외). 게시글 상세는 기존 비밀글 규칙(작성자 + 게시판 관리자)을 따른다.
- 앨범 게시판:
  - 대표 이미지는 본문의 **첫 번째 이미지**(이 글에 연결된 `POST_IMAGE` 중 `order = 0`)다. 별도 컬럼(`thumbnailFileId`)을 두지 않는다. 이미지 순서를 본문 순서로 저장하므로 같은 정보를 두 곳에 두지 않기 위함이다. (대표 이미지 직접 지정이 필요해지면 그때 컬럼 추가)
  - 앨범 게시판에서 글을 작성할 때만 이미지 1개 이상을 필수로 검사한다.
  - NORMAL/NOTICE → ALBUM 타입 변경은 글이 있어도 허용하며, 대표 이미지가 없는 글은 대체 이미지(엑스박스)로 표시한다.
  - 썸네일은 **게시판 타입과 무관하게 모든 본문 이미지 업로드 시** 리사이즈해 따로 저장한다(원본 `images/<KST 연>/<월>/<uuid>.png` → `thumbnails/<연>/<월>/<uuid>.webp`, 원본 path에서 계산하므로 컬럼 없음). 업로드 API는 게시판을 모르고, 일반 → 앨범 변경 시 기존 글도 바로 그리드에 표시하기 위함이다. 목록 그리드에는 썸네일만 내려준다.
  - 목록 카드는 대표 이미지 1장만 보여 주고, 이미지가 2장 이상이면 우측 하단에 "+나머지 수(이미지 아이콘)"를 표시한다(목록 응답 `imageCount`, 글별 개수는 `GROUP BY` 한 번).

# 6. 시설 예약 (애드온 `reservations`)

회의실·차량·장비 등 회사 시설을 등록하고 특정 시간에 예약할 수 있도록 한다. (2026-11-09 사용자 결정: 회의실 → 시설로 일반화)

Entity:

```text
FacilityCategory      시설 분류 (관리자가 만듦: 회의실, 차량, 장비 …, sortOrder)
                      예약 규칙: slotMinutes(단위, 기본 30) / openMinute·closeMinute(자정부터 분, 기본 540·1080)
                                 operatingDays(ISO 요일 배열, 기본 [1..5]) / maxAdvanceDays(기본 90)
Facility              시설 (categoryId 필수, isActive로 사용 여부)
FacilityReservation   예약 (startAt / endAt, status: RESERVED / CANCELLED)
FacilityUnavailable   예약 불가 기간 (점검 등)
```

규칙 (2026-11-09 사용자 결정):

- 이름은 "시설"로 일반화한다. 모든 시설은 분류에 속한다(`categoryId` 필수). 시설이 남아 있는 분류는 삭제할 수 없다.
- **분류가 예약 규칙을 정한다**: 예약 단위(분), 운영 시간(시작·종료), 운영 요일, 최대 며칠 앞까지 예약 가능. (처음에는 "분류는 묶어서 보여 주는 용도"였으나 같은 날 변경) 승인 여부는 다루지 않는다(전부 바로 확정).
- 한 분류에 여러 시설이 들어가고, **다른 시설끼리는 예약 시간이 겹쳐도 된다. 한 시설 안에서는 겹칠 수 없다.**
- 주차 자리 배정(해지할 때까지 유지)은 시설 예약과 성격이 달라 제외한다. (별도 애드온 후보, Plan.md "시간이 날 때")

시간·겹침:

- 시간 범위는 **`[시작, 종료)`**: 10:00~11:00과 11:00~12:00은 둘 다 예약된다.
- 예약은 **하루 안에서만**(시작·종료가 같은 날, 운영 시간 안, 운영 요일). 시작·종료는 분류의 예약 단위에 맞아야 한다. 시각은 한국 시간 기준으로 판단한다.
- 겹침 방지는 **이중**: ① 트랜잭션 안에서 겹치는 예약·사용 불가 기간을 검사(사용자에게 보여 줄 메시지) ② PostgreSQL exclusion constraint(같은 시설 + 시간 범위 겹침 + `RESERVED` + 삭제 안 됨, `btree_gist`)로 동시 요청 최종 방어 → 위반 시 409.
- 사용 불가 기간에는 새 예약을 받지 않는다.
- DB 제약은 마이그레이션 SQL에 직접 작성(`20261109224642_facility_reservation_rules`): `facility_reservation_no_overlap`(exclusion), `facility_reservation_time_check`·`facility_unavailable_time_check`(종료 > 시작), `facility_category_settings_check`(단위 > 0, 0 ≤ 시작 < 종료 ≤ 1440, 기간 > 0, 요일 1~7 하나 이상·NOT NULL). Prisma `migrate diff`가 이 제약들을 지우지 않음을 확인.

권한 (예약 수정·취소·삭제):

| | 시작 전 | 시작 후(지난 예약) |
|---|---|---|
| 예약자 본인 | 수정·취소·삭제 | 불가 |
| 관리자(`ADMIN`) | 수정·취소·삭제 | 삭제만 |

- **지난 예약 = 시작 시각이 지난 예약**(진행 중 포함). 일찍 끝나도 그대로 둔다.
- 취소 = `status: CANCELLED`(기록이 남고 "취소됨"으로 보임, 그 시간은 다시 예약 가능). 삭제 = soft delete(목록에서 숨김, DB에는 남음).
- 일괄 처리(`ids` 배열, 최대 100건): 취소 `PATCH /reservations/bulk/cancel`, 삭제 `DELETE /reservations/bulk`, 시간 변경 `PATCH /reservations/bulk/time`. 권한은 위 표와 같고 **한 건이라도 처리할 수 없으면 전체 실패**(트랜잭션). 단건 취소·삭제도 같은 서비스를 쓴다. 관리자 예약 관리 화면에서 체크박스로 골라 쓴다.
  - 일괄 시간 변경(2026-11-14 사용자 결정): **날짜는 예약마다 그대로 두고 시작·종료 시각(`startTime`·`endTime`, HH:mm)을 모두 같은 시간대로 맞춘다**. 같은 시설·같은 날짜 예약이 둘 이상 섞이면 반드시 겹치므로 400. 규칙 위반은 400, 겹침은 409(어느 예약인지 메시지에 표시). 관리자가 바꾼 남의 예약은 예약별로 시간 변경 알림.

사용 불가 기간:

- 등록할 때 겹치는 기존 예약이 있어도 **저장하고, 관리자 화면에 경고(겹치는 예약 목록)만 표시**한다. 기존 예약은 그대로 두고, 예약자에게 알림은 보내지 않는다.

반복 예약 (스키마 변경 없음):

- 기간 + 같은 시간대 + **요일 선택**(매일 = 모든 요일)으로 날짜마다 별도 예약을 만든다.
- 이미 예약된 날짜·사용 불가 기간·운영하지 않는 요일은 **건너뛰고**, 응답에 만든 날짜와 건너뛴 날짜(이유)를 함께 준다.
- 기간은 분류의 "최대 며칠 앞까지" 안에서만. 묶음 정보가 없으므로 취소는 날짜별(여러 건은 내 예약 목록에서 골라 일괄 취소).
- 미리 검사한 뒤 저장하는 사이에 다른 요청이 같은 시간을 잡으면 DB 제약으로 요청 전체가 409 → 다시 시도하면 그 날짜는 건너뛴다(드문 경우라 감수).

API·구조: [docs/backend/reservations.md](../backend/reservations.md) (2026-11-09 백엔드 구현)

- 시간표에는 예약 제목·예약자 이름을 모든 회원에게 공개한다. 앞으로의 예약이 있는 시설은 삭제할 수 없고(409) 사용 안 함은 허용한다(기존 예약 유지). 관리자가 남의 예약을 취소·삭제하거나 시간을 바꾸면 예약자에게 알린다(제목·설명만 고치면 알리지 않음). 예약 수정에서 시설은 바꿀 수 없다. (2026-11-09 사용자 결정)

# 7. 전자결재 / 연차·병가 신청

연차·병가 신청을 전자결재 흐름에 통합한다.
단, 모듈과 DB 테이블은 합치지 않는다. **전자결재는 공통 승인 기능**을 담당하고, **연차는 별도의 업무 데이터**로 분리해 결재 문서와 결합한다.
이후 다른 업무(지출결의, 일반 기안 등)도 같은 방식으로 결재에 연결할 수 있다.

## 7.1 모듈 구조

## 7.2 DB 구조

| 테이블 | 역할 | 주요 데이터 |
|---|---|---|
| ApprovalLineTemplate | 결재라인 템플릿 | 이름, 구분(`scope`: ADMIN 공용 / DEPARTMENT 부서 / PERSONAL 개인), 부서 ID 또는 소유자 ID |
| ApprovalLineTemplateStep | 템플릿에 속한 결재자와 순서 | 템플릿 ID, 결재자 ID, 순서(템플릿 내 unique), 단계명 |

| ApprovalDocumentStep | 문서별 결재 진행 내역 (스냅샷) | 문서 ID, 결재자 ID, 순서, 상태(`WAITING / PENDING / APPROVED / REJECTED`), 의견, 결재 당시 이름·부서·직급·직책명 |

## 7.3 동작 흐름

```text
휴가 신청 → LeaveRequest + ApprovalDocument 생성
         → 결재라인(ApprovalLineTemplateStep)을 ApprovalDocumentStep으로 복사 (스냅샷)
         → 1번 결재자 승인 → 다음 결재자 … → 최종 승인 → LeaveRequest 확정 + 잔여 연차 반영
                         └ 어느 단계든 반려 → 문서 반려, 이후 단계 진행 중단
         (상태가 바뀔 때마다 ApprovalDocumentHistory에 기록)
```

- 결재 진행 내역은 문서별 `ApprovalDocumentStep`에 복사해 두므로, 결재라인을 나중에 수정해도 진행 중인 문서에는 영향이 없다.
- 결재 당시의 결재자 이름·부서·직급·직책명도 `ApprovalDocumentStep`에 함께 저장해, 이후 인사이동이 있어도 문서에는 결재 당시 정보가 남는다.
- 결재자는 자기 차례인 단계만 승인·반려할 수 있다.
- 단계는 **순차**로 진행하고, 한 단계에 여러 명을 넣으면 **병렬**(모두 승인해야 다음 단계)이다. (2026-11-10 추가, 7.5) 전결·대결·참조·수신은 제외

## 7.4 구현 시 결정 필요

- ~~최종 승인 → 업무 처리 연결 방식~~ → **결정됨 (2026-11-07, 사용자 결정): 문서 유형별 처리기 등록**
  - 결재는 "문서 유형 → 최종 승인 처리기" **등록 지점**을 열어 두고, 업무(휴가)가 켜지면 자기 처리기를 등록한다. 결재 본체는 휴가를 모른다. (10.1의 등록 지점 방식과 같은 패턴)
  - 최종 승인 시 결재가 **같은 트랜잭션(`tx`)을 처리기에 넘겨** 호출한다 → 승인과 연차 반영이 함께 커밋되거나 함께 롤백된다.
  - 처리기가 등록되지 않은 문서 유형(옵션이 꺼진 업무)은 문서를 만들 수 없다.
  - 비교한 선택지: 결재가 휴가를 직접 호출(공통 결재가 업무를 알게 되고 문서 종류마다 분기 추가) / 이벤트(보통 트랜잭션 밖에서 처리돼 승인만 되고 연차 반영이 실패하는 경우를 따로 처리해야 함).
- ~~잔여 연차 관리 방식~~ → **결정됨 (2026-11-10, 사용자 결정): 부여는 저장, 사용은 합계로 계산** — 계산식·예시표·관리자 조정 절차는 [leave_calculate_manual.md](leave_calculate_manual.md)(규칙을 바꿀 때 이 문서부터 고친다)
  - `LeaveGrant`(회원, 연도) 한 행: `baseDays`(규칙 계산값) + `adjustDays`(관리자 ±, 사유) → **부여 일수 = 둘의 합**. 계산값과 조정값을 나눠 두어 다시 계산해도 관리자 조정이 지워지지 않는다(특정 회원 계산이 틀리면 관리자가 조정).
    - **영구 조정 (2026-11-12 사용자 결정)**: 임원 전입처럼 다른 근속을 인정할 때 매년 조정을 다시 넣지 않도록 회원별 영구 조정값(`LeaveUserSetting`)을 두고 연도 행의 `permanentDays`로 복사한다 → **부여 = 계산값 + 영구 조정 + 매년 조정**(25일 한도 없음). 연차 관리 [조정] 창에서 "영구 조정값·사유"와 "매년 초기화되는 조정값·사유"를 함께 저장, 저장하면 올해부터 반영(입사한 해·지난 연도 제외). 입사한 해의 월 단위 연차는 매년 조정값으로만. (검토한 대안: 연차 산정 기준일(날짜) - 사용자가 일수 방식을 선택)
  - 사용 일수는 저장하지 않는다: 그 연도에 최종 승인된 연차(`ANNUAL`) `LeaveRequest.days` 합계. 저장값과 승인 내역이 어긋날 일이 없다.
  - 비교한 선택지: 전부 계산(테이블 없음 — 관리자 조정·비례 부여를 표현할 곳이 없음) / 부여·사용 모두 저장(`LeaveBalance` — 사용 일수를 승인 내역과 맞춰야 함, 신청 시 확인을 고르면 조건부 UPDATE의 장점도 줄어듦).
  - **기준 기간: 회계연도(1/1~12/31)**. 회계연도여도 부여 일수는 근속에 따라 사람마다 다르다. 연도를 걸치는 휴가는 나눠 신청한다.
  - **계산 규칙** (Y = 연도, J = 입사 연도, 순수 함수 하나로 두고 단위 테스트):

    | 연도 | baseDays |
    |---|---|
    | Y = J | 월 단위 연차(제60조 제2항): 입사한 해 안에서 한 달마다 1일 |
    | Y ≥ J+1 | n = Y − J, `15 + floor((n−1)/2)`, 최대 25 (제60조 제4항: 3년 이상 계속 근로 시 2년마다 1일 가산, 한도 25일) - **입사 다음 해 1/1에 15일** |

    - **2026-11-12 변경 (사용자 결정)**: 입사 다음 해는 15일을 모두 준다(1년차라도 15일). 이전 안(2026-11-10)의 "남은 월 단위 + 비례 부여 `15 × 작년 근무일 / 365`(0.25 단위 올림)"는 삭제했다. 다음 해 부여 일수는 이전 안보다 항상 같거나 많고, 다음 해 값이 기준일과 무관해져 12월에 미리 확정할 수 있다.
    - 예: 2026-07-01 입사 → 2026년 5 / 2027년 15 / 2028년 15 / 2029년 16. 개근 여부는 보지 않는다.
  - **부여 배치: 매월 1일 00시(KST) 재계산** — 재직자 전원의 올해 `baseDays`를 upsert(1월 1일 실행이 새해 행을 만든다), `adjustDays`는 건드리지 않는다. 입사한 해의 월 단위 연차가 매달 늘고 연도 중 입사자는 행이 없으므로 1/1 한 번으로는 부족하다. 실행이 한 번 빠져도 다음 실행에서 맞춰진다. 관리자 화면에 "지금 재계산"(같은 서비스 호출).
    - **12월에는 다음 해 행도 만든다** (2026-11-12 사용자 결정): 다음 해 1월 휴가를 12월에 미리 신청할 수 있게. 1/1 배치는 같은 행을 같은 값으로 다시 계산한다(조정값 유지).
  - **이월 없음, 기록은 남김**: 연도별 행을 지우지 않고 미사용(부여 − 그해 사용)은 조회 시 계산한다(연차수당 근거). 배치와 관리자 조정은 **올해 행(12월에 만든 다음 해 행 포함)만** 바꿀 수 있어 지난 연도 값은 바뀌지 않는다. 조정 이력은 감사 로그.
- ~~잔여 연차 차감 시점~~ → **결정됨 (2026-11-10, 사용자 결정): 신청 시 확인 + 최종 승인 시 차감**
  - 대상은 연차(`ANNUAL`)만. 병가·공가는 결재만 거치고 잔여 연차와 무관하다.
  - 상신할 때 `사용 + 결재 진행 중(REQUESTED·IN_PROGRESS) 신청일 합계 + 이번 신청 ≤ 부여`를 확인한다. 진행 중 합계도 결재 상태로 계산하므로 별도 "예정" 컬럼이 없고, 반려·회수 시 되돌릴 것이 없다.
  - 같은 회원이 동시에 두 건을 상신하면 둘 다 통과할 수 있으므로 신청 확인은 **회원 단위 잠금**(예: 회원 행 `SELECT ... FOR UPDATE`) 안에서 한다. 최종 승인 처리기도 같은 확인을 한 번 더 한다.
- **휴가 신청 규칙 (2026-11-12, 사용자 결정)**
  - **사용 일수**: 종일(`FULL`) = 시작일~종료일의 **달력 일수**(양 끝 포함). 서버는 주말·공휴일을 가정하지 않는다(회사마다 쉬는 요일이 다를 수 있음) → 쉬는 날은 신청자가 기간에서 빼고 **나눠 신청**한다. 반차(`HALF`) 0.5일, 반반차(`QUARTER`) 0.25일이고 하루 안(시작일 = 종료일).
  - **반차·반반차 시각**: 시작 시각만 받고(30분 단위) 종료는 서버가 채운다(반차 +4시간, 반반차 +2시간, 그날 24:00을 넘으면 안 됨). 근무시간·점심시간 규칙은 두지 않는다.
  - **기간 겹침**: 같은 회원의 결재 진행 중·승인된 휴가(유형 무관)와 ① **시간이 겹치면 불가**(2026-11-12 추가, 종일은 그날 00:00~24:00, 반차는 [시작, 종료) - 끝나는 시각에 시작하는 것은 가능) ② 합쳐서 **하루 합계 1일까지**(예: 같은 날 09:00 반차 + 13:00 반차는 가능, 09:00 반차 + 11:00 반차·종일 + 반차는 불가). 상신·최종 승인 때 잔여 확인과 같은 회원 잠금 안에서 검사한다.
  - 입사일을 바꾸면 연차 부여는 다음 월 배치 또는 "지금 재계산" 때 반영된다. 휴가 옵션이 켜져 있으면 관리자 회원 상세에서 입사일 저장 후 안내 창(+ 지금 재계산 버튼)을 띄운다(2026-11-12).
  - **휴가 화면 구성 (2026-11-12 사용자 결정)**: 신청은 [전자결재] 작성 화면에서 문서 유형 "휴가"로(저장만 휴가 API), 마이페이지 아래 [휴가내역] 메뉴에 전체 휴가(부여 = 계산값 + 조정값)·남은 연차·신청 이력(병가·공가 포함, 유형 표시, 임시저장·반려·회수도 상태 배지). 캘린더에는 하루에 "휴가 N명" 항목 하나 + 마우스를 올리면 명단 "이름(직급/소속): 휴가(종일) 또는 시각" - **전 직원**이 보고, **최종 승인된 휴가만**, 휴가 유형은 내보내지 않음(`GET /approvals/leaves/calendar`). 캘린더는 핵심이라 휴가를 모르므로 화면이 두 API를 합친다. 별도 휴가 캘린더는 만들지 않고 **캘린더 게시판의 "휴가자 표시" 옵션**으로 표시한다(5.3)
  - **지난 날짜 신청 허용**(병가 등 사후 신청, 결재자가 판단). 한 신청은 한 연도 안.
  - 신청 화면은 휴가 API(`POST /approvals/leaves`)로 임시저장 문서 + `LeaveRequest`를 같은 트랜잭션에서 만들고, 상신·회수·승인·반려·삭제·다시 기안은 결재 문서 API를 그대로 쓴다. 문서 제목은 유형·기간으로 서버가 만든다.
  - 배치에 **휴직(`INACTIVE`) 회원 포함**(재직자 전원, 휴직 차감은 관리자 조정). 관리자 조정은 **부여 합계(`base + adjust`) ≥ 0**만 막고, 조정 후 잔여가 음수가 되는 것은 허용(화면에 음수 표시, 새 신청은 불가).

## 7.5 결재 규칙 (2026-11-10, 사용자 결정)

- **상태 전이** (문서)

  ```text
  DRAFT ──상신──▶ REQUESTED ──첫 승인──▶ IN_PROGRESS ──마지막 승인──▶ APPROVED
    │ (수정·삭제)      │                      │
    │                 ├─회수(기안자)─▶ CANCELLED
    │                 └─반려──────────────────┴──────────────▶ REJECTED
  ```
  - **임시저장(DRAFT)** 지원: 본인만 보며 결재라인 미확정도 허용, 수정·삭제(soft) 가능. 상신할 때 결재라인을 검사하고 스냅샷을 저장한다.
  - **회수**는 첫 승인 전(REQUESTED)까지 기안자만. 한 명이라도 승인했으면(IN_PROGRESS) 회수할 수 없고 결재자가 반려해야 한다.
  - **반려·회수된 문서는 고치지 않고 "다시 기안"으로 복사**(제목·본문·첨부·결재라인 → 새 DRAFT). 원래 문서는 그대로 남아 반려 사유가 보존되고 상태는 한 방향으로만 흐른다.
  - 상신 후에는 본문·첨부를 수정할 수 없다.
  - 결재자는 자기 차례(PENDING) 단계만 승인·반려. 동시 처리(두 탭·더블 클릭)는 `WHERE status = PENDING` 조건부 UPDATE로 막고 0행이면 409.
  - **반려는 의견 필수**, 승인 의견은 선택.
  - 상태가 바뀔 때마다 `ApprovalDocumentHistory`에 기록한다.
  - **임시저장 생성과 상신은 API를 나눈다**(`POST /approvals/documents` → `PATCH :id/submit`). 화면의 "상신" 버튼은 저장 후 상신을 연달아 호출한다.
  - 동시 처리 구현: 모든 상태 변경은 ① 문서 행을 기대 상태·단계 조건으로 UPDATE(잠금) → ② 단계 행을 기대 상태·결재자 조건으로 UPDATE 순서로 한다. 승인·반려·회수·결재자 교체가 같은 순서로 잠가 차례대로 실행되고 교착이 생기지 않는다. 이미 처리한 결재를 다시 누르면 409.
- **병렬 단계** (2026-11-10 사용자 결정): 한 단계에 여러 명을 넣을 수 있다.
  - 저장: 행 하나 = 결재자 한 명, 같은 `stepOrder` = 같은 단계. unique는 `(문서, 결재자)`(같은 사람 중복을 DB가 막음). 템플릿도 같은 구조로 단계 묶음을 저장하고, 단계명은 단계의 모든 행에 같은 값.
  - **모두 승인(AND)** 해야 다음 단계가 열린다. 첫 승인에서 문서는 결재중(→ 회수 불가)이 되고 단계는 유지된다.
  - **한 명이라도 반려하면 문서 반려**. 같은 단계에서 아직 처리하지 않은 사람은 대기로 돌려 결재 대기함에서 뺀다.
  - 단계가 열리면 그 단계 결재자 모두에게 결재 요청 알림. 관리자 교체는 한 명씩(`PATCH :id/steps/:stepId` - 단계 번호로는 한 사람을 정할 수 없어 행 id).
  - ⭐ 같은 단계 두 명이 동시에 승인: 문서 행을 먼저 잠그므로 뒤의 요청은 앞 요청 커밋 후 "남은 인원"을 세어, 마지막 승인자만 다음 단계를 연다(둘 다 200, 다음 단계·알림은 한 번). 다음 단계 알림 대상도 잠근 뒤 다시 읽는다(그사이 교체 대비).
  - 최종 방어선: exclusion constraint `EXCLUDE USING gist (approval_document_id WITH =, step_order WITH <>) WHERE status = 'PENDING'` - 같은 문서의 PENDING 행은 모두 같은 단계 번호 (예전의 "문서당 PENDING 하나" 부분 unique를 대신함)
  - 입력 형식: `steps: [{ approverIds: number[], name? }]` (배열 순서 = 결재 순서, 빈 단계 불가, 전체 1~10명)
- **결재함** (`GET /approvals/documents?box=`)

  | box | 들어가는 문서 | 정렬 |
  |---|---|---|
  | `drafts` 임시저장 | 내가 기안, `DRAFT` | 최근 수정 |
  | `mine` 기안함 | 내가 기안, `DRAFT` 제외 전부(`status` 필터) | 상신 최신 |
  | `pending` 결재 대기 | 내 단계 `PENDING`, 문서 `REQUESTED`·`IN_PROGRESS` | 상신 오래된 순 |
  | `upcoming` 결재 예정 | 내 단계 `WAITING`, 문서 `REQUESTED`·`IN_PROGRESS` (아직 내 차례가 아님) | 상신 오래된 순 |
  | `processed` 결재 완료 | 내 단계 `APPROVED`·`REJECTED` (문서 상태 무관) | 내가 처리한 시각 최신 |
  | `all` 전체 (관리자) | 전체, `DRAFT` 제외 | 상신 최신 |

  반려·회수로 내 차례가 끝내 오지 않은 문서는 어느 결재함에도 나오지 않는다.

  - **탭 건수** (2026-11-10 사용자 결정, `GET /approvals/documents/counts`): 결재 대기·결재 예정·임시저장은 목록 개수, **기안함은 결재요청·결재중인 내 문서만** 센다(목록은 완료·반려·회수까지 보임). 결재 완료·전체 문서는 계속 늘기만 해서 표시하지 않는다. 0건은 숫자를 숨긴다.
- **결재라인**
  - 기안자가 결재자를 **자유 지정**하고 순서를 정한다. 템플릿은 목록을 채우는 **불러오기 단축키**(불러온 뒤 수정 가능), 사용한 템플릿 id만 기록.
  - 검사: 결재자 1~10명, 기안자 본인 제외, 같은 사람 중복 불가, 재직(ACTIVE) + USER/ADMIN만. 스냅샷(이름·주 소속 부서·직급·직책)은 상신 시점에 저장한다.
  - 템플릿: 공용(ADMIN)·부서(DEPARTMENT)는 **결재라인 관리자**가 만들고, 개인(PERSONAL)은 본인이 만든다(`ownerUserId`는 토큰의 회원 id, 남의 개인 라인은 관리자도 보지 않으며 접근 시 404). 공용은 전원, 부서 템플릿은 그 부서 소속자(겸직 포함), 개인은 본인만 불러온다. `scope`와 `departmentId`/`ownerUserId`의 짝은 서비스 검사 + DB CHECK 제약.
  - **결재라인 관리자 (`Role.ADMIN`과 별개 위임 권한)**: ADMIN이 규칙을 등록·해제하고, ADMIN은 규칙 없이도 항상 관리할 수 있다. 결재 애드온의 테이블(`ApprovalLineManager`)이라 핵심은 모른다(게시판 `BoardAuth`와 같은 기능별 권한). 토큰에 넣지 않고 요청마다 DB로 판정해 지정·해제가 즉시 반영된다.
    - 한 행 = **대상 1개**(회원 `userId` 또는 직책 `jobTitleId` 중 정확히 하나) + **범위**: `ALL`(공용 + 모든 부서 라인) / `DEPARTMENT`(지정한 `departmentId`의 부서 라인) / `MY_DEPARTMENT`(직책 대상만 — 그 직책으로 소속된 부서의 라인, 겸직은 소속 단위, 인사이동을 자동으로 따라감). **맡은 부서의 하위 부서 전체(모든 단계)도 관리한다** (2026-11-10 사용자 결정: 기술본부 관리자 → 개발1팀·개발2팀·인프라팀·정보보안팀의 부서 결재라인도 추가). 판정과 화면 선택지가 같은 범위(`withDescendants`)를 쓴다.
    - 예: 회원 홍길동 → 전체 / 회원 김서무 → 영업부 / 직책 팀장 → 본인 부서(영업부 팀장은 영업부 라인만).
    - 공용 라인은 범위 `ALL`만 관리한다. 퇴사·휴직·삭제된 회원의 규칙은 판정에서 무시한다(로그인 불가).
    - DB CHECK: 대상 둘 중 정확히 하나, `DEPARTMENT` ⇔ `departmentId` 있음, `MY_DEPARTMENT` ⇒ 직책 대상.
    - 비교한 선택지: 게시판 권한과 같은 조건(부서·하위·직급·직책 목록 AND) + 범위 — 부서가 대상 조건과 관리 범위에 두 번 나오고 중간 테이블이 늘어 제외.
- **열람**: 기안자 + 결재라인 전원(아직 차례가 아닌 WAITING 포함) + 관리자(전체 조회만, 처리는 못 함). 그 외 404. DRAFT는 기안자만.
- **결재자 부재**: 관리자가 진행 중 문서의 남은 단계(PENDING/WAITING) 결재자를 교체한다(새 스냅샷, 이력·감사 로그). 퇴사·휴직 상태 변경은 막지 않는다.
- **핵심 데이터 삭제는 막지 않고 결재 쪽 조회에서 숨긴다** (2026-11-10 사용자 결정): 회원·부서·직책 삭제 시 결재 데이터를 확인하지 않는다(10.1 등록 지점을 만들지 않음).
  - 이유: 셋 다 soft delete라 FK가 깨지지 않고, 부서·직책은 소속 인원이 있으면 이미 삭제할 수 없어 남은 템플릿·관리자 규칙에 해당하는 사람이 없다. 막아 줄 위험이 없는데 핵심에 등록 장치와 모든 삭제 서비스 수정이 필요해 과설계로 판단.
  - 결재 쪽 처리: 관리자 판정·부서 템플릿 조회는 `department.deleted = false`, `jobTitle.deleted = false`로 거른다. 관리자 화면의 규칙·템플릿 목록에는 "(삭제된 부서/직책)"으로 표시해 관리자가 직접 지운다.
  - 템플릿에 들어간 삭제·퇴사 회원은 불러올 때 "사용할 수 없는 결재자"로 표시해 빼고 상신한다.
  - 진행 중 문서의 남은 결재자가 삭제되면 상세에 "결재자 삭제됨"을 표시하고 **관리자 결재자 교체**로 푼다.
- **알림** (기존 3종): 내 차례 도착 → 그 결재자(`APPROVAL_REQUESTED`), 최종 승인·반려 → 기안자(`APPROVAL_APPROVED`·`APPROVAL_REJECTED`). 관리자 교체로 새 결재자가 PENDING이 되면 `APPROVAL_REQUESTED`. 중간 승인은 알리지 않는다.
- **본문·첨부**: 게시판과 같이 Tiptap 본문(백엔드 정제 재사용) + 첨부(`FileTargetType.APPROVAL_DOCUMENT`, 열람 권한 확인 후 다운로드). 본문 이미지는 공개 uuid 주소라 결재 문서에는 만들지 않는다.

# 8. 채팅 (애드온 `chats`)

> 규칙 확정 2026-11-13(사용자 결정). 구조 3가지(보내기는 REST, 받는 사람은 user room, 소켓 연결 수명 = access token 수명)는 NestJS_SNS 채팅 구조를 검토한 뒤 정했다. 검토 내용은 devlog 2026-11-13.

## 8.1 구조

```text
chats/
├── chats.module.ts
├── chat-rooms.controller.ts / chat-rooms.service.ts        # 방 목록·생성·초대·내보내기·나가기·읽음
├── chat-messages.controller.ts / chat-messages.service.ts  # 메시지 조회·보내기·수정·삭제
├── chats.gateway.ts   # 소켓 연결 인증, user room, 토큰 만료 시 연결 끊기 (클라이언트 이벤트는 받지 않음)
├── chat-events.ts     # 서버 → 클라이언트 푸시 (서비스가 커밋 후 호출)
└── dto/
```

| 역할 | 담당 |
|---|---|
| 보내기·수정·삭제·방 관리·읽음 | REST (`@Roles(USER)`, DTO 검증, 트랜잭션, 감사 로그) |
| 실시간 받기 | Socket.IO, 서버 → 클라이언트 푸시만. 클라이언트가 보내는 소켓 이벤트는 없다 |

- 서비스는 **트랜잭션 커밋 후** `ChatEvents`를 호출해 푸시한다(알림 `*-notifier.ts`와 같은 위치). 푸시가 실패해도 업무는 성공이다.
- 받는 사람은 매번 DB의 **활성 참여자**(`leftAt IS NULL`)로 정하고, 각자의 `user:{id}` room으로 보낸다(`server.to([...]).emit` 한 번). 채팅방 room은 두지 않는다. 그래서 초대·퇴장 때 소켓 room을 맞출 일이 없고, 나간 사람은 자동으로 받지 않는다.
- 단일 서버 기준. 서버를 여러 대로 늘리면 room 정보를 공유하는 Redis adapter가 필요하다(설명만).

## 8.2 소켓 연결

- namespace `/chats`, 서버 path `/socket.io`. 브라우저는 `/api/socket.io`로 접속한다(Next rewrite·Nginx가 `/api`를 떼고 전달).
- handshake `auth.token`에 access token을 넣는다. 검증: 서명·만료·`type=access` + DB에서 `tokenVersion` 일치·status `ACTIVE`·삭제 안 됨·role USER 이상. 실패하면 연결을 거부한다(`connect_error`).
- 연결되면 `user:{id}` room에 넣는다.
- **access token의 `exp` 시각에 서버가 연결을 끊는다.** 클라이언트는 `auth`를 함수로 넘겨 재연결 때 최신 토큰을 쓰고, 다시 연결되면 열린 방의 메시지를 REST로 다시 받는다.
  - 그래서 소켓도 REST처럼 권한 변경·퇴사·로그아웃이 최대 10분 안에 반영된다. 핵심(auth·users)이 채팅을 호출하지 않아도 된다(R-ARCH-01).

서버 → 클라이언트 이벤트:

| 이벤트 | 받는 사람 | 내용 |
|---|---|---|
| `message:created` | 방의 활성 참여자 | 새 메시지 (시스템 메시지 포함) |
| `message:updated` | 〃 | 수정된 메시지 |
| `message:deleted` | 〃 | `{ roomId, messageId }` |
| `room:read` | 〃 | `{ roomId, userId, lastReadMessageId }` (화면이 안 읽은 사람 수를 다시 계산) |
| `room:updated` | 〃 (새로 들어온 사람 포함) | `{ roomId }` 방 정보·참여자가 바뀜 (생성·초대·내보내기·나가기·OWNER 변경) |
| `room:removed` | 내보내진 사람 | `{ roomId }` (목록에서 제거) |

## 8.3 채팅방 규칙

- 대상: USER 이상, `ACTIVE`, 삭제되지 않은 회원끼리. GUEST는 쓸 수 없다. 관리자도 남의 채팅을 볼 수 없다(열람 API 없음, 필요하면 개발자가 DB에서 확인).
  - 상대 검색: `GET /chats/users?search=` (USER 이상) - 위 대상 조건 + 본인 제외, 이름·사번·소속 부서명(겸직 포함), 이름순 최대 20명. 결재 애드온의 결재자 검색은 쓰지 않는다(애드온끼리 의존 금지, R-ARCH-01). (2026-11-13 사용자 결정)
- 1:1 (`DIRECT`)
  - 두 사람당 방 하나(`directKey = "작은id:큰id"`, 부분 unique). 이미 있으면 그 방을 돌려준다.
  - 나가기 = 내 목록에서 숨기기(`leftAt`). 상대가 메시지를 보내거나 내가 다시 1:1을 열면 같은 방에 다시 참여한다(`leftAt` NULL, `joinedAt` 갱신 → 이전 기록은 보이지 않음).
  - 상대가 `ACTIVE`가 아니거나 삭제되면 **읽기 전용**: 기록은 보이고 보내기는 막는다.
- 그룹 (`GROUP`)
  - 생성: 본인 포함 3명 이상, 이름은 선택(1~50자). 만든 사람이 OWNER. 이후 2명만 남아도 그룹으로 유지한다.
    - 이름을 비우면 참여자(본인 포함) 이름으로 만든다: 한글이 아닌 이름(영문 등) 먼저 → 한글 가나다순, 3명까지 쉼표, 넘으면 "외 N명" (예: "Michael Johnson, 관리자, 신민아 외 2명"). 만들 때 한 번만 저장하고 이후 참여자가 바뀌어도 그대로 둔다(OWNER가 바꿀 수 있음). `chats/util/chat-room-name.util.ts` (2026-11-13 사용자 결정)
  - 초대: 참여자 누구나. 내보내기: OWNER만(본인 제외).
  - 다시 초대된 사람은 기존 참여 행을 다시 쓴다(`leftAt` NULL, `joinedAt` 갱신, role MEMBER, `lastReadMessageId` NULL).
  - OWNER 나가기: 다음 OWNER를 지정(`nextOwnerId`)하고, 지정하지 않으면 가장 오래 참여한 사람(`joinedAt`, 같으면 회원 id 순)에게 자동으로 넘긴다.
  - 비활성 회원이 있어도 남은 사람끼리 계속 보낼 수 있다.
  - 마지막 사람까지 나가도 방 행과 메시지는 남긴다(누구의 목록에도 나오지 않음). 방 삭제 API는 없다.
- 방 이름 (2026-11-13 사용자 결정) - 화면 표시 순서: 나만 보는 이름 → 기본 이름 → (1:1) 상대 이름
  - **기본 이름**(`ChatRoom.name`): 그룹만, OWNER가 바꾼다. 모든 참여자에게 보이고 시스템 메시지를 남긴다.
  - **나만 보는 이름**(`ChatRoomMember.customName`): 참여자 누구나, 1:1·그룹 모두. 본인에게만 보이며 비우면 기본 이름으로 돌아간다. 나갔다가 다시 참여하면 초기화된다.
  - 참여자 변경과 같이 OWNER 확인 후 바꾸므로 기본 이름 변경도 방 행을 잠근다. 두 이름 변경 모두 감사 로그는 남기지 않는다(8.6의 기록 대상이 아님).
- 시스템 메시지(`type=SYSTEM`): 그룹 생성·초대·내보내기·나가기·OWNER 변경·기본 이름 변경을 같은 트랜잭션에 남긴다. `senderId` = 행위자. 화면은 일반 메시지와 구분해 가운데 문구로 표시한다.
  - 1:1 나가기는 남기지 않는다. 상대에게는 보이지 않는 "숨기기"이기 때문이다.

## 8.4 메시지 규칙

- 참여 시점 이후 메시지만 보인다(`createdAt >= joinedAt`). 다시 참여해도 같다.
- 보내기: 활성 참여자만, 텍스트 1~2000자. 보내면 방의 `lastMessageAt`과 보낸 사람의 `lastReadMessageId`를 같은 트랜잭션에서 갱신한다.
- 수정·삭제: 본인 메시지만, **보낸 뒤 5분 이내**(서버 시각 기준). 삭제된 메시지는 수정할 수 없다.
  - 수정: `TEXT`만. 수정 전 내용을 `ChatMessageEdit`에 1행 쌓고 `content`·`editedAt`을 갱신한다. 화면은 "수정됨"을 표시한다. 이력 조회 API는 없다.
  - 삭제: `TEXT`·`FILE`. soft delete(원문은 DB에 남김). 응답에서는 `content`를 비우고 화면은 "삭제된 메시지입니다"로 표시한다. 파일 메시지는 연결된 파일도 soft delete → 누구도 받을 수 없다(404).
- **파일 메시지 (`FILE`, 2026-11-13 사용자 결정)**
  - **요청 1개 = 메시지 1개, 업로드와 메시지 생성을 한 번에**: 이미지 `POST /chats/:roomId/images`(1~10장) / 그 밖의 파일 `POST /chats/:roomId/files`(1개, 이미지 확장자는 400), multipart `files`. 올렸는데 보내지 않은 파일이 남지 않게 두 단계(업로드 → 연결)로 나누지 않는다.
  - **이미지만 묶는다**: 이미지 여러 장 = 메시지 1개(카톡 방식, 파일 순서는 `Files.order`). 동영상과 그 밖의 파일은 파일마다 메시지 1개. 화면은 한 번 보내기에 최대 10개를 고를 수 있고, 이미지는 한 요청으로 묶고 나머지는 하나씩 보낸다.
  - 묶음은 통째로만 삭제한다(한 장만 지울 수 없음). 파일 메시지는 수정할 수 없다.
  - 종류는 게시판 첨부와 같다(`ATTACHMENT_EXTENSIONS`). 크기는 **이미지 장당 20MB**(본문 이미지 `MAX_IMAGE_SIZE`와 같음, 묶음 요청 최대 200MB), **동영상·그 밖의 파일 200MB**(`MAX_ATTACHMENT_SIZE`). 한도는 업로드를 받는 단계(multer)에서 건다 - 서버 메모리에 한꺼번에 올라오는 양을 막기 위해 (2026-11-13 사용자 결정). 분류는 확장자로: 이미지(png·jpg·gif·webp) / 동영상(mp4·mov·avi·mkv·webm·wmv) / 파일.
  - **이미지 미리보기**: 업로드 때 썸네일을 만든다(앨범과 같은 480px webp). 단, 파일 앞부분(시그니처)이 실제 이미지인 경우만. 썸네일이 없거나(가짜·깨진 파일) 불러오지 못하면 화면은 **엑스박스**(밝은 회색 바탕 + 가운데 어두운 회색 X).
  - 썸네일·원본은 공개 주소가 아니라 채팅 권한을 확인하는 API로만 준다: `GET /chats/:roomId/files/:fileId`(다운로드), `.../thumbnail`. 권한 = **활성 참여자 + 참여 시점 이후 메시지 + 메시지·파일 삭제 안 됨**, 아니면 404(나간 사람, 재참여 전 파일 포함).
  - 1:1 읽기 전용(상대 비활성)이면 업로드도 막는다(403).
  - 안 읽은 수·읽음은 일반 메시지와 같다. 목록 미리보기는 회색 작은 아이콘 + "이미지" / "동영상" / "파일명.확장자".
  - 보관 기간 없음(기한 없이 보관). 용량이 부족해지면 업로드 날짜(`Files.path`의 연/월, `createdAt`)로 정리 방법을 정한다.
  - **파일 보관함** (2026-11-13 사용자 결정): 방 메뉴의 "대화 상대 초대"와 "방 이름 변경" 사이에 구분선으로 나눠 둔다. `GET /chats/:roomId/files`(최신순 커서, 파일 id 기준) - 보이는 범위는 대화와 같다(참여 이후, 메시지·파일 삭제 안 됨). 격자로 보여 주고, 이미지는 미리보기(없으면 엑스박스), 그 밖의 파일은 아이콘(동영상 · 압축 = 지퍼 달린 폴더 · 그 밖의 파일). 파일 메시지가 오거나 지워지면 바로 갱신
  - 아이콘(대화·보관함 공통): 동영상 = 비디오, 압축(`.zip`) = 지퍼 달린 폴더, 그 밖의 파일 = 파일. 목록 미리보기는 그대로("파일명.확장자" + 파일 아이콘)
- 조회: 커서 페이지네이션(id 내림차순), 공용 `CursorArgs`·`CursorResult`를 쓴다.

## 8.5 읽음

- 참여자별 `lastReadMessageId`만 저장한다(메시지별 읽음 행은 없음). 방을 보고 있으면 화면이 "여기까지 읽음"을 보내고, 값은 앞으로만 움직인다.
- **방별 안 읽은 수**: 참여 시점 이후, 내 `lastReadMessageId`보다 큰 메시지 중 내가 보낸 것·시스템 메시지·삭제된 메시지를 뺀 개수. 헤더 배지는 전체 합계.
- **메시지별 안 읽은 사람 수**(카톡의 "1"): 활성 참여자 중 `joinedAt <= 메시지 시각`이고 `lastReadMessageId < 메시지 id`인 사람 수.
  - 서버는 방 상세에서 참여자별 `lastReadMessageId`·`joinedAt`을 내려주고, 화면이 계산한다. `room:read`를 받으면 다시 계산한다. 시스템 메시지에는 표시하지 않는다.

## 8.6 알림 · 감사 로그

- 채팅은 `Notification` 행을 만들지 않는다(알림함이 채팅으로 가득 차지 않게). 헤더에 채팅 안 읽음 배지를 따로 두고 소켓 푸시로 갱신한다.
- 감사 로그(`AuditTargetType.CHAT_ROOM`): 방 생성(`CREATE`), 초대·내보내기·나가기·OWNER 변경(`UPDATE` + `detail.action`). 메시지 보내기·수정·삭제는 기록하지 않는다(`ChatMessage`·`ChatMessageEdit`가 이력이다).

# 9. 알림

업무 이벤트에 대한 알림 기능 (채팅은 알림 행을 만들지 않는다, 8.6).

Entity (공통):

```text
Notification   사용자 알림 (수신자 userId FK, isRead / readAt)
Audit          주요 행위 로그 (수정·삭제 없이 쌓기만 함, ipAddress VarChar(45) / userAgent)
Files          첨부파일 (targetType: USER_PROFILE / POST / APPROVAL_DOCUMENT / CHAT_MESSAGE)
```

- 세 모델 모두 `targetType` + `targetId`로 대상을 가리키는 **다형 참조**라 `targetId`에는 FK를 걸지 않는다.
  - 알림과 감사 로그는 보는 관점이 달라 enum을 분리한다(2026-11-09). 알림은 "받는 사람에게 무슨 일이 생겼는지", 감사 로그는 "작업자가 무엇을 했는지"다.
    - `Notification.targetType`: `NotificationTargetType` (`USER / POST / COMMENT / APPROVAL / MEETING_RESERVATION`)
    - `Notification.actionType`: `NotificationActionType` (`SYSTEM / SIGNUP_REQUESTED / SIGNUP_APPROVED / NOTICE_CREATED / POST_COMMENTED / COMMENT_REPLIED / POST_DELETED_BY_ADMIN / COMMENT_DELETED_BY_ADMIN / SESSION_REVOKED / APPROVAL_REQUESTED / APPROVAL_APPROVED / APPROVAL_REJECTED / RESERVATION_CANCELLED`)
    - `Audit.targetType`: `AuditTargetType` (`USER / AUTH_SESSION / DEPARTMENT / POSITION / JOB_TITLE / USER_DEPARTMENT / BOARD / BOARD_AUTH / POST / COMMENT / FILE / MEETING_ROOM / MEETING_RESERVATION / APPROVAL_LINE / APPROVAL / LEAVE / CHAT_ROOM`)
    - `Audit.actionType`: `AuditActionType` (`CREATE / UPDATE / DELETE / RESTORE / ROLE_CHANGE / STATUS_CHANGE / LOGIN / LOGIN_FAILED / LOGOUT / PASSWORD_CHANGE / PASSWORD_RESET / TOKEN_REUSE`)
- `createdId`(알림 발신자, 감사 로그 작업자)는 다형 참조가 아니므로 `Users` relation(FK)을 둔다. 회원은 soft delete라 로그가 사라지지 않는다. 시스템 알림·로그인 실패처럼 회원이 없으면 NULL.

알림 (`Notification`):

- 받는 사람마다 행 1개. 전체 공지처럼 여러 명이면 `createMany`.
- `link`: 알림을 **만드는 쪽이 이동할 프론트 주소를 정해 저장**한다(예: `/boards/3/posts/120`). 누를 때 대상을 다시 조회하지 않으므로 핵심(common)이 애드온 테이블을 알 필요가 없다. 대상이 옮겨지거나 삭제되면 이동한 화면의 404 안내로 처리한다.
- 삭제는 **물리 삭제**(soft delete 없음): 본인 삭제 + 90일이 지난 알림은 하루 1회 배치로 정리. 알림은 복구할 일이 없고 쌓이기만 하는 데이터라서다.
  - 대규모 서비스에서는 보관 기간 + 월별 파티션 DROP(RDB) 또는 TTL(NoSQL)을 쓴다. Prisma 마이그레이션이 파티션을 지원하지 않아 이 프로젝트는 배치 `DELETE`로 두고, 규모가 커지면 파티션으로 바꾼다.

감사 로그 (`Audit`):

- `content`: 사람이 읽는 요약, `detail Json?`: 변경 내용(변경 전후 값).
- 일괄 처리(`ids` 배열)는 **묶어서 1행**: `targetId`는 NULL, `detail`에 `batch: true` + 대상 pk 배열(`targetIds`) + 변경 내용.
  - 대상별 조회 인덱스(`targetType, targetId`)로는 일괄 행이 잡히지 않는다. "회원 5번의 이력"에 일괄 처리도 포함하려면 `detail`의 pk 배열로 찾는다.
- `Notification`, `Audit`, `ApprovalDocumentHistory`는 행이 빠르게 쌓이므로 id를 `BigInt`로 둔다. 응답 시 BigInt는 `JSON.stringify`가 처리하지 못하므로 문자열로 변환해 내보낸다.

알림 대상 후보:

- 결재 요청 (내 차례 도착)
- 결재 완료 (최종 승인)
- 결재 반려
- 공지사항 등록
- 회의실 예약 관련 이벤트

초기 버전에서는 단순 DB 기반 알림으로 구현하고, 필요 시 Socket.IO 실시간 알림으로 확장한다.

알림(`Notification`)과 감사 로그(`Audit`)는 파일과 같이 **핵심(공통) 모듈**이다(`common`, 10.1). 애드온이 직접 호출하고, 알림·감사 로그는 애드온을 모른다(대상은 `targetType` + `targetId`로만 가리킴).


호출 규칙 (2026-11-09 사용자 결정, 구조 상세는 [docs/backend/audit-notifications.md](../backend/audit-notifications.md)):

- **감사 로그는 모든 CRUD에서 기록**, 알림은 사용자가 정한 곳에서만 보낸다.
- 감사 로그는 업무 작업과 **같은 트랜잭션**에 기록한다(`tx` 전달, 업무가 롤백되면 로그도 롤백). **알림은 커밋 후** 보내고 실패해도 업무를 막지 않는다(2026-11-09 사용자 결정 — 알림은 빠져도 불편에 그치고, 공지처럼 받는 사람이 많으면 트랜잭션이 길어지므로).
- 작업자·IP·User-Agent는 **AsyncLocalStorage 요청 컨텍스트**에서 읽는다(서비스 인자로 넘기지 않음).
- 일괄 처리 `detail`은 대상별 변경 전 값을 남긴다: `{ batch: true, targetIds, changes: { 필드: { before: { pk: 값 }, after } } }`.
- 알림을 보내는 곳 (2026-11-09 사용자 결정): ① 신규 회원가입 → 재직 중인 관리자 전원에게 승인 대기 알림(`SIGNUP_REQUESTED`, link `/admin/users/:id`) ② 가입 승인(GUEST → USER/ADMIN) → 승인된 회원에게(`SIGNUP_APPROVED`, link `/`). ③ 내 글에 댓글(대댓글 포함) → 글 작성자에게 `POST_COMMENTED` ④ 내 댓글에 답글 → 부모 댓글 작성자에게 `COMMENT_REPLIED` (글 작성자와 같으면 ④만, 본인이 단 댓글은 알림 없음, 익명 게시판은 발신자 NULL, link `/boards/:boardId/posts/:postId`). ⑤ 공지 게시판 새 글(비밀글 제외, 수정 시 재알림 없음) → 그 게시판 읽기 권한이 있는 재직 중 회원에게 `NOTICE_CREATED`(고정 여부와 무관 — 일반 게시판 고정·나중에 고정은 알림 없음, 2026-11-09 사용자 결정으로 유지) ⑥ 관리 권한으로 남의 글·댓글 삭제 → 작성자에게 `POST_DELETED_BY_ADMIN`·`COMMENT_DELETED_BY_ADMIN`(삭제한 관리자는 드러내지 않음) ⑦ refresh token 재사용 감지 → 세션 주인에게 `SESSION_REVOKED`(link `/mypage`). 그 외는 기능 구현 시 사용자가 정한다
- 감사 로그를 남기지 않는 것: 조회·조회수·좋아요, 토큰 재발급(재사용 감지만 기록), 내 알림 읽음·삭제. 적용 현황은 [audit-notifications.md](../backend/audit-notifications.md) 6장
