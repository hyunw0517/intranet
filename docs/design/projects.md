# 과제 관리 (애드온 `projects`)

> [AGENTS.md](../../AGENTS.md) 10.1 애드온 구조를 따른다. 결정 날짜와 결정한 사람을 함께 적는다.
> 시작: 2026-11-16.

## 1. 목적과 범위

- **목적**: 결재·예약·채팅만으로는 인트라넷 상품성이 부족해서, 프로젝트 → 견적 → 매출 → 예산으로 이어지는 회사 업무 흐름을 하나의 애드온으로 제공한다. (2026-11-16 사용자 결정, 11/10에 "회계 성격이라 제외"했던 견적·매출·예산을 다시 포함)
- **하위 기능**

| 하위 기능 | 내용 | 상태 |
|---|---|---|
| 프로젝트 | 이름·상태·기간·책임자·참여자·거래처, 참여자만 열람 | 백엔드·프론트 완료 (11/17) |
| 과제 | 담당자·상태·마감일, 칸반 보드, 진척도 = 완료 과제 비율 자동 계산 | 백엔드·프론트 완료 (11/17) |
| 거래처 | 프로젝트·견적·매출이 같이 참조하는 고객사 | 백엔드·프론트 완료 (11/17) |
| 견적서 | 프로젝트별 견적, 확정 시 결재 연동(결재가 켜져 있을 때) | 백엔드·프론트 완료 (11/17) |
| 매출 | 프로젝트별 매출 | 백엔드·프론트 완료 (11/17) |
| 예산 | 프로젝트별 예산·지출·그래프, 관리자 전사 통계 | 백엔드·프론트 완료 (11/18) |

- **재사용**: 첨부 = `FilesService`, 변경 이력 = 감사 로그, 담당 지정·마감 임박 = 알림(notifier).
- **제외**: Gantt 차트(나중 선택), 별도 역할 관리 페이지.

## 2. 모듈 구조 (2026-11-16 사용자 결정)

- **애드온 하나**: `ADDONS=projects`로 하위 기능이 모두 함께 켜진다. 하위 기능을 옵션(`quotes` 등)으로 나누지 않는다. 코드는 `backend/src/projects/` 안에서 하위 기능별 폴더로 나눈다.
- **결재 연동은 결재가 켜져 있을 때만**: `projects`는 `approvals`를 requires로 선언하지 않는다(결재 없이도 과제 관리를 쓸 수 있다).
  - 연결 코드는 `ProjectsApprovalModule`([backend/src/projects/projects-approval.module.ts](../../backend/src/projects/projects-approval.module.ts))에만 둔다. AppModule에서 `addonModule([ 'projects', 'approvals' ], ...)`로 **둘 다 켜졌을 때만** 등록한다.
  - `ProjectsModule`이 `ApprovalsModule`을 직접 import하지 않는 이유: import하면 결재를 끈 배포에서도 결재 컨트롤러가 등록되어 결재 API가 생긴다.
  - 둘 다 켜짐: 견적서를 결재에 올리고, 휴가와 같은 방식(문서 유형별 처리기 등록 + 같은 `tx`, features.md 7.4)으로 최종 승인 시 견적을 확정한다.
  - 결재 꺼짐: 권한자가 과제 관리 화면에서 직접 확정한다.

```text
backend/src/projects/
├── projects.module.ts            # 애드온 본체
├── projects-approval.module.ts   # 과제 관리 ↔ 결재 연결 (현재 뼈대만)
├── project-access.service.ts     # 프로젝트 권한 판단 (하위 기능이 모두 먼저 호출)
├── projects.service.ts / project-members.service.ts / projects.controller.ts
├── project-notifier.ts           # 알림 3종
├── util/project-rules.util.ts    # 진척도·담당자 부재·칸반 재정렬 (순수 함수, 단위 테스트)
├── tasks/                        # 과제 (칸반, 마감 임박 배치)
├── clients/                      # 거래처 + 담당자
├── quotes/                       # 견적서 (예정)
├── sales/                        # 매출 (청구·수금·세금계산서 첨부)
└── budgets/                      # 예산 (비용 항목·항목별 예산·지출·통계)
```

## 3. 권한 (2026-11-16 사용자 결정)

- **열람**: 프로젝트는 참여자만 본다(11/10 결정 유지).
- **금액(견적·매출·예산·외주)**: 프로젝트를 볼 수 있는 사람(참여자·과제 관리 관리자) **모두가 본다**. (2026-11-17 사용자 결정으로 변경)
  - ~~11/16: 책임자 + 관리자만, 참여자별 "금액 열람 허용" 옵션~~ → 11/17 외주 금액을 정하다가 금액 열람 규칙 자체를 없앴다. `ProjectMember.canViewAmount` 컬럼은 마이그레이션 `20261117120000_project_partners`에서 삭제.
  - 필요해지면 다시 추가한다(그때는 참여자 옵션 / 개별 권한 테이블 / 역할 기반 중 고른다). 별도의 역할 관리 페이지는 만들지 않는다.
- **금액 타입 (2026-11-17 사용자 결정)**: 원화 정수 `Decimal(15,0)`(최대 999조), 부가세는 별도 칸. 요청은 숫자로 받고 응답은 문자열(Prisma Decimal 직렬화), 화면 합계는 `BigInt`로 더한다.
- **부가세 (2026-11-17 사용자 결정)**: 견적·매출·협력사 모두 **과세/면세 선택 + 부가세율(%) 직접 입력, 기본 과세 10%**. 부가세율은 `Decimal(5,2)`(0~100, 소수 둘째 자리까지, DB CHECK `*_vat_rate_check`)로 행마다 저장한다(나중에 기본값이 바뀌어도 낸 문서는 그대로). 부가세 = 공급가액 합계 × 부가세율 ÷ 100 **원 미만 버림**(서버 `calcVat` 하나로 계산), 면세는 부가세율과 관계없이 0. 마이그레이션 `20261117120330_project_vat_rate`(기존 행은 10%로 채움).
- 과제 관리 관리자 기능은 `AdminPermission.PROJECTS`("과제 관리")로 추가한다(features.md 5.1 "관리자 기능 권한").

## 4. 거래처 (2026-11-16 사용자 결정)

- 별도 테이블로 둔다. 프로젝트·견적·매출이 참조하고, 거래처별 매출 집계에 쓴다.
- **모델 이름**: 과제 관리의 모델은 모두 `Project` 접두어를 붙인다(2026-11-16 사용자 결정). 예: `ProjectClient`, `ProjectClientContact`, `ProjectTask`
- **항목**: 거래처 `ProjectClient` = 회사명(필수)·사업자등록번호·대표자·주소·대표 전화·메모. 담당자는 별도 `ProjectClientContact`(여러 명) = 이름(필수)·부서·직책·연락처·이메일·메모.
- **등록·수정·삭제**: USER 이상 누구나. 등록자가 퇴사해도 인수인계자가 고칠 수 있도록 수정 권한을 등록자로 묶지 않는다. 누가 무엇을 바꿨는지는 감사 로그(변경 전후 값)로 추적한다.
- **삭제**: soft delete. 삭제된 거래처는 새 프로젝트에서 고를 수 없지만, 기존 프로젝트·견적에는 **실제 거래처 이름이 그대로 보인다**("(삭제된 거래처)"로 가리지 않음, 문서 이력 보존). 담당자(`ProjectClientContact`)도 soft delete.
- **[삭제된 거래처] 탭**: 삭제된 거래처 목록과 삭제한 사람·삭제 시각(`deletedId`·`deletedAt`)을 보여 준다.
- **사업자등록번호 중복**: 입력했을 때만, 삭제되지 않은 거래처끼리 중복 금지. DB 부분 unique 인덱스(`where: { deleted: false }`, `Users.email`과 같은 방식) + 서비스 검사(친절한 400 메시지).
- **견적서의 거래처 정보**: 견적 작성 당시 회사명·사업자번호·담당자를 견적서 행에 스냅샷으로 복사한다(결재라인 스냅샷과 같은 이유 - 발행한 문서가 나중에 바뀌지 않게). 견적서 스키마 때 적용.

### 협력사 (하청기업) (2026-11-17 사용자 결정)

- 한 프로젝트에 하청기업이 여럿일 수 있다. 발주처(`Project.clientId`, 돈을 받는 쪽 - 견적·매출)는 **하나로 유지**하고, 협력사(돈을 주는 쪽 - 예산 집행 외주비·매입 세금계산서)는 **별도 연결 테이블 `ProjectPartner`**(프로젝트 ↔ 거래처, 여러 개)로 둔다. (B안 "역할 있는 연결 테이블로 발주처까지 통합"은 기존 스키마·화면 수정이 커서 제외)
- 회사 정보는 거래처(`ProjectClient`) **한 목록**에 둔다. 같은 회사가 프로젝트에 따라 발주처도, 협력사도 될 수 있으므로 역할은 회사가 아니라 프로젝트와의 관계에 둔다(목록을 나누면 같은 회사를 두 번 등록하게 되고 사업자번호 중복에 걸린다).
- 화면: 프로젝트 상세에 **"협력사" 탭** 추가(칸반 / 개요 / 참여자 / 협력사). 거래처 목록에는 **"발주 프로젝트 N개 / 협력 프로젝트 N개"** 열을 실제 연결에서 계산해 보여 준다((a)안, 구분 필드를 따로 두지 않음).
- **항목**: 업무 범위, 외주 계약 금액(공급가액, 원) + 과세/면세 + 부가세율(기본 10%) → 부가세·합계는 서버가 계산해 저장(금액이 없으면 둘 다 NULL, 셋 중 하나만 고쳐도 다시 계산), 계약 기간(선택, 시작 ≤ 종료), 협력사 담당자(거래처 담당자를 고르지 않고 **직접 기재**, **여러 명** - 2026-11-17 사용자 결정 B안: 별도 테이블 `ProjectPartnerContact` = 이름(필수)·역할(PM·실무·정산 등)·연락처·이메일, 최대 20명, 수정 시 보내면 목록 전체 교체(견적 품목과 같은 방식), 마이그레이션 `20261117123946_project_partner_contacts`에서 기존 담당자 한 명을 옮기고 옛 칸 삭제). 회사(`clientId`)는 바꾸지 않는다(빼고 새로 추가).
- **권한**: 참여자 누구나 등록·수정·빼기, 금액도 참여자 전원.
- **외주 계약 금액과 견적·매출·예산 (2026-11-17 사용자 결정 B안)**: 외주 금액은 우리가 **주는** 돈이라 견적·매출(받는 돈) 계산에 넣지 않는다. 금액은 계약 정보로 **협력사에 그대로 두고**, 예산에서 가져다 쓴다. 연결 방식(외주비에 자동 반영 / 참고로만 표시, 손익에 공급가액을 쓸지)은 예산 설계 때 정한다. (A안 "협력사에서 금액을 빼고 예산에서 입력"은 예산이 생기기 전까지 외주 금액을 적을 곳이 없어져 제외)
- **빼기**: soft delete(예산 집행·매입 세금계산서가 연결될 예정이라 기록 유지). 같은 회사는 활성 한 행(부분 unique, 중복 409), 빼고 다시 넣으면 새 행.
- **DB CHECK**: `project_partner_model_amount_check`(금액 ≥ 0), `project_partner_model_period_check`(시작 ≤ 종료).
- API: `GET`·`POST /projects/:projectId/partners`, `PATCH`·`DELETE /projects/:projectId/partners/:partnerId`. 거래처 목록·상세의 `_count.partners` = 협력 프로젝트 수(삭제되지 않은 프로젝트만).
- 예산 지출과의 연결은 5-3장(지출에 협력사를 고르는 방식).
- 마이그레이션 메모: 개발 DB에 값이 있는 `can_view_amount`를 지우는 마이그레이션이라 비대화형 환경에서 `migrate dev --create-only`가 확인 질문에서 멈췄다 → `prisma migrate diff --from-config-datasource --to-schema --script`로 SQL을 만들고 `migrate deploy`로 적용(`--from-migrations`는 shadow DB 설정이 필요해 쓰지 않음).

## 5. 프로젝트·과제 (2026-11-16 사용자 결정)

| 항목 | 결정 |
|---|---|
| 프로젝트 상태 | 준비 · 진행 · 보류 · 완료 · 종료 · 취소 (`PLANNED / IN_PROGRESS / ON_HOLD / COMPLETED / CLOSED / CANCELLED`). **종료**는 완료와 별개로, 유지보수 기간까지 끝나 프로젝트가 완전히 닫혔다는 뜻 |
| 과제 상태 | 고정 3단계: 할 일 → 진행 → 완료 (`TODO / IN_PROGRESS / DONE`), 칸반 컬럼도 고정 |
| 참여자 역할 | 책임자(`MANAGER`) · 참여자(`MEMBER`), **책임자 여러 명 허용**. 참여자 테이블의 역할 컬럼으로 구분 |
| 칸반 순서 | 컬럼(상태) 안의 정수 `sortOrder`. 카드를 옮기면 그 컬럼을 트랜잭션 안에서 다시 번호 매김 |
| 하위 과제 | 만들지 않는다 |
| 진척도 | 완료 과제 수 / soft delete되지 않은 전체 과제 수 (조회 시 계산, 저장하지 않음, 과제마다 가중치 없이 1개씩). 담당자 부재·담당자 없음(`NULL`)과 관계없이 모두 센다. 부재 담당의 미완료 과제는 인수인계(담당자 교체)하거나, 필요 없으면 삭제한다 (2026-11-16 사용자 결정 - 처음에는 부재 담당 과제를 빼기로 했다가, 인수인계가 필요한 일이 진척도에서 사라지지 않도록 포함으로 변경) |
| 과제 삭제 | soft delete (진척도 계산에서 제외) |
| 담당자 부재 표시 | (제안, 확인 전) 칸반 카드와 프로젝트 상세에 "담당자 부재"를 표시해 인수인계할 과제를 찾게 한다 |
| 담당자 부재 | 담당자가 프로젝트 참여자에서 빠졌거나, 회원이 퇴사·삭제된 경우 |
| 참여자 제외 | 빠진 참여자가 담당인 과제는 **담당자를 그대로 둔다**(이력 보존). 부재 담당 과제의 담당자 교체는 **책임자와 과제 관리 관리자만** 한다(일반 과제의 담당자 지정은 참여자도 가능) |
| 완료 시각 | 저장하지 않는다(`completedAt` 없음). 기록이 필요해지면 별도 `ProjectHistory` 모델을 만든다(현재 계획 없음) |

### 구현 방향 (Claude 제안, 2026-11-17 사용자 승인 · 구현 완료)

- **상태 저장**: 버전에는 `DRAFT / CONFIRMED / CANCELLED`와 연결된 결재 문서 id만 저장하고, "결재 중·반려"는 연결된 결재 문서 상태로 계산한다. 결재 쪽에는 반려·회수 때 업무를 부르는 지점이 없어서(처리기는 상신·최종 승인·다시 기안만), 따로 저장하면 어긋날 수 있다.
- **결재 본문 스냅샷**: 상신할 때 서버가 견적(발주처·품목표·합계)을 HTML로 만들어 결재 문서 본문에 넣는다 → 결재 화면은 과제 관리를 몰라도 견적을 보여 주고(R-ARCH-01, 결재 → 과제 관리 의존 없음), 승인한 내용이 그대로 남는다.
- **결재 연결**: `ApprovalDocumentType.QUOTE` 추가, `ProjectsApprovalModule`(둘 다 켜졌을 때만)에 견적 처리기 등록 - `directCreate: false`(결재 작성 화면에서 직접 못 만듦), `onFinalApproved` = 그 버전 확정(같은 tx). `onCopy` 없음 → 반려된 견적은 결재함의 "다시 기안"이 아니라 견적 화면에서 다시 상신.
- **결재가 꺼진 배포**: 처리기가 없으므로 [결재 요청] 대신 [확정] 버튼(직접 확정).

| 금액 입력 | **공급가액 입력 + 부가세 자동**(과세 = 부가세율 버림 / 면세 0), 청구 건마다 과세·면세와 부가세율 입력(기본 과세 10%, 견적을 고르면 그 견적 값으로 채움). 청구한 건은 부가세율도 잠금 |
| 세금계산서 | 외부에서 발행한 파일을 청구 건에 **첨부**(여러 개) + 국세청 **승인번호**(선택). 발행일 = 청구일. 수정세금계산서는 파일을 **추가 첨부** |
| 권한 | 참여자 누구나 (견적·협력사와 같음, 변경은 감사 로그) |
| 삭제·취소 | 청구 예정은 **삭제**(soft), 청구한 건은 **취소**("취소됨"으로 남김, 매출·청구 합계에서 빠짐) - **수금 기록이 있으면 취소 불가**(수금을 먼저 지운다) |
| 견적 확정 취소 | **매출(취소되지 않은 청구)이 연결된 견적은 확정 취소 불가** (5-1의 남은 규칙) |

- 구현에서 정한 것(Claude 제안): 금액은 청구 예정일 때만 고치고 청구한 뒤에는 잠근다(바꾸려면 취소 후 다시), 승인번호·첨부는 청구 뒤에도 고칠 수 있다(수정본 추가). 견적을 고르면 과세 구분 기본값을 그 견적의 값으로 채운다(화면). 합계 검사는 견적 행을 잠근 뒤 센다(동시 등록 방지). 등록할 때 청구일을 함께 보내면 바로 "청구"로 만든다(이미 세금계산서를 낸 경우). 수금일 ≥ 청구일 같은 날짜 검사는 두지 않았다(선수금 가능성).
