## 2026-10-15 ~ 10-16 · 회원 상태, 탈퇴, 비밀번호, 토큰 보안

관련 커밋: `4fbebe4` (Users 회원, Auth 인증 기능 구현)

### 1. 탈퇴(퇴사)와 삭제의 분리 — `status` vs `deleted`
- **문제**: soft delete 컬럼(`deleted`) 하나로 탈퇴까지 처리할지 고민.
- **고민**: 퇴사를 `deleted: true`로 처리하면 ① 조회가 모두 `deleted: false`로 걸러져 게시글·결재 이력의 작성자 join이 끊김 ② `@@unique([empNo], where: { deleted: false })` 때문에 퇴사자 사번이 재사용 가능해짐 ③ "퇴사자 목록"과 "잘못 등록된 데이터"를 구분할 수 없음.
- **결정**: `isActive`(Boolean)를 없애고 `status` enum(`ACTIVE`/`INACTIVE`/`RESIGNED`)으로 대체. `deleted`는 관리자 삭제(잘못 등록 등) 전용. 두 컬럼을 같이 두면 `isActive: true` + `RESIGNED` 같은 모순 상태가 생기므로 하나로 통합.
- **설계 포인트**: 상태와 삭제는 의미가 다르다. 사번은 재사용하지 않는 식별자이므로 퇴사자도 unique를 계속 점유해야 한다.

### 2. 로그인·요청 시 상태 체크
- **결정**: `AuthService.checkUserStatus()`를 만들어 Basic 가드(로그인)와 Bearer 가드(모든 요청)에서 호출. 상태 때문에 막힐 때는 401이 아닌 **403**(인증은 됐지만 권한 없음).
- **설계 포인트**: 로그인 시점에만 체크하면 퇴사 처리 전에 발급된 토큰이 계속 유효하다 → 요청마다 확인.

### 3. 회원 탈퇴 API — `DELETE /users/me`
- **고민 1**: soft delete는 플래그만 바꾸니 `PATCH`인가? → **`DELETE`**. HTTP 메서드는 내부 구현이 아니라 클라이언트 관점의 의도를 표현한다. `PATCH { deleted: true }`는 일반 수정 권한으로 삭제가 가능해지는 문제도 있음.
- **고민 2**: 처음엔 `DELETE /users/:id` + 본인/관리자 권한 체크 → 본인 탈퇴만 필요하므로 `/users/me`로 단순화. 관리자 삭제는 추후 `@Roles(Role.ADMIN)` 별도 라우트.
- **고민 3**: `@HttpCode(204)` (RFC 9110 §9.3.5: 처리 완료 + 추가 정보 없음 → 204 권장, `SHOULD`) → 다른 API와 응답 형식 통일을 위해 제거.

### 4. 비밀번호 변경 — `PATCH /auth/change/pw`
- **고민**: auth vs users 컨트롤러? → **auth**. 해시 로직(bcrypt, HASH_ROUNDS)이 `AuthService`에 있고 의존 방향이 `Auth → Users` 단방향이라 users에 두면 순환 의존 또는 중복. 인증 정보(credential) 관리는 auth의 책임.
- **결정**: `hashPassword()`로 해시 로직 추출(회원가입과 공용). `UsersService.updatePassword`는 해시된 값 저장만 담당 → 평문 비밀번호는 AuthService에서만 다룬다. 새 비밀번호 == 현재 비밀번호면 400.

### 5. 비밀번호 해시 노출 방지 — Prisma 전역 omit
- **문제**: `GET /users/me`가 가드에서 조회한 전체 행(`req.user`)을 그대로 반환 → 비밀번호 해시 노출.
- **고민**: 응답에서만 빼기 vs 구조적으로 막기. bcrypt salt는 비밀이 아니므로 해시가 유출되면 오프라인 대입 공격이 가능(약한 비밀번호는 금방 뚫림). 토큰 탈취가 영구적인 계정 탈취로 확대될 수 있음.
- **결정**: `PrismaService`에 `omit: { users: { password: true } }`. 해시가 필요한 곳은 `getUserWithPasswordByEmpNo`(로그인), `getPasswordHashById`(본인 확인)로 한정.
- **함정 (트러블슈팅)**: `PrismaService`가 `PrismaClient`를 **상속**하는 구조라 생성자 옵션의 omit이 **타입에 반영되지 않음** → tsc는 통과하지만 런타임에 `password`가 `undefined`라 로그인이 깨짐. 실제 DB에 스크립트를 돌려 동작을 검증하고, 해시 전용 조회 함수 규칙으로 해결.
- **추가 고민**: 실제 회사라면 password만 빼는 블랙리스트보다, 용도별로 필드를 고르는 **화이트리스트(`select`)**가 기준이어야 함(hp, birthday 등 임직원 개인정보). 관리자 모드에서 적용 예정.

### 6. refresh 토큰 무한 갱신 (보안 버그) ⭐
- **문제**: 토큰 재발급 라우트에 `@IsPublic()`이 붙어 있어 `BearerTokenGuard`가 public 분기로 빠지고, `RefreshTokenGuard`도 `isRoutePublic`이면 그냥 통과 → 실제로는 JWT 서명만 확인. 탈퇴·퇴사자도 refresh를 계속 갱신하며 로그인 유지 가능.
- **시행착오**: 처음엔 `@IsPublic()`을 제거하자고 판단 → NestJS 가드는 **전역 → 컨트롤러 → 라우트** 순서로 실행되므로, 전역 `AccessTokenGuard`가 refresh 토큰을 먼저 거부해 재발급 자체가 막힘. `@IsPublic()`은 "누구나 접근"이 아니라 **전역 Access 가드를 우회하기 위한 장치**였음.
- **결정**: `@IsPublic()`은 유지. 엄격한 검증 로직을 `protected authenticate(req)`로 분리하고, `RefreshTokenGuard`는 public 여부와 상관없이 항상 `authenticate` 실행.
- **결과**: 퇴사자 refresh → 403, 삭제 회원 → 401, 토큰 없이 호출 시 500 → 401.
- **설계 포인트**: 가드 실행 순서, 데코레이터의 실제 의도 파악, `protected`로 상속용 내부 메서드 범위 제한.

### 7. `rotateToken` 500 에러 + 중복 코드
- **문제**: `rotateToken`이 `jwtService.verify`를 직접 호출하고 예외를 잡지 않아 만료 토큰이면 500.
- **결정**: 이미 try/catch로 401을 던지는 `verifyToken()`을 재사용 → 중복 제거 + 401 처리. (강의 코드에서 단계별로 작성되며 남은 중복으로 판단)

### 8. 비밀번호 변경 후 탈취 토큰 무효화 — `tokenVersion` ⭐
- **문제**: JWT payload에 비밀번호 정보가 없어 비밀번호를 바꿔도 기존 토큰 유효. refresh 시 새 refresh도 발급하므로 탈취된 토큰이 영원히 살아남을 수 있음.
- **고민**: `passwordChangedAt` vs 토큰 `iat` 비교 → `iat`이 초 단위라 같은 초 경계 문제. **버전 숫자**가 더 단순.
- **결정**: `Users.tokenVersion Int @default(0)`, payload에 `ver`. 가드에서 `ver !== user.tokenVersion`이면 401(이미 조회한 사용자 값과 비교 → 추가 쿼리 없음). 비밀번호 변경 시 `increment: 1` + 본인에게 새 토큰 응답.
- **설계 포인트**: JWT stateless의 한계와 보완. 관리자 강제 로그아웃도 같은 방식으로 확장 가능.
- **트레이드오프**: 요청마다 DB 조회 → 완전한 stateless는 아님. 즉시 차단(보안)을 우선했고, 트래픽 증가 시 캐시(Redis)나 짧은 access 만료로 조정 가능.

### 9. Basic 인증 파싱 버그
- **문제**: `decoded.split(':')` + `length !== 2` → 비밀번호에 `:`이 있으면 로그인 실패(가입은 성공).
- **결정**: RFC 7617 기준 첫 번째 `:`(`indexOf`)으로 분리. 사용자 ID에는 `:` 불가, 비밀번호에는 허용.

### 10. 권한 enum 정리

- `GET /users`는 `@Roles(Role.ADMIN)`으로 관리자 전용.

## 2026-10-17 · 전체 스키마 리뷰 (게시판·결재·회의실·연차)

관련 커밋: `9f6d4c3`

전체 기능 스키마를 먼저 짠 뒤 리뷰를 받아, 구현 단계에서 막힐 부분 4가지와 휴가 단위를 수정했다.

### 1. 캘린더 게시판 일정 필드 — Post 컬럼 vs CalendarEvent 분리
- **문제**: `BoardType.CALENDAR`는 있는데 `Post`에 일정 시간 필드가 없어 달력에 표시할 수 없었음.
- **고민**: ① `Post`에 nullable 컬럼 추가 ② `CalendarEvent` 모델을 따로 두고 1:1 연결(결재/연차처럼 공통·업무 데이터 분리). 분리는 일정 전용 필드(반복 규칙, 참석자, 장소)가 많아질 때 유리하고, 일반 글에 항상 NULL인 컬럼이 쌓이는 것을 피할 수 있음.
- **결정**: 캘린더는 게시판 모듈에 기본 포함하고 일정 필드가 2~3개뿐이라 `Post`에 `eventStartAt` / `eventEndAt` / `isAllDay` 추가. 분리하면 조인과 생성 트랜잭션만 늘어남. 반복 일정·참석자가 필요해지면 그때 분리.
- **`isAllDay`가 필요한 이유**: 없으면 종일 일정을 `00:00~23:59`로 저장해야 하고, 프론트에서 진짜 그 시간대 일정과 구분 불가(달력 UI는 종일 일정을 상단 띠로 따로 그림). UTC 저장 시 KST 자정이 전날 15시가 되는 타임존 문제도 "종일이면 날짜만 사용" 규칙으로 피함.
- **부수 변경**: `Post.content`를 optional로 변경(캘린더 글은 본문이 없을 수 있음) → 일반 글 본문 필수, CALENDAR 글 일정 필수는 다른 테이블(`Board.type`)을 봐야 해서 DB 제약 불가, 서비스/DTO에서 검증.
- **설계 포인트**: 월간 조회 조건은 `eventStartAt < 다음달1일 AND eventEndAt >= 이번달1일`(월을 걸치는 일정 포함).

### 2. 게시판 권한에 읽기/쓰기/댓글 구분
- **문제**: `BoardAuth`가 접근 가능 여부만 표현 → 공지 게시판의 "전원 읽기, 관리자만 쓰기"를 표현할 수 없음.
- **결정**: `authRead`(기본 true) / `authWrite`(기본 false) / `authComment`(기본 true) 추가. 기본값은 쓰기를 막는 안전한 쪽.
- **남은 결정**: 권한 행이 없는 게시판의 의미(전체 공개 vs 접근 불가), 여러 행일 때 OR 판정 여부, ADMIN 우회 여부 → 게시판 서비스 구현 전에 확정.

### 3. 결재 문서 유형 컬럼 — `documentType`
- **문제**: 문서가 어떤 업무용인지 `leaveRequest` 관계 존재 여부로만 알 수 있음. 업무 종류가 늘면 관계를 하나씩 확인해야 함.
- **결정**: `ApprovalDocumentType`(`GENERAL` / `LEAVE`) enum 추가. 최종 승인 시 "문서 유형별 핸들러" 또는 이벤트로 업무 모듈을 호출할 때 분기 기준이 됨(CLAUDE.md 7.4).
- **규칙**: `LEAVE` 문서는 `LeaveRequest`가 반드시 있어야 함 → DB 제약 불가, 두 행을 같은 트랜잭션에서 생성해 보장.

### 4. 회의실 중복 예약 — "트랜잭션 + 생성 전 조회"로는 부족 ⭐ (구현 예정)
- **처음 판단**: 트랜잭션 안에서 겹치는 예약을 1회 조회하고 없으면 INSERT하면 된다.
- **문제**: PostgreSQL 기본 격리 수준(READ COMMITTED)에서는 동시에 들어온 두 트랜잭션이 서로의 미커밋 INSERT를 보지 못해 둘 다 "겹침 없음"으로 판단 → 중복 예약. 조회 시 `FOR UPDATE`를 걸어도 잠글 대상(아직 없는 행)이 없음(팬텀).
- **고민**: ① 부모인 회의실 행을 `FOR UPDATE`로 잠근 뒤 조회 ② PostgreSQL `EXCLUDE USING gist` 제약(DB가 보장, Prisma 스키마로 표현 불가 → 마이그레이션 SQL 직접 작성) ③ SERIALIZABLE + 재시도.
- **결정**: ① 회의실 행 잠금. 기존 계획(조회 후 생성)을 거의 그대로 유지하고, 같은 회의실 요청만 직렬화되어 다른 회의실은 서로 막지 않음. 설명하기 쉬움. 스키마 변경 없음.
- **적용 범위**: 예약 생성과 시간 수정 모두. 겹침 조건은 `start < 상대.end AND end > 상대.start`(경계가 맞닿는 건 허용).
- **검증 계획**: `Promise.all`로 동시 요청을 보내 잠금 전/후 결과 비교.
- **설계 포인트**: 트랜잭션만으로 동시성이 보장되지 않는 이유(격리 수준, 팬텀), 존재하는 부모 행을 잠그는 방식.

### 5. 휴가 사용 단위 — 반차·반반차(0.25일)
- **문제**: 반반차까지 지원하려면 일수 표현은 `Decimal(5,2)`로 충분하지만, `startDate`/`endDate`가 `@db.Date`라 하루 중 언제 쉬는지 저장할 곳이 없음.
- **고민**: ① 사용 단위 enum + 시간 컬럼 ② `startAt`/`endAt` timestamp 하나로 저장 → 모든 단위를 한 구조로 표현하지만 사용 일수를 시간으로 계산해야 해서 점심시간·근무시간 규칙이 필요.
- **결정**: ① `LeaveUnit`(`FULL` / `HALF` / `QUARTER`) + `startTime` / `endTime`(`@db.Time(0)`, FULL이면 NULL).
- **규칙(서비스 검증)**: HALF/QUARTER는 하루(`startDate == endDate`)에만, 시간 필수. "2일 + 반차"는 신청을 나눔. `days`는 서버가 계산(FULL = 기간 내 근무일 수). 시간은 고정 슬롯 중 선택.
- **설계 포인트**: 일수 합산에 Float 대신 Decimal(부동소수점 오차 방지). Prisma `Decimal`은 Decimal.js 객체로 반환되어 JSON에서 문자열로 직렬화됨 → BigInt와 함께 응답 변환 규칙 필요(미결정).
