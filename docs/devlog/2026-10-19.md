## 2026-10-20 · 조직(부서·직급·직책) CRUD 리뷰

관련 커밋: `9fedc24` (소속 부서·직급·직책 CRUD 작업)

departments를 기준으로 positions / job-titles를 작성한 뒤 리뷰를 받아 권한·검증·정렬 문제를 수정했다.

### 1. 서비스 메서드에 붙인 `@Roles`가 동작하지 않음 (권한 우회) ⭐
- **문제**: 세 서비스의 모든 메서드에 `@Roles(UserRole.ADMIN)`을 붙였지만, 로그인한 일반 USER도 부서·직급·직책을 생성·수정·삭제할 수 있는 상태였음.
- **원인**: `@Roles`는 `SetMetadata`로 메타데이터만 기록하는 데코레이터이고, `RolesGuard`는 `context.getHandler()` / `context.getClass()`, 즉 **요청을 처리하는 컨트롤러의 핸들러와 클래스**에서만 메타데이터를 읽는다. 서비스 메서드는 ExecutionContext에 없으므로 `requiredRole`이 `undefined` → 그대로 통과.
- **결정**: 컨트롤러 메서드로 이동. 나중에 일반 사용자에게 조회를 열 수 있도록 클래스 단위가 아닌 **메서드 단위**로 적용.
- **설계 포인트**: 가드는 "어느 컨트롤러의 어느 핸들러로 요청이 왔는가"만 안다. `SetMetadata` 계열(`@Roles`, `@IsPublic`)은 컨트롤러에 붙여야 효과가 있다. 컴파일·실행 에러 없이 조용히 권한이 열리는 종류의 버그라 테스트로 확인해야 한다.

### 2. 수정 시 이름 중복 검사 + 목록 정렬
- **문제**: 생성 때만 이름 중복을 막고, 수정 때는 다른 직급과 같은 이름으로 바꿀 수 있었음. 목록 조회에 `orderBy`가 없어 `sortOrder`를 관리하면서도 정렬되지 않은 순서로 응답.
- **결정**: 수정 시 `id: { not: 자기 id }`로 자기 자신을 제외하고 중복 검사. 부서는 같은 상위 부서 아래에서만 이름이 겹치면 안 되므로 **수정 후의 상위 부서** 기준으로 비교. 목록에 `orderBy: { sortOrder: 'asc' }`.
- **함정**: Prisma는 `where`에 `undefined`가 들어오면 그 조건을 **제외**한다. 최상위 부서 생성 시 `parentDepartmentId`를 생략하면 중복 검사·`sortOrder` 카운트가 전체 부서 대상이 됨 → `body.parentDepartmentId ?? null`로 통일.

### 3. PartialType과 `IsOptional` — Update DTO에서 `name: null`이 통과
- **문제**: `UpdateXxxDto extends PartialType(CreateXxxDto)`에서 `{ "name": null }`이 검증을 통과 → NOT NULL 컬럼에 null이 들어가며 Prisma 에러(500).
- **원인**: `@nestjs/mapped-types`의 `PartialType`은 부모의 검증 규칙을 복사한 뒤 모든 속성에 `IsOptional()`을 **추가**한다. `IsOptional`은 값이 `null`/`undefined`이면 그 속성의 나머지 규칙(`IsNotEmpty` 포함)을 건너뛴다.
- **시행착오**: 처음엔 Update DTO에서 `name`을 다시 선언하면 된다고 판단 → class-validator는 상속 규칙과 자식 규칙이 겹칠 때 **같은 종류(type)끼리만** 자식 것으로 대체한다. `IsOptional`은 조건부(CONDITIONAL) 종류라 일반 검증 규칙만 다시 선언하면 상속된 `IsOptional`이 남는다. (`MetadataStorage.getTargetValidationMetadatas`에서 확인)
- **고민**: ① `PartialType(..., { skipNullProperties: false })` — undefined만 허용, null은 검증 ② `OmitType`으로 name을 빼고 필수로 재선언.
- **결정**: ② 수정은 폼 전체를 제출하는 방식으로 정하고 `name`을 필수화. `PartialType(OmitType(CreateDto, ['name']))` + `name` 재선언 → 서비스의 `name` undefined 분기도 제거.
- **설계 포인트**: PATCH의 "보낸 필드만 수정" 의미와 검증의 관계. `EmptyToNull`(class-transformer)은 변환일 뿐 검증이 아니며, ValidationPipe는 변환 → 검증 순서로 실행된다.

### 4. 부서 이동 시 `sortOrder` 재정렬 트랜잭션
- **문제**: `parentDepartmentId`만 바꾸면 이전 소속에는 빈 번호, 새 소속에는 중복 번호가 생김(A팀 `0,2` / B팀 `0,1,1`). 이후 생성·삭제 재정렬도 계속 어긋남.
- **결정**: 상위 부서가 바뀔 때만 `$transaction([update, updateMany])` — 대상 부서는 새 소속의 맨 뒤(`count`)로, 이전 소속은 `sortOrder > 기존 값`을 `decrement: 1`. 이동이 먼저 적용되든 나중이든 자기 자신은 재정렬 대상에서 빠진다.
- **한계**: `count`와 기존 `sortOrder`를 트랜잭션 밖에서 읽어 동시 요청에는 취약. 관리자 기능이라 감수하고, 필요하면 콜백 형태(interactive) 트랜잭션으로 이동.
- **메모**: 배열 형태 `$transaction`은 쿼리 순서대로 결과 배열을 반환 → `const [updated] = ...`.

### 5. 자기 참조 트리의 순환 참조 방지 ⭐
- **문제**: 상위 부서 변경 시 ① 없는/삭제된 부서 id → FK 위반 500 또는 삭제된 부서 아래로 이동 ② 자기 자신이나 자기 하위 부서를 상위로 지정 → 서로를 부모로 가지는 묶음이 트리에서 통째로 사라지고, 트리를 따라가는 로직(`BoardAuth.includeSubDepartment` 등)이 무한 루프.
- **고민**: 프론트에서 select 선택지를 걸러 막으면 되지 않나? → 프론트 검증은 API 직접 호출로 우회 가능하고, 관리자 두 명이 동시에 서로를 옮기면 각 화면 기준으로는 정상이라 원리상 막을 수 없음.
- **결정**: 프론트는 사용 편의(선택지 제외), 백엔드는 무결성. 새 상위 부서부터 최상위까지 `parentDepartmentId`를 따라 올라가며 자기 id가 나오면 400, 조회 결과가 없으면 400 → 검증 ①②를 하나의 반복문으로 처리.
- **한계**: 검사가 트랜잭션 밖이라 정확히 동시에 들어온 두 이동 요청은 이론상 통과 가능. 완전히 막으려면 잠금(`FOR UPDATE`) 또는 SERIALIZABLE.
- **설계 포인트**: 프론트 검증과 백엔드 검증의 역할 분리, 자기 참조 트리 수정 시 주의점, 동시성 한계를 인지하고 범위를 정한 판단.

## 2026-10-20 ~ 10-21 · 회원 소속(UserDepartment) 작업 + 직급 위치 변경

관련 커밋: `efae797`

### 1. 하위 부서·소속 인원이 있는 부서 삭제 차단
- **문제**: `deleteDepartment`가 바로 soft delete → 하위 부서는 삭제된 부서를 부모로 가진 채 트리에서 사라지고, 소속 인원은 삭제된 부서에 묶여 남음.
- **결정**: 가장 단순한 방법으로 하위 부서(`deleted: false`)나 소속 인원이 있으면 400. 소속 인원 집계에서 **퇴사자(`RESIGNED`)는 제외** — 퇴사자 소속 행이 남아 있어도 부서는 정리할 수 있어야 함. (`user: { status: { not: RESIGNED } }` 관계 필터)

### 2. 직급 연동은 소속(UserDepartment)에서 회원(Users)으로 이동
- **문제**: `positionId`가 `UserDepartment`에 있어 겸직 시 소속마다 직급이 달라질 수 있음. 실제로 직급(과장·차장)은 사람 단위, 직책(팀장)은 소속 단위. `BoardAuth`의 "최소 직급" 판정 시 어느 소속의 직급을 볼지도 애매해짐.
- **결정**: `Users.positionId Int?`로 이동(관리자 지정 전 신규 가입자는 NULL), `UserDepartment`는 회원-부서-직책만 연결. 소속 API 구현 전이라 데이터 손실 없이 바꿀 수 있는 시점.
- **설계 포인트**: 도메인 개념(사람 속성 vs 소속 속성)에 맞춰 FK 위치를 정한 판단.

### 3. 소속은 관리자가 지정, 대표 소속은 본인도 변경
- **고민**: 신규 회원이 가입 시 소속을 직접 선택 vs 관리자 지정.
- **결정**: 관리자 지정. 소속(부서·직책)과 직급이 게시판 권한(`BoardAuth`)·결재라인의 판단 근거라 본인 입력을 허용하면 권한 상승이 가능. 가입 기본 role이 `GUEST`인 것도 "관리자 승인 후 정식 직원" 흐름과 맞음. 대표 소속만 회원이 마이페이지에서 고를 수 있게 함.
- **퇴사자 소속 추가**: 관리자 재량으로 막지 않음.

### 4. 대표 소속 규칙과 partial unique 순서
- **규칙**: 첫 소속은 자동 대표. 같은 부서 중복 소속 400. 대표 소속 삭제 시 남은 소속 중 가장 오래된 것(`createdAt`, `id` 순)을 자동 승격 — 대표 소속이 비는 상태를 만들지 않아 이후 권한·결재 스냅샷 로직이 "대표 없음"을 처리하지 않아도 됨.
- **함정**: `@@unique([userId], where: { isPrimary: true, deleted: false })` 때문에 트랜잭션 안의 실행 순서가 중요. 대표 변경은 **기존 대표 해제 → 새 대표 지정**, 대표 삭제는 **삭제 → 승격** 순서여야 unique 위반이 나지 않음(배열 `$transaction`은 쿼리 순서대로 실행).
- **본인 확인**: 회원용 `PATCH /organization/me/departments/:id/primary`는 관리자용과 같은 서비스 메서드를 쓰되 `userId` 자리에 로그인 회원 id를 넘김 → 다른 회원의 소속 id는 `where: { id, userId }` 조회에서 걸러짐.
- **한계**: 첫 소속 두 개가 동시에 추가되면 unique 위반(P2002) 500. 발생 빈도가 낮고 DB 제약이 무결성을 지키므로 감수.

### 5. `IsOptional` + Prisma `undefined` 조건 무시 함정
- **문제**: 직급 지정 DTO를 기존 패턴(`@IsInt() @IsOptional() @EmptyToNull()`)으로 바꾸면 키 누락(`undefined`)이 서비스까지 통과. 이때 `null`만 거르면 `findFirst({ where: { id: undefined } })` → Prisma가 조건을 **제외**해 아무 직급이나 찾아 검증 통과.
- **결정**: `undefined`(변경 없음)와 `null`(해제)을 모두 걸러 검사. `checkJobTitle`도 같은 방식.
- **설계 포인트**: 10-20 항목 2의 `parentDepartmentId` 함정과 같은 원인. Prisma `where`의 `undefined`는 "조건 없음"이다.

### 6. 마이그레이션 미적용으로 로그인 전체 실패 (시행착오)
- **문제**: 스키마 변경 후 로그인 시 P2022 `column users_model.position_id does not exist`.
- **원인**: `migrate dev --create-only`로 마이그레이션 파일만 만들고 적용하지 않은 상태에서 `generate` → client는 새 컬럼을 알지만 DB에는 없음. `select` 없는 `findFirst`는 모든 컬럼을 SELECT하므로 `Users`를 조회하는 모든 API가 실패.
- **해결**: `prisma migrate status`로 미적용 마이그레이션 확인 → `migrate dev`로 적용.
- **배운 점**: `generate`는 스키마 파일 기준, DB 상태와 무관. 스키마 변경 후에는 `migrate status`로 DB와 일치하는지 확인.

## 2026-10-21 · 관리자 회원관리 (Users) + 권한 등급 비교

관련 커밋: `acb432f`
테스트: 회원 상세 조회만 확인. 나머지(정보 수정, 승인·권한, 상태, 복구, 비밀번호 초기화, 삭제 회원 목록)는 10-22에 Postman으로 확인 예정.

### 1. `RolesGuard` 비교를 "같은 값"에서 "등급 이상"으로
- **문제**: `user.role !== requiredRole` 비교라 `@Roles(USER)`를 붙이면 ADMIN이 거부됨. GUEST를 막기 시작하면 바로 부딪힘.
- **고민**: Prisma enum에는 값을 붙일 수 없음 → ① `Role` 테이블(name, level) ② 코드에서 enum → level 매핑.
- **결정**: ② `ROLE_LEVEL: Record<UserRole, number>` (`auth/const/role-level.const.ts`). 스키마 변경 없음, CLAUDE.md 5.1 "권한은 enum" 유지. `Record<UserRole, ...>`라 enum에 값이 추가되면 매핑 누락이 컴파일 에러로 드러남.
- **남은 결정**: GUEST 접근 범위. 마이페이지(본인 계정 조회·수정·비밀번호 변경·탈퇴)만 허용하고, 기본값을 USER 이상으로 두는 방향(빠뜨려도 닫히는 쪽으로 실패) 검토 중.

### 2. 관리자 본인 대상 변경 차단 = 마지막 ADMIN 보호
- **고민**: 마지막 ADMIN 강등·퇴사를 막으려면 ADMIN 수를 세야 하나?
- **결정**: 권한·상태 변경에서 대상이 요청한 관리자 본인이면 400(`checkNotSelf`). 요청자는 항상 ADMIN으로 남으므로 별도 count 없이 "관리자 0명" 상태가 생기지 않음.
- **설계 포인트**: 규칙 하나로 두 문제(자기 권한 상실, 마지막 관리자)를 함께 해결.

### 3. 가입 승인과 입사일
- `GUEST → USER/ADMIN`이 승인. 입사일(`joinAt`)이 없는 GUEST를 승인할 때는 `joinAt` 필수(연차 계산 전제). `GUEST`로 되돌리기는 금지.
- 입사일은 승인 시 + 관리자 회원 정보 수정에서 입력. (가입 DTO에는 없음)

### 4. 삭제 회원 복구 시 `tokenVersion` 증가
- **문제**: 복구만 하면 삭제 전에 발급된 토큰이 다시 유효해짐(가드는 deleted만 보고 막았으므로).
- **결정**: 복구 시 `tokenVersion` +1. 삭제 기간 중 다른 회원이 같은 이메일·사번을 쓰고 있으면 복구 400.

### 5. 비밀번호 초기화 — 관리자 입력 vs 서버 생성
- **처음 구현**: 관리자가 임시 비밀번호를 body로 입력.
- **문제**: 관리자가 정한 값은 예측 가능(모두에게 같은 값 반복 등). 관리자가 평문을 알고 직접 전달하는 점은 두 방식이 같음.
- **결정**: 서버가 `crypto.randomInt`로 12자리 생성(헷갈리는 문자 0/O, 1/l/I 제외) → 응답으로 한 번만 반환, DB에는 해시만. `Math.random()`은 암호학적으로 안전하지 않음. `tokenVersion` 증가로 기존 토큰 무효화. 위치는 auth(해시 로직 + Auth → Users 단방향 의존).
- **한계 / 개선**: 진짜 일회용이 아님(변경 강제 없음). 메일 재설정 링크(SES)가 관리자도 비밀번호를 모르는 방식 → Plan.md "시간이 날 때"에 기록. 회고 "더 개선한다면?" 소재.

### 6. 회원 목록 `allDepartments` 버그 (직접 구현 리뷰)
- `isPrimary: allDepartments ? false : true` → `false`는 "조건 없음"이 아니라 "대표가 아닌 소속만". `undefined`로 바꿔 조건 제외. 10-20 항목 5와 같은 Prisma `undefined` 규칙.

## 2026-10-22 · 페이지네이션 이식 + BigInt 직렬화 + 부서 목록 트리 순서

관련 커밋: `b32f01a`

### 1. 페이지네이션을 공통 서비스가 아닌 순수 함수로 분리 ⭐
- **배경**: NestJS_SNS(TypeORM)는 `CommonService.paginate(dto, repository)`처럼 `Repository<T>`를 받아 조회까지 공통 서비스가 처리했다.
- **고민**: Prisma는 모델마다 delegate(`prisma.users`, `prisma.notification`) 타입이 달라 공통 제네릭으로 받기 어렵다. 억지로 묶으면 `any`가 들어가고 `select`/`include`에 따른 결과 타입 추론이 사라진다. 조회 함수를 콜백으로 넘겨 하나로 합치는 방법도 검토.
- **결정**: 조회(`findMany`, `count`)와 정렬은 도메인 서비스에 두고, 공통으로는 인자 계산과 응답 형식만 순수 함수로 뺐다 (`common/util/pagination.util.ts`).
  - page: `PageArgs`(page → skip/take), `PageResult`(totalPages, hasNext, hasPrevious)
  - cursor: `CursorArgs`(cursor/skip/take, `take + 1`), `CursorResult`(초과분 제거, `nextCursor`)
- **응답은 링크 대신 boolean**: 서버가 `next` URL을 만들려면 외부 주소(프로토콜·호스트, Nginx의 `/api` 제거)를 알아야 하고, 쿼리스트링 재조립 시 falsy 필터가 빠지는 버그가 생기기 쉽다. 프론트가 이미 page와 검색 조건을 알고 있으므로 `hasNext`/`hasPrevious`만 내려 준다.
- **설계 포인트**: 같은 기능이라도 ORM 특성(TypeORM Repository 제네릭 vs Prisma delegate)에 따라 공통화 범위를 다르게 잡은 판단.

### 2. 쿼리스트링 숫자 변환 — `@Type(() => Number)` 대신 `@StringToNumber`
- **문제**: Intranet `main.ts`에는 `enableImplicitConversion`이 없어 `?take=20`이 문자열로 들어온다. `@Type(() => Number)`는 `Number(value)`라 `""` → `0`(검증 통과), `"abc"` → `NaN`, `"0x10"` → `16`.
- **결정**: 숫자 형식 문자열(`/^-?\d+(\.\d+)?$/`)만 변환하고 나머지는 그대로 두어 `@IsInt()`에서 400. `take`는 `@Min(1) @Max(100)`, `page`는 `@Min(1)`(음수 skip은 Prisma 에러).
- **TS enum 함정**: 문자열 enum 타입에는 값이 같아도 리터럴(`'desc'`)을 넣을 수 없다 → `SortOrder.DESC`. 런타임 요청 값은 `@IsEnum`이 검사하므로 `"desc"` 문자열로 들어와도 통과.

### 3. 커서 정렬 기준과 정렬 컬럼 제한 (시행착오)
- **처음**: `where id < cursor` + id 정렬 고정.
- **요구**: 정렬 기준 선택. "정렬이 바뀌면 커서 초기화"만으로는 부족 — ① 커서 조건이 정렬 기준과 맞아야 하고 ② 정렬 값이 같은 행이 있으면 경계에서 누락·중복.
- **변경**: Prisma `cursor: { id }, skip: 1` + `orderBy: [{ [sortBy]: order }, { id: order }]`. Prisma가 커서 행의 정렬 값을 읽어 비교 조건을 만들고, id 2순위로 동점 순서를 고정. 커서는 그대로 id 하나.
- **시행착오**: 정렬 허용 목록을 유틸이 런타임에 확인하는 `SortArgs`(`const` 타입 파라미터로 컬럼명까지 컴파일 검사)까지 만들었다가 너무 복잡해서 되돌림 → 도메인 DTO의 `sortBy` enum(`@IsEnum`)으로 제한하고 Service가 `orderBy`를 직접 작성. 대신 `{ [query.sortBy]: ... }`는 Prisma가 컬럼명을 검사하지 못하므로 enum 값이 유일한 방어선.
- **타입 함정**: `CursorArgs`가 커서 유무에 따라 `{}` / `{ cursor, skip }`처럼 유니온을 반환하면 `findMany` 제네릭 추론 실패 → 항상 같은 형태(`cursor: undefined`, `skip: 0`)로 반환.
- 정렬·검색 조건이 바뀌면 커서 초기화는 프론트 책임(서버는 stateless). TanStack Query `useInfiniteQuery`의 queryKey에 필터를 넣으면 자동 초기화.

### 4. `orderBy` 생략·2순위 id — query 로그로 확인
- **확인 결과** (직책 테이블, Prisma query 로그):
  - `orderBy` 생략 + skip/take 또는 cursor → Prisma가 `ORDER BY id ASC` 자동 추가. 단 `order` 방향은 무시되고 문서로 보장된 동작이 아니라 의존하지 않음.
  - 정렬 컬럼 지정 시 그 컬럼만 사용, **id 2순위는 자동으로 붙지 않음**.
  - cursor + id 없는 정렬: `WHERE name >= (커서 행의 name)`이라 같은 값 행이 다시 포함되고 SQL에 `LIMIT`도 빠짐.
- **시행착오**: 처음엔 "`orderBy` 생략 시 ORDER BY가 안 붙는다"고 판단했으나 로그로 보니 skip/take가 있으면 id 정렬이 붙었다. 추측 대신 로그로 확인.
- **결정**: 페이지네이션 조회는 항상 `orderBy` 지정 + 마지막에 `{ id: order }`. 직급·직책은 이름 중복 불가·10개 안팎이라 생략해도 실제 문제는 거의 없음.

### 5. 트랜잭션으로 묶어도 "같은 시점 조회"가 아니다 ⭐
- **처음 판단**: `$transaction([findMany, count])`이면 목록과 total이 같은 시점 기준이라고 생각해 주석에도 그렇게 적음.
- **바로잡음**: PostgreSQL 기본 격리 수준 READ COMMITTED는 **쿼리마다 스냅샷**을 새로 잡는다. 트랜잭션 안에서도 두 쿼리 사이에 커밋된 변경이 보인다(non-repeatable read, phantom read). 같은 스냅샷이 필요하면 REPEATABLE READ.
- **결정**: 목록의 total이 순간적으로 하나 어긋나는 정도는 허용 → `Promise.all`로 병렬 조회(동시성, DB가 다른 연결에서 동시에 처리). 쓰기에는 쓰지 않는다.
- **관련 정리**: 같은 트랜잭션 안에서 내가 INSERT한 행은 커밋 전에도 나에게 보인다. Prisma 콜백 트랜잭션에서는 `tx`를 써야 하고, `this.prisma`를 쓰면 조용히 트랜잭션 밖에서 실행된다. 회의실 예약 중복(조회 후 INSERT)은 READ COMMITTED에서 두 요청이 동시에 통과할 수 있음 → 행 잠금 필요.
- **설계 포인트**: 트랜잭션은 쓰기를 묶는 도구이고 읽기 일관성은 격리 수준이 정한다.

### 6. BigInt 응답 직렬화 — Express `json replacer`
- **문제**: `Notification`·`Audit`·`ApprovalDocumentHistory`의 BigInt id는 `JSON.stringify`가 처리하지 못해 500. `CursorResult`는 `nextCursor`만 문자열로 바꿈.
- **고민한 선택지**: `BigInt.prototype.toJSON`(전역 패치, 영향 범위 넓음) / 커스텀 인터셉터(재귀 순회 코드, Date·Decimal 오처리 위험, 응답 이중 순회) / 응답 DTO 직접 변환(타입 일치하지만 중첩 관계 포함 반환하는 곳마다 필요, 빠뜨리면 런타임 500) / Express `json replacer`.
- **결정**: `main.ts`에 `app.set('json replacer', ...)`. 직렬화 문제를 직렬화 단계에서 푸는 방식이 범위가 가장 좁고 단순.
- **측정**: replacer가 있으면 V8 `JSON.stringify` 빠른 경로가 꺼져 직렬화가 약 2배 느려짐(20행 10µs → 24µs, 100행 50µs → 115µs). DB·네트워크(ms 단위) 대비 무시할 수준, `take` 최대 100이라 MB 단위 응답 없음.
- **한계**: 타입은 `bigint`인데 응답은 문자열(프론트 타입은 string), Socket.IO emit에는 적용 안 됨, Fastify 전환 시 재처리.
- **설계 포인트**: 인터셉터가 "Nest다운" 방식이지만 문제 크기에 맞는 해결책을 골랐고, 성능 영향을 측정으로 확인.

### 7. 부서 목록 — 페이지네이션 대신 트리 순서 목록 ⭐
- **처음**: 부서 목록에도 page 방식을 이식 → 부서는 트리이고 `sortOrder`는 같은 상위 부서 안의 순서라, 전체를 sortOrder로 정렬해 자르면 본부와 하위 팀이 뒤섞임. `sortBy`·`order`를 받지만 무시하는 문제도 있었음.
- **고민**: 평평한 목록(A) / 서버에서 중첩 트리 조립(B) / 펼칠 때 하위만 조회(C). Prisma 중첩 include는 깊이가 고정되어 제외.
- **결정**: 경로 형식의 평평한 목록 (`경영지원본부`, `경영지원본부/인사팀` …). 같은 이름의 부서를 구분할 수 있고(부서명 중복은 같은 상위 안에서만 막음), 검색 시 위치가 함께 보이며, 표·선택 목록에 그대로 쓸 수 있다.
  - `parentDepartmentId, sortOrder, id` 정렬만으로는 안 됨: 같은 상위끼리 모일 뿐 하위가 상위 바로 아래에 오지 않고, NULL(최상위)은 오름차순에서 맨 뒤.
  - 한 번 조회 → 상위 id별 하위 목록 Map → 형제는 `sortOrder`, `id` 순 정렬 → 전위 순회로 `depth`, `path` 부여. 상위를 못 찾으면 최상위로 취급해 목록에서 사라지지 않게 함.
  - `common/util/tree.util.ts`의 `toTreeList(items, getParentId)`로 분리 (게시판 `parentBoardId`에도 재사용 가능). 정렬을 유틸 안에서 해서 쿼리 `orderBy`에 의존하지 않음.
  - 검색은 `path.includes(name)` → 상위 부서명으로 검색하면 하위까지 함께 조회.
- **측정**: 1만 개 트리 조립 3.5ms / 응답 1.1MB, 5만 개 12.4ms / 6MB → 서버 계산이 아니라 응답 크기·렌더링이 병목. 대규모라면 단계별 지연 로딩 + 서버 검색 + 캐시, 하위 조회가 잦으면 ltree/closure table.
- **남은 결정**: 메서드·DTO 이름(`paginateDepartment`)이 더 이상 페이지네이션이 아님, 경로 구분자 `/`가 부서명에 들어갈 수 있음.

### 8. 기타
- 상속받은 DTO 속성은 데코레이터 없이 `order: SortOrder = SortOrder.ASC;`로 기본값만 바꿀 수 있다(부모 검증 규칙 유지, 확인함). 단 `target: ES2023`(`useDefineForClassFields`)에서 초기값 없이 재선언하면 `undefined`로 덮어써짐.
- Jest 설정이 `src/...` 경로 매핑, Prisma 7 생성 코드의 `.js` import, `@nestjs/config` ESM을 처리하지 못해 서비스 단위 테스트가 실행되지 않음 → 테스트 작성 전에 설정 정비 필요.

## 2026-10-23 · 프론트엔드 초기 설정 (Next.js 16 + shadcn/ui)

관련 커밋: `3b8e816` 프론트엔드 기본 세팅

### 1. 프론트엔드 작업 기준 문서
- `docs/frontend_requirements.md`는 매번 지켜야 하는 공통 규칙(디자인, 레이아웃, 반응형, API 연동, 작업 방식)만 담는다. 화면별 기능은 작업할 때마다 프롬프트로 지정한다.
- 라우팅은 CLAUDE.md 12~13장을 기준으로 맞췄다(`(auth)` / `(main)` / `admin`).

### 2. 브라우저 → 백엔드 호출 경로: `/api` rewrite ⭐
- **문제**: NestJS(3100)에 CORS 설정과 `/api` 접두사가 없어서, 브라우저가 3000에서 3100을 직접 부르면 CORS에 막힌다.
- **고민한 선택지**: NestJS에 `enableCors` 추가(백엔드 수정 필요, 운영 구조와 다름) / Next.js `rewrites`로 같은 출처의 `/api/*`를 프록시.
- **결정**: `rewrites`로 `/api/:path*`를 `${API_SERVER_URL}/:path*`로 보내며 `/api`를 뗀다. 운영 Nginx의 `intranet 도메인/api → NestJS`와 같은 경로 정책이라 개발과 운영에서 프론트 코드가 같다. 브라우저는 상대 경로만 쓰므로 `NEXT_PUBLIC_` 변수가 필요 없어졌다(`API_SERVER_URL`은 서버 전용).
- **확인**: 3100에 요청 경로를 돌려주는 임시 서버로 `/api/users?page=2` → `/users?page=2`, `/api/auth/login/emp` → `/auth/login/emp` 전달 확인.
- **주의**: rewrite 목적지는 `next build` 시점에 고정된다. Docker 이미지는 빌드 인자로 넘겨야 하는데, 운영에서는 Nginx가 `/api`를 먼저 처리하므로 개발 환경에만 해당된다.

### 3. 인증 Route Handler는 `/api` 밖의 `/auth/*`로 분리 ⭐
- **문제**: 로그인·재발급·로그아웃은 Next.js Route Handler가 HttpOnly 쿠키를 다루기로 했다. 이 Handler를 `/api/auth/...` 아래에 두면 개발에서는 파일 라우트가 rewrite보다 먼저 잡히지만, 운영에서는 Nginx가 `/api/`를 NestJS로 보내 버려 동작이 달라진다.
- **고민한 선택지**: `/api` 아래에 두고 rewrite와 Nginx 양쪽에 예외 규칙 추가 / `/api` 밖에 두기.
- **결정**: `/api/*`는 NestJS 프록시, `/auth/*`는 Next.js Route Handler(BFF, Backend For Frontend 패턴). 예외 규칙이 없어 rewrite와 Nginx 규칙이 각각 한 줄로 끝난다. NestJS의 `/auth/*`는 브라우저에서 `/api/auth/*`로 부르므로 겹치지 않는다.
  - 처음엔 `/bff/*`로 정했다가 `/auth/*`로 변경. (`app/(auth)/` Route Group은 URL에 안 나타나므로 충돌 없음. 단 `app/auth/`(Handler)와 `app/(auth)/`(로그인 화면) 폴더 이름이 비슷하니 주의.)
- **BFF가 필요한 이유**: HttpOnly 쿠키는 브라우저 JS가 만들거나 읽거나 지울 수 없고 서버의 `Set-Cookie`로만 다룰 수 있다. NestJS는 토큰을 응답 본문으로 주고 refresh token을 `Authorization` 헤더로 받으므로, 중간에서 "본문 → 쿠키 저장", "쿠키 → 헤더 변환", "쿠키 삭제"를 해 줄 서버 계층이 필요하다. `/api` rewrite는 그대로 전달만 하므로 이 역할을 못 한다.
- **경로를 분리한 추가 이유 (FE-01에서 쿠키 설정으로 확정)**:
  - refresh 쿠키를 `Path=/auth`로 제한하면 일반 `/api` 요청에는 붙지 않는다. 섞여 있으면 모든 API 요청마다 오래 유효한 토큰이 NestJS까지 전달되어 노출 경로가 늘어난다.
  - 쿠키가 자동으로 붙는 경로가 `/auth`의 몇 개로 줄어 CSRF 대응(`SameSite`, Origin 검사)도 여기에 집중하면 된다.
  - URL만 보고 NestJS 처리인지 Next.js 서버 처리인지 구분된다.
- **반론과 트레이드오프**: NestJS가 직접 `Set-Cookie` 하면 BFF 계층이 필요 없어 더 단순하다. 이번에는 "백엔드 API를 바꾸지 않는다"는 제약 때문에 BFF를 택했고, 대가로 요청 한 단계와 관리할 코드가 늘어난다. FE-01 시작 시 다시 검토할 수 있다.
- **설계 포인트**: 같은 기능이 개발과 운영에서 다른 경로 규칙을 타지 않도록 프록시 경계를 URL 접두사로 나눴다.

### 4. 토큰 저장: Access는 메모리, Refresh는 HttpOnly 쿠키 (구현은 FE-01)
- **배경**: 백엔드는 토큰을 응답 본문으로 돌려준다. Next.js `proxy.ts`(Next 16에서 middleware가 바뀐 이름)로 페이지 접근을 막으려면 서버에서 읽을 수 있는 쿠키가 필요하다.
- **결정**:
  - Refresh Token: `/auth` Route Handler가 NestJS 응답 본문에서 꺼내 HttpOnly 쿠키로 저장 → JS에서 읽을 수 없어 XSS로 탈취되지 않는다.
  - Access Token: React 메모리에만 둔다. 새로고침하면 사라지므로 `/auth`의 재발급으로 다시 받는다.
  - localStorage/sessionStorage에는 JWT를 저장하지 않는다.
  - 백엔드 수정 없이 프론트(BFF) 계층에서 해결한다.
- **FE-01에서 정할 것**: 쿠키의 `SameSite`·`Path` 범위(CSRF 대응), 앱 시작 시 재발급 흐름, 401 → 재발급 1회 → 재시도, 동시에 여러 요청이 401일 때 재발급 중복 방지.
- **설계 포인트**: localStorage(XSS에 노출) vs 쿠키(CSRF 고려 필요)의 트레이드오프, stateless JWT와 `tokenVersion` 무효화가 프론트 재발급 흐름과 어떻게 이어지는지.

### 4-1. 결정 변경: BFF 대신 NestJS가 직접 `Set-Cookie` ⭐
- **처음 판단**: "백엔드 API를 바꾸지 않는다"는 전제로, Next.js Route Handler(BFF, `/auth/*`)가 NestJS 응답 본문의 refresh token을 HttpOnly 쿠키로 바꾸도록 설계했다(3번 항목).
- **다시 본 이유**: "NestJS가 직접 Set-Cookie 하면 BFF가 필요 없지 않나?"라는 질문에 답해 보니, 근거가 "백엔드를 바꾸지 않는다"는 제약뿐이었다. 그런데 그 제약은 AI 에이전트가 프론트 작업 중 백엔드를 임의로 고치지 못하게 하려는 규칙이었지, 백엔드를 직접 수정하는 것까지 막는 규칙이 아니었다.
- **결정**: NestJS가 로그인 시 refresh token을 HttpOnly 쿠키로 내려주고, 재발급 시 쿠키에서 읽는다. 프론트와 API가 같은 출처(`/api` rewrite, 운영 Nginx)라 CORS 없이 동작한다.
  - 실무에서도 백엔드가 직접 쿠키를 다루는 구성이 흔하다. BFF는 백엔드를 바꿀 수 없거나 도메인이 완전히 다를 때 주로 쓴다.
  - Route Handler 계층이 없어져 구조가 단순해지고, 인증 처리가 백엔드에 모인다(백엔드 중심 포트폴리오에도 맞음).
- **백엔드 작업(FE-01 전)**: 로그인 응답에 `Set-Cookie` 추가, `RefreshTokenGuard`·재발급 API가 쿠키에서 토큰 읽기(cookie-parser), 로그아웃 API(쿠키 삭제), 쿠키 옵션(`HttpOnly`, `SameSite`, `Path=/api/auth` — rewrite로 `/api`가 떨어져도 Path는 브라우저 기준), 개발 환경 `Secure` 처리.
- **설계 포인트**: 처음 설계의 근거를 다시 따져 보니 제약을 잘못 해석한 것이었고, 더 단순한 구조로 바꿨다. PHP 세션 쿠키(`PHPSESSID`)와 같은 원리로 설명할 수 있다.

### 5. 데이터 패칭: TanStack Query + 공통 `apiFetch`
- `services/api-client.ts`: `/api` 기준 fetch 래퍼. NestJS 기본 에러(`{ statusCode, message, error }`, ValidationPipe는 `message` 배열)를 `ApiError(status, messages)`로 바꾼다.
- QueryClient 기본값: `staleTime` 30초, 창 포커스 시 재조회 끔, **4xx는 재시도하지 않음**(권한·검증 오류는 다시 보내도 결과가 같다), 5xx·네트워크 오류는 1회 재시도.

## 2026-10-23 · 백엔드: refresh token을 HttpOnly 쿠키로 (NestJS 직접 Set-Cookie)

관련 커밋: `7d31250` refreshToken 토큰 전달 방식 변경(백엔드에서 HttpOnly 쿠키 발급)

> 결정 배경(BFF → NestJS Set-Cookie)은 위 "프론트엔드 초기 설정" 항목 4-1 참고.

### 1. 나가는 곳: 응답 본문 → `Set-Cookie`
- 로그인, 회원가입, 비밀번호 변경, refresh 재발급에서 refresh token을 `res.cookie()`로 내려주고, 본문에는 `{ accessToken }`만 남김. 본문에도 넣으면 JS가 읽을 수 있어 쿠키에 담은 의미가 없어진다.
- **서비스(`loginUser`)는 그대로**: 토큰을 만드는 것까지가 서비스의 일이고, 쿠키로 보낼지 본문으로 보낼지는 HTTP 응답에 관한 일이라 컨트롤러가 `@Res({ passthrough: true })`로 처리. `passthrough`가 없으면 Nest가 응답을 대신 보내지 않아 return 값이 무시된다.
- 회원가입·비밀번호 변경 서비스는 async라 `await` 없이 구조 분해하면 Promise를 분해해 두 값이 `undefined`가 된다.
- `Response` 타입은 `express`에서 import해야 한다. 안 하면 Node 내장 fetch의 `Response`로 잡혀 `res.cookie`가 타입 에러.

### 2. 들어오는 곳: 가드에서 "꺼내기"와 "검증" 분리 ⭐
- **문제**: `authenticate(req)`가 Authorization 헤더에서 토큰을 꺼내는 일과 검증을 함께 하고 있어서 refresh만 쿠키에서 읽게 바꿀 수 없었다.
- **결정**: `authenticate(req, token)`으로 바꿔 검증(서명 → 사용자 조회 → tokenVersion → 상태 체크)만 담당. `BearerTokenGuard`는 헤더에서, `RefreshTokenGuard`는 `req.cookies.refreshToken`(cookie-parser)에서 꺼내 넘긴다. `AccessTokenGuard`는 부모를 호출하므로 변경 없음.
- 재발급 컨트롤러는 헤더를 다시 파싱하지 않고 가드가 저장한 `req.token`을 사용.

### 3. 쿠키 옵션
- `httpOnly`, `path: '/api/auth'`, `sameSite: 'lax'`, `secure: PROTOCOL === 'https'`, `maxAge`.
- **Path는 브라우저 기준**: NestJS는 rewrite로 `/api`가 떨어진 `/auth/...`를 받지만, 쿠키 경로는 브라우저가 보는 `/api/auth`로 판단한다.
- **시행착오 1 (환경 구분)**: 처음에 `NODE_ENV`로 secure를 나누려다 NestJS는 NODE_ENV를 넣어 주지 않고 설정이 복잡해짐 → 이미 있던 `PROTOCOL` 환경변수 재사용(사용자 제안).
- **시행착오 2 (읽는 시점)**: 옵션을 상수 객체로 두고 `process.env.ENV_PROTOCOL_KEY`를 읽었는데 ① 변수 이름이 틀렸고(상수 이름이지 env 키가 아님, 실제는 `PROTOCOL`) ② 상수 객체는 import 시점에 한 번 계산되는데, `app.module.ts`에서 `AuthModule` import가 `ConfigModule.forRoot()`보다 먼저 평가되어 `.env`가 아직 로드되지 않음 → 운영에서도 secure가 항상 false. **호출할 때 계산되는 함수 `refreshTokenCookieOptions()`로 변경.**
- 유효시간: JWT `expiresIn`(초)과 쿠키 `maxAge`(밀리초)가 같은 기간이므로 `REFRESH_TOKEN_EXPIRES_IN` 상수 하나에서 계산. refresh를 1시간 → 1일로 변경(사내 인트라넷, 매일 로그인).
- 쿠키 이름 `'refreshToken'`은 바뀔 일이 없어 상수로 만들지 않고 문자열 사용(사용자 판단).

### 4. 로그아웃 `POST /auth/logout`
- `res.clearCookie()`는 저장 때와 `path`가 같아야 지워지므로 같은 옵션 함수를 사용하고 `maxAge`만 제외(최신 Express는 clearCookie에서 무시하고 경고).
- access token이 만료돼도 로그아웃할 수 있게 `@IsPublic()`.
- GET이 아닌 POST: 상태를 바꾸는 요청. GET이면 다른 사이트의 이미지 태그·링크(SameSite=Lax는 링크 이동에 쿠키 전송)·프리패치로 사용자 모르게 로그아웃될 수 있음.
- 이미 발급된 access token은 서버가 회수하지 않아 최대 10분 유효(만료를 짧게 둔 이유). 강제 무효화는 tokenVersion.

### 5. Postman 테스트에서 겪은 것
- 쿠키 Path가 `/api/auth`라 3100번으로 직접 `/auth/...`를 호출하면 쿠키가 자동으로 붙지 않음 → `Cookie: refreshToken={{refreshToken}}` 헤더를 직접 넣거나 3000번 `/api/...`로 호출.
- `pm.response.cookies`도 Path가 맞지 않는 쿠키는 걸러서 빈 값 → `Set-Cookie` 헤더를 정규식으로 파싱.
- 재발급 요청에 예전 설정(`Authorization: Bearer {{refreshToken}}`)이 남아 401 → 실패 응답에 스크립트가 `accessToken`을 undefined로 덮어씀. 재발급 요청은 `No Auth` + Cookie 헤더, 스크립트는 상태 코드 확인 후 저장.

### 설계 포인트
- 토큰 전달 통로만 바꾸고 검증 로직·tokenVersion·stateless 구조는 그대로 유지.
- HttpOnly 쿠키는 "값 탈취"를 막지만 페이지 안에서의 "악용"까지 막지는 못함 → XSS 방지가 우선.

- 현재 비밀번호 칸을 폼에서 빼고 [저장]/[비밀번호 변경] 시 모달로 입력받음. 두 폼이 같은 `CurrentPasswordDialog`를 사용.
- 오류 위치를 나눔: 비밀번호 불일치(401)는 모달 안에서 재입력, 이메일 중복 같은 폼 오류는 모달을 닫고 폼 위에.
- **발견한 점**: 백엔드가 현재 비밀번호 불일치를 401로 응답 → apiFetch가 토큰 만료로 보고 재발급·재시도를 한 번 더 함(`/auth/*` 경로인 비밀번호 변경은 제외). 401(인증 안 됨)과 "입력한 비밀번호가 틀림"은 의미가 다르므로 400이 맞다
- **해결 (`f94fb55`, 백엔드는 사용자가 직접 수정)**: `verifyPassword`를 로그인(401)과 본인 확인(400)이 같이 쓰고 있어서 그냥 400으로 바꾸면 로그인까지 400이 됨.
  - 고민한 선택지: ① 함수가 호출한 곳을 스택으로 알아내기(깨지기 쉽고 의존 방향이 거꾸로) ② `purpose` 인자로 호출하는 쪽이 상황을 넘기기 ③ boolean만 반환하고 호출부에서 예외 ④ 함수 분리.
  - 결정: ② `verifyPassword(user, pw, purpose: 'login' | 'confirm' = 'confirm')`. 함수 하나를 유지하면서 로그인만 `'login'`을 넘기면 됨.
  - 프론트: 비밀번호 불일치와 이메일 중복이 둘 다 400이 되어 상태 코드로 구분 불가 → 저장 오류는 모두 모달 안에 표시, 모달을 닫으면 오류 초기화. 비밀번호 오류 시 재발급 요청이 0회가 된 것을 확인.

### 설계 포인트
- 토큰 위치(메모리 / HttpOnly 쿠키)와 새로고침 시 재발급 흐름, 동시 401 처리, GUEST 화면 가림과 백엔드 차단의 역할 구분, 로그인 실패 메시지 통일.
