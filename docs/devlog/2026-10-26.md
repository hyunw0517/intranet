  - 페이지 이동 UI가 안 보이던 원인: 백엔드 기본 `take`가 20인데 회원이 6명이라 1페이지뿐이었고, `PaginationBar`가 1페이지면 숨김 → 항상 표시 + 표시 개수 선택. 백엔드 페이지네이션은 정상이었음.
- **일괄 API 설계 — 단건을 "원소 1개짜리 일괄"로**: 단건 서비스(`updateUserRole`, `updateUserStatus`, `adminDeleteUser`)가 `ids` 배열을 받게 바꾸고 단건 컨트롤러는 `[id]`로 호출. 본인 제외·삭제 회원 제외 검증이 `validateTargetUsers` 한 곳에 모임.
  - **반복문 + 트랜잭션 vs `updateMany`**: 모두 같은 값을 넣으므로 `updateMany` 한 번. 반복문은 회원마다 다른 처리가 필요할 때. (반복문이면 `forEach(async)`는 await를 기다리지 않으므로 `for...of`)
  - **검증과 수정 사이 경쟁 상태**: `findMany`로 검증한 뒤 `updateMany` 전에 다른 관리자가 삭제할 수 있음 → 검증 조건을 `updateMany`의 `where`에도 다시 걸고, 바뀐 `count`가 요청 수와 다르면 트랜잭션 안에서 예외 → 전체 롤백. "검증은 친절한 메시지용, WHERE 조건은 무결성용".
  - **권한·상태를 한 요청으로 vs 나누기**: 처음엔 `role-status` 하나로 제안. 컨트롤러에서 두 서비스를 이어 부르면 트랜잭션이 쪼개지고(일부만 반영), 서비스 하나로 합치면 응집도가 떨어진다는 고민(사용자) → **엔드포인트를 `bulk/role`, `bulk/status`로 나눔**. 요청 하나가 동작 하나라 부분 반영 문제가 생기지 않고 기존 서비스를 그대로 씀. 프론트 버튼도 [권한 변경]·[상태 변경]·[삭제]로.
  - 컨트롤러에서 `$transaction`을 열어 두 서비스에 `tx`를 넘기는 방법도 가능하지만 컨트롤러가 Prisma에 의존하게 됨(계층 위반). 서비스 간 트랜잭션은 전자결재(결재 승인 ↔ 연차 차감)에서 다시 결정할 문제로 남김.
  - **라우트 선언 순서**: `PATCH /users/bulk/role`은 `PATCH /users/:id/role`과 칸 수·끝 이름이 같아 `:id`가 먼저면 `"bulk"`가 id로 잡힘(`ParseIntPipe` 400). 고정 경로(`me`, `bulk`, `order`)는 `:id`보다 위에 둔다. Express 5는 경로 정규식(`:id(\\d+)`)을 지원하지 않아 선언 순서로 해결. 처음에 `bulk/role-status`는 끝 이름이 달라 충돌하지 않는다고 했는데, 단건을 `:id/agree` → `:id/role`로 바꾸면서 충돌하게 됨(설명 정정).
  - 일괄 삭제는 단건 `DELETE /users/:id`와 맞춰 `DELETE /users/bulk` + 본문 `{ ids }`. DELETE 본문은 표준상 의미가 정해져 있지 않지만 fetch·Express·Nginx에서 동작하고 `DELETE /users/me`가 이미 본문을 씀.
- **가입 승인 입사일 정책 (사용자 결정)**: 입사일은 연차 계산에 필수 → 유지.
  - 승인 API가 `joinAt`을 함께 받던 방식(A)과 "입사일 먼저 등록 → 승인"(B) 중 **B**. 일괄 승인에서 입사일을 넣을 방법이 없고, 단건·일괄을 "입사일이 등록된 회원만 승인" 규칙 하나로 설명할 수 있음. `validateTargetUsers(user, ids, { requireJoinAt: true })`로 대상 중 입사일 없는 GUEST의 이름을 메시지에 담아 400.
  - 검토에서 발견: `updateMany`의 `where: { NOT: { role: GUEST, joinAt: null } }`는 **수정 전 값**으로 판단하므로, 요청에 입사일을 같이 보내도 신규 회원이 걸러져 승인이 항상 실패하는 상태였음 → B로 확정하며 해소.
  - 승인된 회원은 정보 수정에서 입사일을 비울 수 없게(400). 이 구멍 때문에 실제로 입사일 없는 직원이 생겼었음(오전의 폼 버그).
  - "입사일은 한 번 넣으면 변경 불가"도 검토했으나, 오타를 고칠 방법이 없어 DB 직접 수정이 필요해짐 → 취소(사용자). 비우기만 금지.
- **직급·직책 삭제 시 사용 중 확인**: 직급은 회원(`Users.positionId`)·게시판 권한(`BoardAuth.positionId`), 직책은 소속(`UserDepartment.jobTitleId`)·게시판 권한(`BoardAuthJobTitle`)을 확인해 400. 부서 삭제와 같이 퇴사자는 제외. 게시판 권한은 아직 데이터가 없지만 빠뜨리지 않도록 함께 넣음.

  - 화면 순서대로 id 전체를 보내고, 서버는 트랜잭션 안에서 현재 목록과 **같은 id 집합인지**(빠짐·초과·중복 없음, `isSameIdSet`) 확인한 뒤 배열 위치를 `sortOrder`로 저장. 그 사이 추가·삭제가 있었다면 400 → 순서가 꼬이지 않음.

  - 선택지: ① 컬럼 collation 변경 마이그레이션 ② DB를 ICU 한국어 로캘로 재생성(infra-db init, 기존 DB 재생성 부담) ③ 쿼리마다 `ORDER BY name COLLATE ...`(Prisma `orderBy`에 collation 옵션이 없어 raw SQL 필요).
  - 결정: ① (사용자). 마이그레이션 `20261101102319_users_name_collation_ko`에서 `ALTER COLUMN "name" SET DATA TYPE TEXT COLLATE "ko-x-icu"`. Prisma 스키마에는 collation 문법이 없어 `migrate dev --create-only`로 빈 마이그레이션을 만들고 SQL 직접 작성.
  - 확인: 적용 후 다시 `--create-only`를 실행해 **빈 마이그레이션**이 나오는 것으로 Prisma가 이후 마이그레이션에서 collation을 되돌리지 않음을 확인(확인용 폴더는 삭제). 회원 203명 전체 DB 정렬이 `localeCompare('ko')`와 일치. 소속 정렬은 원래 메모리에서 `localeCompare('ko')`라 영향 없었음 — **DB 정렬과 메모리 정렬이 다른 기준을 쓰면 같은 화면에서 정렬 결과가 어긋날 수 있다**는 점도 함께 드러남.
  - 운영: 같은 postgres 18 공식 이미지(ICU 포함)라 `migrate deploy`로 동일 적용.
- **검증**: `UsersService.paginateUser`를 실제 DB에 직접 호출(정렬 4종 asc/desc, 소속 정렬 2페이지, 직급·직책 필터, 부서명 검색, 잘못된 `sortBy` 거부). backend tsc·frontend eslint 통과. 관리자 계정 정보가 없어 브라우저 확인은 사용자 화면으로 대체.
- **설계 포인트**: to-many 관계 정렬의 ORM 제약과 대안별 비용, 겸직 조건을 하나의 `some`에 넣는 이유, DB collation이 한글 정렬에 미치는 영향과 ICU collation, Prisma가 표현하지 못하는 DB 설정을 마이그레이션 SQL로 관리하고 drift가 없는지 확인한 방법.
