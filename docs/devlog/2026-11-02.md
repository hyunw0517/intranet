## 2026-11-02 · 게시글 목록 조회(paginate) + 좋아요·작성자 스냅샷 스키마

- **`PaginatePage` 공용 함수 (pagination.util)**: 서비스마다 반복되던 `Promise.all([findMany(...PageArgs), count])` + `PageResult`를 하나로 묶음. 반환 값은 기존과 동일(`{ data, meta }`)하고 `PageArgs`/`PageResult`는 내부 함수로 바꿈. Prisma delegate를 넘기면 select에 따른 반환 타입 추론이 깨져 조회는 콜백으로 받음. users·positions·job-titles 서비스에 적용.
- **들여쓰기 혼재 (시행착오)**: VSCode 기본 `tabSize` 4 + `detectIndentation` 때문에 CLI 생성 파일은 2칸, 직접 만든 파일은 4칸. `npm run format`(Prettier) 적용 → 103개 파일 변경(줄바꿈·공백 정리 + `autocrlf=true`로 CRLF→LF 25개)이 진행 중 작업과 섞여 **되돌림**(사용자 결정). 작업 중 파일은 VSCode 로컬 히스토리와 HEAD + 재적용으로 복원하고, Prettier로 다시 포맷해 비교(차이 0줄)해 공백 외 변화 없음을 확인. 포맷 통일은 하지 않고 기존 스타일 유지.
- **좋아요 (사용자 결정, 시행착오)**: 인트라넷이라 처음엔 빼기로 했다가 커뮤니티로도 쓰일 수 있다고 판단해 추가.

  - 좋아요 수: `_count` 집계 vs `Post.likeCount` 컬럼 → **컬럼**(좋아요순 정렬 필요). 대가로 생성·삭제와 증감을 같은 트랜잭션으로 묶어야 함(구현 예정). API는 토글 대신 `POST`/`DELETE` 분리 제안(멱등). 댓글 좋아요는 제외.

  - `updatePost`가 글 확인 없이 `where: { id }`만으로 수정 → 다른 게시판 글·남의 글도 수정 가능. `checkPost(…, 'update')`로 해결.

  - `checkPost`의 비밀글 조건이 반대(`canViewSecret`이 true일 때 403) — 볼 수 있는 사람이 막히고 못 보는 사람이 통과.
  - `update-post.dto.ts`가 `class-validator/types/...`(타입 정의 경로)에서 import → tsc는 통과하지만 실행 시 `Cannot find module`.
  - `readPost`가 `$transaction` 결과 배열을 그대로 반환.
  - `@IsDate()`만 있고 `@StringToDate()`가 없어 일정 필드가 항상 400 (JSON에는 날짜 타입이 없음 — 사용자는 "시간이 포함되면 괜찮지 않나"로 질문, 시간 유무가 아니라 값 타입이 문자열인 게 원인).

- **게시판 권한 vs 글 단위 권한 분리**:
  - `assertBoardPermission`: "이 게시판에서 무엇을 할 수 있나"(읽기 없음 404, 동작 없음 403). 반환을 `perm` → `{ board, perm }`로 넓혀 게시판 설정(`type`, `allowSecret`, `isAnonymous`, 이름)을 다시 조회하지 않게 함(이미 조회하던 select만 확장).

- **관리 권한 포함 관계 (사용자 결정, 시행착오)**: Claude는 "삭제는 `'read'`로 검사하고 `(작성자 && write) || admin`" 제안 → 사용자: 관리자라면 쓰기 권한도 있어야 함 → **`authAdmin`은 읽기·쓰기·댓글을 모두 포함**. `normalizeRule`(서버, 사용자 수정) + `normalizePerms`(관리자 화면, 포함된 권한 자동 켜고 잠금) + 데이터 마이그레이션으로 기존 규칙 보정. Prisma Studio는 기록이 남지 않고 운영에 반영되지 않아 `migrate dev --create-only` + SQL 선택. 그 결과 삭제를 `'write'`로 검사해도 게시판 관리자가 막히지 않음. 관리자도 **남의 글 수정은 불가, 삭제만 가능**(글 단위라 게시글 서비스에서 검사).
- **조회 기록 (`PostView`)**:
  - `create`는 복합 PK 중복 시 P2002 → 두 번째 조회부터 500, 그 전에 실행된 조회수 증가만 반영되는 문제.
  - 사용자 결정: 조회수는 열람마다 +1, 기록은 사람당 1회. `createMany({ skipDuplicates: true })`(PostgreSQL `ON CONFLICT DO NOTHING`)로 DB가 한 번에 판단 → 새로고침 연타에도 경쟁 상태 없음. `upsert`는 조건에 따라 조회 후 삽입으로 실행될 수 있어 제외. `create` + P2002 catch는 PostgreSQL이 트랜잭션 안의 에러를 전체 실패로 만들어 같은 트랜잭션의 조회수 증가까지 롤백됨.
  - `createMany`의 `data`는 객체 하나도 받음(배열로 감쌀 필요 없다는 사용자 지적 — Claude의 첫 설명이 틀렸음).

- **일정 (사용자 결정)**: 캘린더가 아니면 일정 필드 null, 캘린더는 시작·종료 필수·`isAllDay` 기본 false. 종일이면 **KST 기준** 00:00:00 ~ 23:59:59로 맞춘 뒤 종료 ≥ 시작 검사(같은 날 10시~9시로 온 종일 일정이 정상 처리되게). `setHours`는 서버 시간대(EC2 UTC)를 따르므로 `common/util/date.util.ts`의 `kstDayStart/kstDayEnd`로 계산. `StringToDate`는 시간대 없는 문자열과 없는 날짜(2/30 → `new Date`가 3/2로 넘김 — 테스트 중 발견)를 거부. 프론트는 날짜·시간 입력을 `+09:00`을 붙여 합쳐 보냄.
- **작성자 소속 스냅샷 (사용자 결정)**: FK(`UserDepartment`) 대신 이름 문자열 — 인사이동·소속 삭제에도 당시 값 유지(결재 스냅샷과 같은 이유). 직책 컬럼 추가. 수정 시에도 갱신하기로 해 의미가 "작성·최종 수정 당시"가 됨. 대표 소속 규칙이 organization에 있어 `getUserOrganization` 재사용(모듈 export/import, `boards → organization` 단방향). 권한 판정용 `loadUserContext`는 모양이 달라 직접 조회 유지.

관련 커밋: 문서만 (CLAUDE.md v1.30)

- **배경**: `RolesGuard`는 `@Roles`가 없으면 통과 → GUEST(승인 전)도 `@Roles` 없는 API를 직접 호출 가능. 알림·감사 로그와 애드온 컨트롤러를 새로 만들기 전에 기본값을 정리.
- **전수 확인 (Claude)**: 전체 컨트롤러에서 `@Roles`·`@IsPublic` 둘 다 없는 API는 10개이고 모두 본인 계정용(`/users/me` 조회·수정·탈퇴, 비밀번호 변경, 모든 기기 로그아웃·기기 목록·기기별 로그아웃, `/organization/me` 조회·대표 소속 변경) → GUEST가 써도 되는 API뿐, 현재 문제 없음. 게시판·글·댓글·캘린더·업로드는 `@Roles(USER)`, 관리 기능은 `@Roles(ADMIN)`.
- **결정 (사용자 결정: A안 유지)**: 기본값은 그대로 두고 **새 API마다 `@Roles(UserRole.USER)` 이상을 명시**. B안(기본값 USER 이상 + GUEST 허용 데코레이터)은 빠뜨려도 닫히는 장점이 있지만, 지금 빠진 API가 없어 현재 문제를 고치는 변경이 아니므로 채택하지 않음. 규칙은 CLAUDE.md 5.2에 기록.
- 참고: `@IsPublic()`(NestJS_SNS에서 가져옴, `eb0fcaa`)은 토큰 검사 자체를 건너뛰는 "로그인 불필요" 표시이고, GUEST 문제는 로그인 후 권한 단계라 별개.
- **설계 포인트**: 인증(`@IsPublic`/`AccessTokenGuard`)과 권한(`@Roles`/`RolesGuard`)의 단계 구분, 기본 허용 vs 기본 거부의 트레이드오프와 선택 이유.

### 이어서: 소속·직급 지정 대상이 GUEST여도 허용 (2026-11-07)

관련 커밋: 없음 (현재 동작 유지, 문서만)

- **질문**: 관리자 소속 추가·수정·삭제(`/organization/users/:userId/departments`)와 직급 지정(`/organization/users/:userId/position`)에서 대상 회원이 GUEST(승인 전)면 막을지. 현재 `checkUser`는 존재·미삭제만 확인해 GUEST에게도 지정 가능.
- **결정 (사용자 결정: 현재 그대로 허용)**: 입사일·소속·직급을 먼저 넣고 승인 한 번으로 정식 직원이 되는 흐름이 "입사일 먼저 등록 → 승인"(10/27)과 같은 순서. 막으면 승인 직후 소속이 빈 시간이 생겨 부서 게시판이 안 보임. 권한 누출은 없음 — 게시판 권한 검사가 소속과 무관하게 GUEST를 먼저 차단.
- 결재라인 결재자 후보에서 GUEST를 빼는 처리는 결재 애드온을 만들 때 그쪽에서 한다.

### 이어서: 페이지네이션 실제 요청 확인 · 부서명 `/` 허용 (2026-11-07)

관련 커밋: 없음 (확인만, 문서만)

- **페이지네이션 확인 (Plan.md "Postman 확인" 항목, 조회만)**: 관리자 토큰으로 스크립트 확인, 전부 통과.
  - 회원 기본 정렬 = 최신 가입순(응답에 `createdAt`이 없어 id 내림차순으로 확인), `sortBy=name&order=asc` 가나다순
  - 400: `sortBy=password`, `take=0`, `page=0`, `take=abc`, `take=101`, `order=up`. 참고로 `take=abc`는 `StringToNumber`가 NaN으로 바꿔 메시지 3개(최대·최소·정수)가 함께 나옴(동작 문제는 없음)
  - `deletedOnly=true`의 `meta.total` 9 = 받은 행 9, 모두 `deletedAt` 있음 (일반 목록 total 203)
  - **페이지 경계 중복·누락 없음**: `take=7`로 29쪽을 끝까지 넘겨 `sortBy=name`(같은 이름 46종, 예: 강예준×3)·`department`·`position`·`createdAt` 모두 203행·고유 id 203
  - 직급·직책 기본 정렬 `sortOrder` asc, `order=desc` 반대 순서
- **부서명에 `/` 허용 (사용자 결정, 현재 그대로)**: `toTreeList`의 `path`는 이름을 `/`로 이어 붙인 문자열이고, 프론트·백엔드 어디에서도 `path`를 `/`로 다시 나누지 않음(표시와 `?name=` 부분 일치 검색에만 사용). 문제는 표시가 애매해지는 것뿐 — 최상위 "연구/개발"과 "연구" 아래 "개발"이 같은 문자열로 보이고, "연구/개발" 검색에 둘 다 걸림. 목록은 `depth` 들여쓰기로 계층이 보이므로 데이터·권한 문제는 없어 허용으로 둠. 나중에 `path`를 나눠 쓰는 기능(빵부스러기 링크 등)이 생기면 그때 배열 반환이나 입력 금지를 다시 검토.
