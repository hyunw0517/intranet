## 2026-11-14 · 관리자 기능 권한 (SUPER_ADMIN · 기능별 관리자 · 마지막 슈퍼관리자 보호)

관련 커밋: (미커밋 — `feature/admin`) · 마이그레이션 `20261114064022_admin_permissions` (개발 DB 미적용, 테스트 DB `intranet_test`에는 e2e global setup이 적용)

- **배경 (사용자 요구)**: 지금은 `Users.role = ADMIN`이면 관리자 기능 7개(회원·조직·게시판·시설·예약·결재라인 관리자·연차)를 모두 쓴다. 슈퍼관리자가 ADMIN마다 쓸 기능을 지정하게 바꾸고 싶다 → 먼저 "지금 바꾸면 비용이 큰가"를 물음
  - Claude 추정: 컨트롤러 `@Roles(UserRole.ADMIN)` 약 50곳(15개 컨트롤러)은 기계적 치환이고, 비용의 핵심은 서비스 안의 "ADMIN이면 예외" 분기 7곳(게시판 전체 열람·예약 강제 삭제·결재 전체 문서·결재자 교체·결재라인 전체 범위)을 어느 기능에 붙일지 정하는 것. 기능이 늘수록 비싸지므로 지금이 싼 편
- **설계 결정 (사용자 결정)**
  1. 권한은 **access token에 넣는다**(`perms`). access 검증은 DB를 보지 않는 기존 원칙(5.2) 유지
  2. `UserRole`에 **`SUPER_ADMIN` 추가**(`ROLE_LEVEL` 3이라 기존 `@Roles(ADMIN)`도 통과)
  3. 저장은 **enum 배열** `Users.adminPermissions AdminPermission[]`(별도 테이블 아님)
  4. **ADMIN 승격·기능 지정은 슈퍼관리자만**. ADMIN → USER로 바꾸면 기능을 비운다
  5. **마지막 슈퍼관리자는 강등·삭제 불가**. 첫 슈퍼관리자는 seed로 만들어 두되 실행하지 않음(사용자가 직접 지정 예정)
  - 이어서 물어본 4가지 (사용자 결정)
    - 기능 지정 화면 = **회원 목록 ⋯ 메뉴의 계정 섹션**. 권한을 관리자로 고르면 체크박스가 나오고 함께 저장(별도 "관리자 권한" 메뉴 대신)
    - 서비스 분기는 **기능별 권한에 붙임**: 게시판 열람 예외 → `BOARDS`, 예약 강제 변경 → `RESERVATIONS`, 결재 전체 문서·결재자 교체·결재라인 전체 범위 → `APPROVAL_LINES`(결재 문서용 권한을 따로 두는 안, ADMIN 전체 유지 안은 고르지 않음)
    - 슈퍼관리자가 **화면에서 다른 회원을 SUPER_ADMIN으로 지정·해제** 가능
    - 권한 반영: 추가는 재발급 때, **회수·강등은 `tokenVersion` +1(다시 로그인)**
- **토큰 반영 설명 정정 (시행착오) ⭐**: 처음에 Claude가 "권한을 바꿀 때 `tokenVersion`을 올리면 재발급 시점에 반영된다"고 설명했으나 틀림. `tokenVersion`을 올리면 재발급이 **거부되어 로그아웃**된다. 재발급은 원래 DB에서 `role`을 다시 읽으므로(`updatePassword`·`increaseTokenVersion`·재발급 가드), 권한도 함께 읽기만 하면 로그아웃 없이 최대 10분 안에 반영된다 → 이 정정을 반영한 선택지로 다시 물음
  - 남은 확인 사항: "회수만 즉시 로그아웃"을 골랐지만 access token은 stateless라 **남은 유효시간(최대 10분)은 막지 못한다**. 반영 시점은 "재발급 때 반영"과 같고, 강제 로그아웃만 더해진 것 → 유지할지 사용자 확인 대기(바꾸려면 `UsersService.isAdminAccessReduced` 한 곳)
- **Claude가 정한 부분 (Claude 결정, 변경 가능 — 사용자 확인 대기)**
  - 여러 관리자 화면이 같이 쓰는 조회(부서·직급·직책 목록, 시설 분류·시설 관리자 목록)는 `@RequireAdmin()`(기능 무관, ADMIN 이상). 회원·게시판 권한·결재라인·예약 관리 화면이 이 목록을 불러서
  - `organization.controller`의 회원 직급·소속 지정 API는 회원 상세 화면에서 쓰므로 `ORGANIZATION`이 아니라 `USERS`
  - **관리자 계정 보호**: 회원 관리 기능만 가진 ADMIN은 ADMIN·SUPER_ADMIN 계정의 권한·상태 변경, 삭제·**복구**, 비밀번호 초기화, 잠금 해제 불가(`UsersService.assertCanManageAccount`, AuthService도 사용). 기본 정보 수정은 막지 않음. 회원 관리자가 슈퍼관리자를 정지·삭제하는 권한 상승 경로를 막기 위함
  - 마지막 슈퍼관리자 판단은 **슈퍼관리자 행 `FOR UPDATE` 잠금 후 집계**(재직 중 인원 기준, 강등·재직 외 상태·삭제에 모두 적용). 두 슈퍼관리자가 동시에 서로를 강등하면 각자 "상대가 남는다"고 보고 0명이 될 수 있어서
  - 첫 슈퍼관리자는 테스트 회원 seed에 섞지 않고 별도 스크립트 `prisma/seed-super-admin.ts <사번>`(이미 있으면 아무것도 안 함, `--dry-run`, 감사 로그 남김)
  - 일괄 권한 변경으로 ADMIN이 된 회원은 기능 없이 시작(기능은 회원별 ⋯ 메뉴에서 지정). `adminPermissions`를 생략하면 지금 값 유지
  - e2e 도우미 `createTestUser(prisma, ADMIN)`은 기능을 생략하면 전부 부여(기존 테스트의 "ADMIN = 모든 관리" 의미 유지)
- **구현 (사용자 요구, Claude 구현)**
  - 백엔드: `@RequireAdmin(permission?)` = `Roles(ADMIN)` + 메타데이터, `RolesGuard`가 등급 → 기능 순으로 판단. `hasAdminPermission`·`isAdminRole`·`adminPermissionWhere`(`src/auth/util/admin-permission.util.ts`). 가입 신청 알림은 슈퍼관리자 + `USERS` 기능 보유자에게. "승인된 회원" 조회(`role in [USER, ADMIN]`: 채팅·결재자·연차 부여)에 `SUPER_ADMIN` 추가. 하네스 `routeGuards.authDecorators`에 `RequireAdmin` 추가
  - 프론트: `lib/admin-permission.ts`(백엔드와 같은 규칙), `AdminPermissionGate`(기능 없으면 관리자 레이아웃은 유지하고 본문 안내), 메뉴 `permission` 필터, 관리자 홈 바로가기 필터, 권한 폼(권한 + 체크박스, 권한이 줄면 "다시 로그인" 안내), 회원 관리 ADMIN에게는 직원 승인만·관리자 계정은 안내문, 예약·결재함의 관리자 동작을 기능 기준으로

## 2026-11-14 · 게시판 삭제 규칙 변경 (게시글 있어도 경고 후 삭제 · 게시글 보관)

  - 하위 게시판이 있는 카테고리 삭제 금지, 권한 규칙 함께 삭제는 그대로 유지

  - 프론트 `board-panel.tsx`의 기존 `ConfirmDialog`(확인/취소) 문구를 `postCount > 0`이면 "게시글 N개가 있습니다 … 보관하며, 게시판을 복구하면 다시 보입니다"로 분기. 글 수는 관리자 게시판 목록 응답(`postCount`, 삭제 안 된 글)에 이미 있어 추가 API 없음
