## 2026-11-24 · 운영 구성 결정 (RDS 하나에 두 서비스 · GHCR 이미지 배포) · 백엔드 Docker 이미지 · arm64 크로스 빌드

관련 커밋: `fa6f15f`(운영 구성 문서) · 이미지 작업은 (미커밋 — `feature/deploy`)

- **운영 DB: RDS 인스턴스 하나에 SNS·인트라넷 (사용자 결정)**: 처음 계획은 인트라넷만 RDS였다. RDS는 인스턴스 단위 과금이라 DB를 하나 더 넣어도 인스턴스 비용은 그대로이고(스토리지만 데이터만큼), SNS는 학습용이라 시연 화면만 동작하면 된다 → 두 DB를 한 인스턴스(PostgreSQL 18)에 두고 SNS는 17 → 18로 올린다. 인스턴스 하나에는 메이저 버전 하나만 돌기 때문이다.
  - DB·계정 분리는 로컬과 같다(`sns`/`intranet`, 각 owner, `REVOKE ALL ... FROM PUBLIC`). "DB 하나에 계정만 둘"은 두 앱(Prisma·TypeORM)의 마이그레이션이 같은 `public` 스키마에 섞여서 하지 않는다 (Claude 제안).
  - EC2에 DB가 남지 않으므로 백업은 `pg_dump` → S3 대신 RDS 자동 백업으로 덮는다 (Claude 제안). 나중에 EC2 Docker로 옮기면 그때 `pg_dump`를 다시 정한다.
  - SNS를 배포하지 않는 안도 비교했다. 추가 AWS 비용은 거의 없고(같은 EC2·RDS·IP, 서브도메인·인증서 무료) 차이는 작업 시간이라 배포하기로 했다 (사용자 결정).
- **배포 방식: 로컬 빌드 → GHCR → 서버는 pull만 (사용자 결정)**: 서버에서 `git pull` 후 빌드하면 빌드가 앱과 메모리를 다투고 서버에 소스·빌드 도구가 필요하다 → 로컬에서 `docker buildx`로 `linux/arm64` 이미지를 만들어 레지스트리에 올리고 EC2는 `docker compose pull && up -d`만 한다.
  - 레지스트리: GHCR 공개 이미지 (사용자 결정). 공개 이미지는 저장·전송 무료, 서버에서 로그인 없이 pull, 저장소가 이미 공개라 새로 드러나는 코드가 없다. 대신 이미지에 비밀값을 넣지 않는다. ECR은 GB당 과금이라 뺐다.
  - 버전은 `main`의 태그, 이미지 태그도 같게. `release/` 브랜치는 혼자 개발이라 두지 않는다. 쿠버네티스는 서버 1대에서 Compose와 차이가 없고 EKS는 제어부 비용이 따로 들어 쓰지 않는다(AGENTS.md 17장).
  - 마이그레이션은 compose에 마이그레이션 전용 서비스를 두고 백엔드가 `depends_on: service_completed_successfully`로 기다리게 할 예정 (Claude 제안). 실패하면 새 백엔드로 넘어가지 않게 하려는 것이고, 실제 동작은 compose 단계에서 확인한다.
  - 루트 도메인은 허브 사이트 대신 Notion 포트폴리오로 301 (사용자 결정). 두 번째 인스턴스(같은 이미지, DB·`JWT_SECRET` 분리)는 데모가 안정된 뒤 추가한다 (사용자 결정) - 실제 데이터라 초기화 스크립트·백업을 확인한 뒤 받는다.
- **백엔드 Dockerfile (사용자 요구, Claude 구현)**: 멀티 스테이지 `build`(개발용 포함 `npm ci` → `prisma generate` → `nest build`) → `prod-deps`(`npm ci --omit=dev`) → `runtime`(`dist` + 운영용 `node_modules` + `prisma/` + `prisma.config.ts`, `USER node`). 자주 바뀌는 것을 아래에 두어 레이어 캐시를 살린다(`package*.json` → `prisma/` → `src/`).
  - 베이스 `node:26-trixie-slim` (사용자 결정, Claude 제안): alpine(musl)은 `bcrypt`·`sharp` 네이티브 모듈의 미리 빌드된 바이너리 문제를 피하려고 뺐다. Node는 메이저만, Debian은 코드명까지 고정해 빌드 날짜에 따라 배포판이 바뀌지 않게 했다. 서버 OS(Ubuntu)와는 무관하고 CPU 아키텍처만 맞추면 된다.
  - `prisma` CLI를 dependencies로 옮겼다 (사용자 결정): 마이그레이션 컨테이너가 같은 이미지로 `npx prisma migrate deploy`를 실행하기 때문. 전용 이미지를 따로 두는 안은 이미지 관리가 늘어 뺐다.
  - `.dockerignore` (사용자 결정): Docker는 git이 아니라 디스크를 보므로 `.gitignore`에 있는 `.env`도 그대로 컨텍스트에 들어간다. 공개 이미지에 비밀값이 들어가지 않게 `.env`·`.env.*`, Windows에서 설치한 `node_modules`(바이너리), `dist`·`src/generated`를 뺐다. 컨텍스트 2.18MB.
- **Prisma 생성 코드가 `.ts`를 import (트러블슈팅) ⭐**: 이미지는 빌드됐지만 컨테이너 시작 시 `Cannot find module './internal/class.ts'`. 로컬 `dist/generated/prisma/client.js`는 `require("./internal/class.js")`, 이미지 안은 `.ts`였다.
  - 원인: `prisma-client` 생성기는 `importFileExtension`이 없으면 tsconfig를 보고 확장자를 정하고, **tsconfig가 없으면 생성 파일 확장자(`ts`)를 그대로 쓴다**(설치된 Prisma CLI 코드에서 확인). 캐시를 위해 `COPY tsconfig*`를 `prisma generate` 아래로 내린 탓에 generate 시점에 tsconfig가 없었다.
  - 해결 (사용자 결정): generator에 `importFileExtension = "js"`를 명시. Dockerfile 복사 순서를 바꾸는 안도 있었지만 추측에 계속 의존해서, 빌드 환경과 상관없이 같은 결과가 나오게 고정하는 쪽을 골랐다. 로컬 생성 결과는 그대로(`.js`).
- **arm64 에뮬레이션에서 `prisma generate` 실패 (트러블슈팅) ⭐**: x86 PC에서 `--platform linux/arm64`로 빌드하자 `prisma generate`가 `The index definition refers to the unknown fields: , .` 같은 검증 오류를 320개 냈다. 같은 스키마가 로컬·amd64 빌드에서는 통과한다.
  - 원인(추정): QEMU 에뮬레이션 위에서 스키마 검증(WebAssembly)이 필드 이름을 빈 문자열로 읽었다. 실제 ARM 서버에서는 생기지 않을 문제로 보고 더 파지 않았다.
  - 해결 (사용자 결정, Claude 제안): `build` 단계를 `FROM --platform=$BUILDPLATFORM`으로 PC 아키텍처에서 돌린다. `build` 결과물(JS, Prisma 생성 코드)은 CPU와 무관하고, CPU별 바이너리가 있는 `prod-deps`·`runtime`만 arm64로 둔다. 무거운 단계가 에뮬레이션 없이 돌아 빌드도 빨라졌다.
- **컨테이너로 실행하며 만난 것 (Claude 설명)**: `docker run --env-file`은 따옴표를 벗기지 않아 Docker용 env 파일(`backend/.env.docker`, git 제외)을 따옴표 없이 따로 만들었다. 컨테이너 안의 `localhost`는 컨테이너 자신이라 `--network infra-db-net` + `infra-postgres18:5432`로 붙였다. Node가 PID 1이면 처리기 없는 SIGINT·SIGTERM을 무시해 `Ctrl+C`로 안 멈추고 `docker stop`은 10초 뒤 강제 종료한다 → compose에 `init: true` 예정.
- **PowerShell 빨간 출력 (시행착오, Claude)**: 빌드 로그를 보려고 `2>&1 | Select-Object`를 붙이라고 안내했는데, Docker는 빌드 로그를 stderr로 내고 Windows PowerShell 5.1은 합친 stderr를 줄마다 오류로 감싸 성공한 빌드가 실패처럼 보였다. 이후 안내와 스크립트에서는 합치지 않는다.
- **빌드 스크립트·절차서 (사용자 요구, Claude 구현)**: 매번 긴 명령을 치지 않도록 `scripts/build-backend.ps1 <태그> [-Push]`(arm64 빌드 + `bcrypt`·`sharp` 로드 확인, PowerShell 5.1용 UTF-8 BOM). 절차와 오늘 만난 증상·원인·해결 표는 [docker.md](../backend/docker.md).
- **검증**: amd64 이미지를 `infra-db-net`에 붙여 실행 → 238개 라우트 등록·`Nest application successfully started`, 없는 사번 로그인 `401`(DB 조회·throttler 헤더 확인), 이미지 안 `whoami` = `node`·`.env`·`src`·`test` 없음. arm64 이미지에서 `require('bcrypt')`·`require('sharp')` → `arm64 OK`(에뮬레이션). 스크립트 1회 실행 성공.
  - 미확인: 실제 ARM 서버에서의 실행, arm64에서 `prisma migrate deploy`(generate와 다른 엔진), GHCR push, compose의 마이그레이션 서비스 실패 시 동작.
- **설계 포인트**: 이미지·컨테이너 분리(상태는 RDS·S3에), 레이어 캐시를 고려한 복사 순서, 멀티 스테이지와 크로스 빌드(단계별 플랫폼), 공개 이미지에서 비밀값 관리(`.dockerignore` + 설정은 실행 시 주입), PID 1 신호 처리, 배포 순서(마이그레이션 → 컨테이너 교체)

### 이어서: 프론트엔드 Docker 이미지 (2026-11-24)

관련 커밋: (미커밋 — `feature/deploy`)

- **standalone 출력 (사용자 요구, Claude 구현)**: `next.config.ts`에 `output: "standalone"` → `next build`가 실행에 필요한 파일만 `.next/standalone`(`server.js` + 최소 `node_modules`)에 모은다. `.next/static`은 따로 복사한다(설치된 Next 16.3.8 문서 `output.md` 기준). Dockerfile은 `build` → `runtime` 두 단계, `node` 사용자, `HOSTNAME=0.0.0.0`(Docker가 `HOSTNAME`을 컨테이너 ID로 넣어서 고정). 인스턴스별 값이 없어 이미지 하나를 같이 쓴다(운영의 `/api`는 Nginx가 백엔드로 바로 보냄).
- **x86용 `sharp`가 arm64 이미지에 들어감 (시행착오) ⭐**: 백엔드처럼 `build` 단계를 PC 플랫폼(`$BUILDPLATFORM`)에서 돌렸더니, standalone이 이미지 최적화(`next/image`)용으로 챙긴 `sharp`가 `sharp-linux-x64` 바이너리로 들어갔다. 지금은 `next/image`를 쓰지 않아 화면은 정상(`GET /login` 200)이었지만 `/_next/image`나 이후 `next/image` 사용 시 ARM 서버에서 실패한다.
  - 선택지: A 이미지 최적화를 끄고(`images.unoptimized`) runtime에서 `sharp`를 지움 (Claude 제안) / B `build` 단계를 arm64 에뮬레이션으로 / C 그대로.
  - 결정 (사용자 결정): **B** - 빌드가 느려지더라도 나중에 `next/image`를 쓸 수 있게. 결과: 캐시 없이 442초(`npm ci` 298초 + `next build` 140초), `sharp-linux-arm64`로 바뀌고 `require('sharp')` 성공. 백엔드의 Prisma 같은 QEMU 문제는 없었다.
  - 백엔드와 판단이 갈린 이유: 백엔드 `build` 결과(`dist`, Prisma 생성 코드)는 CPU와 무관하고 CPU별 바이너리는 `prod-deps`(arm64)에서 따로 설치한다. 프론트는 standalone이 `node_modules`까지 `build` 단계에서 가져와 그 단계가 대상 플랫폼이어야 한다.
- **빌드 스크립트 (Claude 구현)**: `scripts/build-frontend.ps1 <태그> [-Push]`(arm64 빌드 + `server.js`·`.next/static`·`sharp` 확인). 절차는 [fe-21-docker.md](../frontend/fe-21-docker.md).
- **검증**: arm64(에뮬레이션)로 실행 → `Ready`·`Network: http://0.0.0.0:3000`, `GET /`·`/login` 200, 실행 사용자 `node`, 압축 크기 102MB, `--init`으로 `docker stop` 즉시 종료. frontend `typecheck`·`lint:check` 통과.
