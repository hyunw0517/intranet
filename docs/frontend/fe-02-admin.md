# FE-02. 관리자 회원·조직 관리

> 작업일: 2026-10-27 · 12월 "관리자 UI" 주간에서 회원·조직 화면만 앞당겨 구현
> 이유: 가입 승인(GUEST → USER)을 화면에서 할 수 있어야 이후 기능(게시판 등)을 USER 계정으로 테스트하기 편하고, 조직 데이터는 게시판 권한(`BoardAuth`)의 조건으로 쓰인다. 백엔드 API는 10/16~21에 이미 구현되어 있었다.

## 1. 화면과 경로

| 경로 | 화면 | 주요 동작 |
|---|---|---|
| `/admin` | 관리자 홈 | 관리 화면 바로가기 |
| `/admin/users` | 회원 목록 | 이름·사번·이메일 검색, 권한·상태 필터, 표시 개수·페이지 번호 이동, 행 끝 ⋯ 메뉴(상세보기 / 권한·상태·직급·소속 모달), 체크박스 선택 후 일괄 [권한 변경]·[상태 변경]·[삭제], [삭제된 회원] 탭에서 복구 |
| `/admin/users/[id]` | 회원 상세 | 권한·상태·직급·소속 **조회**, 기본 정보 수정(승인된 회원은 입사일 필수), 비밀번호 초기화, 회원 삭제 |
| `/admin/organization` | 조직 관리 | 탭: 부서(트리, 하위 추가·이동) / 직급 / 직책. 셋 다 손잡이를 끌어 순서 변경 → [순서 저장] |

접근 제어는 FE-01의 `admin/layout.tsx`(AuthGate → AdminGate)를 그대로 쓴다. 최종 권한 검사는 백엔드 `@Roles(ADMIN)`이다.

## 2. 사용하는 백엔드 API

| 화면 동작 | API | 비고 |
|---|---|---|
| 회원 목록 | `GET /users?page&name&empNo&email&role&status&deletedOnly` | `role`·`status` 필터, 관리자 삭제 API는 이번에 백엔드에 추가 |
| 회원 상세 | `GET /users/:id` | 삭제된 회원은 400 → 삭제 회원은 목록에서 바로 복구 |
| 가입 승인 / 권한 변경 | `PATCH /users/:id/role` `{ role }` | 입사일이 등록되지 않은 GUEST는 400 (입사일은 정보 수정에서 먼저 등록) |
| 상태 변경 | `PATCH /users/:id/status` | 재직이 아니면 다음 요청부터 차단 |
| 정보 수정 | `PATCH /users/:id` | 빈 문자열 → 서버에서 null. 승인된 회원의 입사일 비우기는 400 |
| 삭제 / 복구 | `DELETE /users/:id` / `PATCH /users/:id/delete_recovery` | 본인 대상은 서버도 400(`checkNotSelf`) |
| 비밀번호 초기화 | `PATCH /auth/reset/pw/:userId` → `{ temporaryPassword }` | 평문은 이 응답에서 한 번만 |
| 직급 지정 | `PATCH /organization/users/:userId/position` `{ positionId \| null }` | |
| 소속 추가·수정·대표·삭제 | `/organization/users/:userId/departments[/:id[/primary]]` | 첫 소속은 서버가 대표로 지정 |
| 부서 | `GET/POST/PATCH/DELETE /departments` | 트리 순서의 평평한 목록(`depth`, `path`) |
| 직급 / 직책 | `GET/POST/PATCH/DELETE /positions`, `/job-titles` | 페이지 응답, `take=100`으로 한 번에. 사용 중이면 삭제 400 |
| 순서 변경 | `PATCH /positions/order`, `/job-titles/order` `{ ids }` / `PATCH /departments/order` `{ parentDepartmentId, ids }` | 화면 순서대로 id 전체. 현재 목록과 다르면 400 |
| 선택 회원 일괄 삭제 | `DELETE /users/bulk` `{ ids }` | 단건과 같은 서비스(`ids` 배열) |
| 선택 회원 권한 일괄 변경 | `PATCH /users/bulk/role` `{ ids, role }` | 입사일 없는 GUEST가 있으면 전체 400 (메시지에 이름) |
| 선택 회원 상태 일괄 변경 | `PATCH /users/bulk/status` `{ ids, status }` | |

> 일괄 API는 한 명이라도 처리할 수 없으면(본인 포함, 삭제된 회원 등) 서버가 트랜잭션으로 전체를 거부한다. 권한과 상태를 한 요청에 섞지 않고 엔드포인트를 나눠서, 일부만 반영되는 경우가 없다.

- **회원과 조직을 `features/admin` 하나에 둔 이유**: 회원 상세의 소속 지정 화면이 부서·직책 목록 훅을 쓴다. 기능 폴더를 둘로 나누면 서로 import하게 되므로(규칙 위반), 둘 다 "관리자 기능"으로 묶었다.

## 4. 데이터 흐름 (조회 → 변경 → 갱신)

```text
UserDetailView
  └ useAdminUser(id)                    queryKey: ["admin","users","detail",id]
       └ fetchUser(id) → apiFetch → /api/users/:id → NestJS

StatusForm [변경]
  └ useAdminUserMutation(updateUserStatus)
       ├ 성공 → invalidateQueries(["admin","users"])   목록·상세를 한 번에 "다시 받아야 함"으로 표시
       │        → 화면에 떠 있는 상세는 즉시 다시 조회 → 배지·폼이 서버 값으로 바뀜
       └ mutate(..., { onSuccess: 토스트 })             화면별 후처리는 호출하는 쪽에서
```

- queryKey를 `["admin","users", ...]`처럼 같은 접두사로 묶어서, 회원을 바꾸는 요청은 모두 이 접두사 하나만 무효화하면 된다.
- 조직(부서·직급·직책)을 바꾸면 회원 목록·상세에 표시되는 부서·직급 이름도 바뀌므로 회원 캐시도 같이 무효화한다(`useOrganizationMutation`).
- **예외: 회원 삭제**. 성공하자마자 다시 조회하면 지금 보고 있는 상세가 (삭제된 회원이라) 400이 되어 오류 화면이 잠깐 보인다. 그래서 `refetchType: "none"`으로 만료 표시만 하고 목록으로 이동한다.
- **비밀번호 초기화**는 캐시에 영향이 없고 이 화면에서만 쓰므로 `useMutation`을 컴포넌트 안에 둔다(AGENTS.md 12장 규칙).

### 변경 위치를 회원 목록으로 모은 이유
- 권한·상태(가입 승인 포함)와 직급·소속 변경은 **회원 목록의 ⋯ 메뉴 모달에서만** 한다. 상세 페이지는 조회 + 기본 정보 수정 + 계정 관리만 남겼다. 같은 변경을 두 곳에서 하지 않도록 한 것이다.
- 모달은 원래 상세 페이지에 있던 구역 컴포넌트(`UserAccountSection`, `UserOrganizationSection`)를 그대로 쓴다. 그래서 컴포넌트는 `users/` 폴더에 그대로 두고, 상세 페이지에서는 import만 뺐다.
- 행마다 버튼 3개를 나열하면 표보다 버튼이 눈에 띄어서 ⋯ 메뉴(shadcn `DropdownMenu`) 하나로 줄였다.

### 목록의 선택 상태와 모달
- **선택 상태는 화면(state)에만** 둔다. 표 컴포넌트에 `key={URL 검색 파라미터}`를 줘서 페이지·필터·표시 개수가 바뀌면 선택이 초기화된다. 다른 페이지의 회원이 보이지 않는 채로 선택되어 있다가 일괄 삭제되는 일을 막기 위함이다.
- 선택 목록은 "선택한 id 중 현재 목록에 있는 회원"으로 계산한다. 일괄 삭제 후 목록이 다시 조회되면 사라진 회원은 자동으로 선택에서 빠진다.
- 헤더 체크박스: 전부 선택이면 ✓, 일부면 −(indeterminate), 없으면 빈칸. 누르면 전체 선택 ↔ 전체 해제.
- 본인 행은 체크박스를 비활성화한다(서버도 `checkNotSelf`로 거부).
- **[권한·상태]·[직급·소속] 모달은 상세 페이지 구역 컴포넌트(`UserAccountSection`, `UserOrganizationSection`)를 그대로 넣었다.** 목록 응답에는 입사일·전체 소속이 없으므로 모달이 열릴 때 상세(`useAdminUser`)를 조회한다. 같은 queryKey라 상세 페이지와 캐시를 공유하고, 변경 후 목록·모달이 함께 갱신된다.

### 드래그 정렬 (`sortable-list.tsx`)
```text
손잡이(⠿) 드래그 / 키보드(스페이스 → ↑↓ → 스페이스)
  └ SortableList.onDragEnd → arrayMove로 새 id 순서
       └ useSortDraft.setDraft(ids)          화면만 바뀜 (서버 요청 없음)
            └ 서버 순서와 다르면 changed → [취소] [순서 저장] 표시
                 └ [순서 저장] → PATCH …/order { ids } → 성공 시 캐시 갱신 후 임시 순서 비움
```
- **왜 `@dnd-kit`인가**: HTML5 기본 드래그는 터치·키보드를 지원하지 않는다. `@dnd-kit`은 포인터·키보드 센서와 스크린 리더 안내를 제공하고 React 19와 호환된다. 정렬 프리셋(`sortable`)과 transform 유틸(`utilities`)만 추가했다.
- **손잡이로만 끈다**: 행 전체를 드래그 대상으로 하면 행 안의 [수정]·[삭제] 클릭과 충돌한다. 손잡이 버튼에만 드래그 이벤트를 연결했다(`setActivatorNodeRef`). 4px 이상 움직여야 드래그로 인식해서 단순 클릭과 구분한다.
- **저장 전 순서는 화면 상태(draft)**: 서버 캐시를 직접 바꾸지 않는다. 그래서 [취소]는 draft만 버리면 된다. 저장 전에 항목이 추가·삭제·이동되어 id 구성이 달라지면 draft를 버리지 않고 지금 서버 목록에 맞춘다(`mergeDraft`: 남은 항목은 드래그 순서 유지, 사라진 항목은 제외, 새 항목은 서버 순서대로 끝에). 결과가 항상 서버 목록과 id 구성이 같아 순서 저장 API의 전체 일치 검사를 통과한다. (2026-11-14 변경, 이전에는 구성이 달라지면 draft를 버렸음)
- **저장 후 깜빡임 없음**: 공용 mutation 훅의 `onSuccess`가 `invalidateQueries`를 기다린 뒤 끝나고, 그다음에 화면의 `onSuccess`(draft 비우기)가 실행된다. 새 서버 순서가 이미 들어온 뒤라 예전 순서로 잠깐 돌아가지 않는다.
- **부서는 형제 그룹마다 따로**: 부서마다 자기 하위 부서 목록(`DepartmentGroup`)을 별도의 정렬 목록으로 그린다. 그래서 다른 상위 부서 아래로는 놓을 수 없고(상위 이동은 [수정]에서), 부서를 끌면 하위 부서가 함께 움직인다. 여러 그룹을 바꿨다면 저장 시 그룹마다 요청을 하나씩 보낸다.
- **직급 순서의 의미**: 위쪽일수록 높은 직급이고, 게시판 권한의 "이 직급 이상" 판단에 그대로 쓰인다. 화면 설명에 적어 두었다.

### 가입 승인과 입사일
- 입사일은 연차 계산에 필요해서, **승인 대기 회원은 입사일이 먼저 등록되어 있어야 승인된다.** 승인 API는 입사일을 받지 않는다(단건·일괄 모두 같은 규칙).
- 입사일이 없으면 승인 모달에 안내와 회원 상세 링크를 보여 주고 [가입 승인]을 비활성화한다. 일괄 권한 변경에서는 목록 응답에 입사일이 없어 미리 알 수 없으므로, 서버가 돌려주는 "입사일이 등록되지 않은 승인 대기 회원이 있습니다: 이름" 메시지를 모달에 그대로 보여 준다.
- 승인된 회원은 정보 수정에서 입사일을 비울 수 없다. 프론트는 필수 표시·미리 검사, 서버도 400.

### 목록 필터를 URL에 둔 이유
`/admin/users?role=GUEST&field=name&q=홍&size=10` 처럼 필터·페이지·표시 개수를 URL 검색 파라미터에 둔다. 상세로 들어갔다가 뒤로 가기나 새로고침을 해도 목록 조건이 유지되고, 그 조건이 그대로 queryKey가 된다. `useSearchParams`를 쓰므로 페이지에서 `<Suspense>`로 감싼다(FE-01의 `(auth)` 레이아웃과 같은 이유).

## 5. Server / Client Component 구분

- `app/admin/**/page.tsx`는 Server Component다. 제목(`PageHeader`)·메타데이터와, 상세 페이지의 id 숫자 확인(`notFound()`)만 한다.
- 데이터 조회는 모두 Client Component에서 한다. access token이 브라우저 메모리에만 있어서 서버에서는 인증된 요청을 보낼 수 없기 때문이다(FE-01과 같은 구조).
- Next 16에서 동적 경로의 `params`는 Promise라서 `await params`로 꺼낸다.

## 6. 화면 구현 시 주의했던 점

| 문제 | 원인 | 처리 |
|---|---|---|
| 가입 승인 후 정보를 저장하면 입사일이 지워짐 | 기본 정보 폼이 승인 전 값(입사일 없음)을 계속 들고 있다가 저장 시 빈 값으로 덮어씀 | 폼에 서버 값으로 만든 `key`를 줘서, 서버 값이 바뀌면 폼을 다시 마운트 |
| 390px에서 회원 목록 페이지 전체가 가로로 넘침 | 표 바깥 `div`가 grid 항목이라 기본 `min-width: auto` → 표 너비만큼 늘어남 | 그 `div`에 `min-w-0`, 표는 자기 컨테이너 안에서 가로 스크롤 |
| 확인 모달이 요청 중에 닫힘 | shadcn `AlertDialogAction`은 누르면 바로 닫힘 | 일반 `Button`으로 두고 성공 시 호출한 쪽에서 닫음 (`ConfirmDialog`) |
| 회원이 적으면 페이지 이동 UI가 안 보여 페이지네이션 동작을 확인할 수 없음 | 백엔드 기본 `take`가 20이고, 1페이지뿐이면 `PaginationBar`를 숨겼음 | 1페이지여도 항상 표시 + 표시 개수(10/20/50, URL `size`) 선택 추가. `?size=2`로 확인 가능 |
| 메뉴 항목에서 모달을 열면 이후 화면 클릭이 막힐 수 있음 | Radix DropdownMenu(모달 모드)와 Dialog가 각각 포커스·포인터 잠금을 걸고 해제 순서가 꼬임 | 메뉴를 `modal={false}`로 두어 잠금은 Dialog만 건다 |
| 직급·직책 삭제 실패 시 확인 모달이 열린 채 남음 | 실패 시 토스트만 띄우고 모달은 닫지 않았음 (부서 패널은 닫음) | 사용 중이면 다시 눌러도 같은 결과이므로 부서 패널처럼 닫고 메시지만 표시 |
| `DndContext`의 접근성 id가 서버·클라이언트에서 달라질 수 있음 | 내부 카운터로 id를 만들어 SSR 후 hydration 시 불일치 경고 가능 | `useId()`로 만든 값을 `DndContext id`로 넘김 |
| Select에 "전체"·"없음" 값을 넣을 수 없음 | Radix Select는 빈 문자열 값을 쓸 수 없음 | `"all"`, `"none"`, `"root"` 같은 별도 값 사용 |

- **부서 이동 시 상위 부서 후보**: 자기 자신과 하위 부서는 고를 수 없게 뺀다. 서버 응답이 트리 순서(전위 순회)라서 "자기 바로 뒤에서 depth가 더 깊은 항목이 이어지는 동안"이 하위 부서다. 최종 검사(순환 참조)는 서버가 한다. 프론트는 편의, 백엔드는 무결성.
- **본인 계정**: 권한·상태 변경과 삭제는 서버가 막지만 화면에서도 미리 비활성화한다.

- 390 / 768 / 1440px: 페이지 가로 넘침 0 (회원 표만 표 안에서 가로 스크롤).

- (추가) ⋯ 메뉴: 상세보기·권한·상태·직급·소속 표시, 메뉴 → 모달 → 닫은 뒤에도 클릭 정상(`body` pointer-events auto), 상세 페이지는 조회 구역만 표시(선택 상자 0개).

## 8. 설계 포인트
- **"수정 후 목록이 어떻게 최신이 되나요?"** → queryKey를 `["admin","users", ...]`로 묶고, 변경 성공 시 접두사로 무효화한다. 화면에 떠 있는 쿼리만 바로 다시 받고, 안 보이는 목록은 다음에 볼 때 받는다.
- **"필터를 왜 URL에 두었나요?"** → 뒤로 가기·새로고침·링크 공유 시 상태 유지. URL이 곧 queryKey가 된다.
- **"프론트에서 막는데 백엔드에서도 막나요?"** → 메뉴 숨김·버튼 비활성은 편의이고, 권한(`@Roles(ADMIN)`)·본인 대상 금지(`checkNotSelf`)·부서 순환 참조는 백엔드가 최종 검사한다.
- **"순서 변경은 어떻게 저장하나요?"** → 드래그 결과는 화면 상태(draft)에만 두고, [순서 저장] 때 화면 순서대로 id 전체를 보낸다. 서버는 현재 목록과 정확히 같은 id 집합인지 확인한 뒤 트랜잭션으로 `sortOrder`를 0, 1, 2…로 다시 매긴다. 그 사이 누가 추가·삭제했다면 400이라 순서가 꼬이지 않는다.
- **"일괄 처리 중 한 명이 실패하면요?"** → 서버가 트랜잭션으로 전체를 되돌리고, 실패 이유(예: 입사일 없는 승인 대기 회원 이름)를 메시지로 준다. 권한과 상태를 한 요청에 섞지 않아 일부만 반영되는 상황 자체를 만들지 않았다.
- **"체크한 상태로 다른 페이지로 가면요?"** → 선택은 현재 페이지에서만 유지되고 URL이 바뀌면 초기화된다. 보이지 않는 회원이 일괄 처리되는 사고를 막기 위한 선택이다.
- **"임시 비밀번호는 어디에 저장되나요?"** → 서버는 해시만 저장하고 평문은 응답으로 한 번만 준다. 프론트도 상태에만 잠깐 두고 모달을 닫으면 버린다. (PHP 시절의 `password_hash`와 같은 원리)

## 추가: 입사일 변경 시 연차 재계산 안내 (2026-11-12)

휴가 옵션(`leaves`)이 켜져 있을 때만, 관리자 회원 상세에서 승인된 회원의 입사일을 바꿔 저장하면 안내 창을 띄운다. 연차 부여는 입사일로 계산해 **저장해 둔 값**이라, 입사일을 바꿔도 다음 월 배치(매월 1일 00시) 전까지는 그대로이기 때문이다.

| 파일 | 역할 |
|---|---|
| `src/services/api/leave-grants.ts` | 백엔드 `leave-grants.controller` 대응. 지금은 `recalculateLeaveGrants`(POST `/approvals/leaves/grants/recalculate`)만 |
| `src/features/admin/components/users/join-at-leave-dialog.tsx` | 안내 창. 공용 `ConfirmDialog` 재사용, [지금 재계산]을 누르면 전체 회원의 올해 계산값을 다시 계산(관리자 조정값 유지) |
| `user-info-form.tsx` | 저장 성공 후 입사일이 바뀌었으면 `onJoinAtChanged()` 호출 |

- 안내 창 상태를 폼이 아니라 **부모**가 가지는 이유: 폼은 서버 값으로 `key`를 받아, 저장 후 값이 바뀌면 다시 마운트된다. 폼 안에 두면 열리자마자 사라진다.
- 휴가가 꺼져 있으면 재계산 API가 서버에 없으므로(404) 안내 창도 렌더링하지 않는다. `useEnabledAddons`는 사이드바와 같은 캐시를 쓰므로 요청이 늘지 않는다.
