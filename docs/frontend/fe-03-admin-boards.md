# FE-03. 관리자 게시판·게시판 권한 관리

> 작업일: 2026-10-31 · 백엔드 `boards` 모듈 중 완료된 부분(관리자 게시판 CRUD, 게시판 권한 규칙 CRUD)만 화면으로 연결
> 이유: 게시글·댓글 백엔드를 만들기 전에 관리자가 부서별 권한 규칙을 실제로 설정해 두기 위함. 직원용 게시판 메뉴·게시글 화면은 백엔드(권한 판정, 게시글 API) 이후 작업.

## 1. 화면과 경로

| 경로 | 화면 | 주요 동작 |
|---|---|---|
| `/admin/boards` | 게시판 관리 | 카테고리 → 게시판 트리, 게시판 추가(최상위 / 카테고리 행의 [게시판 추가]), 수정(타입·상위 카테고리·이름·설명·옵션), 삭제, 같은 상위 안에서 드래그 정렬 → [순서 저장] |
| `/admin/boards/[id]/auths` | 게시판 권한 | 규칙 목록(대상 조건 문장 + 권한 배지), 규칙 추가·수정(부서·하위 포함·최소 직급·허용 직책, 읽기·글쓰기·댓글·관리), 삭제 |

- 각 게시판 행에 **타입 배지, 게시글 수, 권한 상태**를 표시한다. 규칙이 0개면 `관리자만 열람` 배지 (docs/design/features.md 5.3의 기본 거부 정책을 관리자가 놓치지 않게).
- 카테고리 행에는 [권한 설정]이 없다. 카테고리는 규칙을 둘 수 없고(서버 400), 하위 게시판 중 하나라도 볼 수 있으면 표시된다.
- 관리자 메뉴와 관리자 홈에 "게시판 관리"를 추가했다.

## 2. 사용하는 백엔드 API

| 화면 동작 | API | 비고 |
|---|---|---|
| 게시판 트리 | `GET /boards/admin` | 트리 순서의 평평한 목록(`depth`, `path`, `postCount`, `authCount`). 페이지네이션 없음 |
| 게시판 추가 / 수정 | `POST /boards`, `PATCH /boards/:id` | 계층 규칙(상위는 카테고리만, 카테고리는 최상위만)·이름 중복·타입 변경 제한은 서버 검사, 메시지를 모달에 표시 |
| 게시판 삭제 | `DELETE /boards/:id` | 하위 게시판이 있는 카테고리는 400. 게시글이 있으면 확인 창에서 글 수와 함께 경고 후 삭제(게시글은 보관, 2026-11-14). 삭제 시 권한 규칙도 서버에서 함께 삭제 |
| 순서 변경 | `PATCH /boards/order` `{ parentBoardId, ids }` | **현재 백엔드 라우트 선언 순서 문제로 400** (7장) |
| 규칙 목록 | `GET /boards/:boardId/auths` | 부서·직급 이름, 직책 목록 포함 |
| 규칙 추가 / 수정 / 삭제 | `POST`, `PATCH /boards/:boardId/auths/:id`, `DELETE …/:id` | 수정 시 `jobTitleIds`는 전체 교체 |

## 3. 파일 구조와 역할

```text
src/
├── app/admin/boards/
│   ├── page.tsx                       게시판 관리 (Server: 제목만)
│   └── [id]/auths/page.tsx            게시판 권한 (Server: id 숫자 확인만, notFound)
│
├── services/api/                      ← 백엔드 컨트롤러와 1:1
│   ├── boards.ts                      boards.controller (목록·추가·수정·삭제·순서)
│   └── board-auths.ts                 board-auth.controller (규칙 CRUD)
│
├── types/board.ts                     BoardType·라벨, AdminBoard, BoardAuthRule (직원용 게시판에서도 쓸 예정)
│
└── features/admin/
    ├── hooks/
    │   ├── use-admin-boards.ts        adminBoardKeys + 게시판 목록·규칙 조회 훅 + 변경 공용 mutation
    │   └── use-organization.ts        (수정) 조직 변경 시 게시판 캐시도 무효화
    └── components/
        ├── boards/
        │   ├── board-panel.tsx        트리 목록 + 추가·수정·삭제 + 드래그 정렬
        │   ├── board-form-dialog.tsx  게시판 추가·수정 모달
        │   ├── board-auth-view.tsx    권한 규칙 목록 화면
        │   ├── board-auth-dialog.tsx  규칙 추가·수정 모달 (조직 목록 훅 사용)
        │   └── board-auth-rule.tsx    규칙 → "대상" 문장, 권한 배지 (목록·미리보기 공용)
        └── organization/sortable-list.tsx   (수정) 트리용 그룹별 정렬 훅을 부서 패널에서 옮겨 와 공용화
```

- **게시판을 `features/admin`에 둔 이유**: 규칙 모달이 부서·직급·직책 목록 훅(`use-organization`)을 쓴다. 기능 폴더를 따로 만들면 서로 import하게 되므로 FE-02와 같은 이유로 관리자 기능에 묶었다. 직원용 게시판 화면은 이후 `features/board/`로 따로 만든다.
- **트리 정렬 훅 공용화**: 부서 패널 안에 있던 "상위별 저장 전 순서" 훅(`useGroupedSortDrafts`)과 `groupByParent`를 `sortable-list.tsx`로 옮겨 부서·게시판이 같이 쓴다. 로직은 그대로이고 위치만 바뀌었다(부서 화면 동작 동일).
- **단건 조회 API가 없는 게시판 정보**: 권한 화면 상단의 게시판 이름·타입은 `GET /boards/admin` 목록(같은 queryKey 캐시)에서 찾는다. 게시판 관리에서 들어오면 추가 요청이 없다.

## 4. 데이터 흐름

```text
BoardAuthView
  ├ useAdminBoards()          ["admin","boards","list"]        → 게시판 이름·타입 (없거나 카테고리면 안내만)
  └ useBoardAuths(boardId)    ["admin","boards","auths",id]    → 카테고리가 아닐 때만 조회 (enabled)

규칙 추가·수정·삭제 / 게시판 변경
  └ useAdminBoardMutation → invalidate ["admin","boards"]       → 규칙 목록 + 게시판 목록의 authCount 함께 갱신

부서·직급·직책 변경 (조직 관리)
  └ useOrganizationMutation → invalidate 조직 + 회원 + ["admin","boards"]   (규칙에 부서·직급·직책 이름이 표시되므로)
```

## 5. 규칙 모달의 입력 규칙 (서버 정규화와 동일)

| 화면 | 이유 |
|---|---|
| 부서를 고르지 않으면 [하위 부서 포함] 비활성 | 서버도 부서가 없으면 `includeSubDepartment=false`로 저장 |
| 글쓰기·댓글·관리 중 하나라도 켜면 읽기가 켜지고 잠김 | 서버도 읽기를 함께 켬. 화면에서 미리 같은 상태를 보여 줘 "저장했더니 값이 바뀌는" 혼란을 막음 |
| 권한이 하나도 없으면 제출 차단 | 서버도 400 ("최소 하나의 권한을 선택하세요.") |
| 하단 "대상:" 미리보기 | 조건 조합을 문장으로 확인 (조건이 모두 없으면 "전체 회원") |
| 새 규칙 기본값: 읽기·댓글 켜짐 | 서버 DTO 기본값과 동일 |

- 직급 선택지는 `회장 이상`처럼 표시한다. "이 직급 이상"의 기준은 조직 관리의 직급 순서(위쪽이 높음)다.
- 판정 방식(사용자 결정): 규칙 안의 조건은 AND, 여러 규칙에 해당하면 권한별 OR(합집합). "빼기"(거부 규칙)는 두지 않고 허용 대상만 쌓는다. 화면 안내문에도 같은 내용을 적었다.
- 권한 포함 관계(11/3 사용자 결정): **게시판 관리 → 읽기·글쓰기·댓글 모두 포함**, 글쓰기·댓글 → 읽기 포함. 규칙 모달은 `normalizePerms`로 포함된 권한을 자동으로 켜고 잠근다(끄려면 상위 권한을 먼저 끔). 서버 `normalizeRule`도 같은 규칙으로 맞춰야 한다. 관리 권한이 있어도 남의 글 **수정**은 불가, 삭제만 가능(게시글 서비스에서 검사).
- 규칙 모달은 조직 데이터가 모두 로딩된 뒤 폼을 그린다. Select 값이 목록에 없는 상태로 그려지지 않게 하기 위함이다.

## 6. 게시판 모달

- 타입이 카테고리면 상위 선택을 잠그고 최상위로 고정, 게시판 옵션(익명·비밀글)을 숨긴다.
- 앨범 타입도 선택할 수 있다(사용자 결정). 썸네일·그리드 목록은 파일 기능 이후 구현 예정이지만, 게시판과 권한 규칙을 미리 만들어 두면 기능이 생겼을 때 그대로 쓰인다. 그 전까지는 일반 게시판과 같이 동작한다.
- **익명·비밀글 옵션 (해결, 2026-11-04)**: 처음에는 목록 응답(`GET /boards/admin`)에 `isAnonymous`·`allowSecret`이 없었다. 모르는 값을 `false`로 보내면 기존 설정을 덮어쓰므로, 수정 모달에서는 체크박스를 비활성화하고 요청에서 뺐다(`optionsKnown`). 백엔드 select에 두 필드가 추가되어 이 우회 처리를 지우고 항상 현재 값을 보여 준다.

## 6-1. 트리 접기·펼치기 (부서·게시판 공용)

`features/admin/components/organization/tree-collapse.tsx`
- `useCollapsedIds()`: 접힌 항목 id를 `Set`으로 보관. **메모리(useState)만 사용**한다. 이미 받은 목록을 보여 줄지 말지만 정하는 화면 상태라 서버 요청이 전혀 없고, 페이지를 다시 열면 전부 펼친 상태로 시작한다(사용자 결정: localStorage 유지는 불필요).
- `CollapseToggle`: 이름 **왼쪽**의 ▸/▾ 버튼 (`aria-expanded`, "OO 하위 접기/펼치기"). 하위가 없는 항목은 같은 너비의 빈 칸을 둬서 이름 위치를 맞춘다.
- `CollapseAllBar`: 목록 위 [모두 펼치기]·[모두 접기]. "모두 접기"는 하위가 있는 항목 id 전체를 Set에 넣는다.
- 접힌 항목은 **하위 그룹 컴포넌트를 그리지 않는다**(`{!collapsed && <DepartmentGroup …/>}`). 재귀 구조라 이 조건 하나로 끝난다.
- 드래그 정렬과 독립: 저장 전 순서(`useGroupedSortDrafts`)는 별도 상태라 접었다 펼쳐도 유지되고, 접힌 상위를 끌면 숨은 하위도 함께 움직인다.
- 접힌 상위 아래로 추가·이동에 성공하면 그 상위를 자동으로 펼친다(`collapse.expand(parentId)`). 새 항목이 안 보이는 혼란을 막기 위함이다.

## 8. 설계 포인트
- **"권한 규칙이 없는 게시판은?"** → 기본 거부. 목록에서 `관리자만 열람`으로 드러내 설정 누락을 눈으로 확인할 수 있게 했다.
- **"화면에서 읽기를 강제로 켜는 건 백엔드와 중복 아닌가요?"** → 최종 정규화는 서버가 한다. 화면은 저장 결과와 같은 상태를 미리 보여 주는 편의다. 프론트는 우회 가능하므로 서버 규칙을 대체하지 않는다.
- **"모르는 값을 보내지 않은 이유는?"** → PATCH는 보낸 필드만 바꾼다. 응답에 없는 값을 기본값으로 채워 보내면 기존 설정을 조용히 덮어쓰는 버그가 된다.
- **"부서 이름을 바꾸면 권한 화면은?"** → 조직 변경 mutation이 게시판 캐시까지 무효화한다. queryKey 접두사(`["admin","boards"]`)로 묶었기 때문에 한 줄로 처리된다.
