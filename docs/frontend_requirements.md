# Intranet 프론트엔드 공통 요구사항

> 목적: Claude Code가 Next.js 프론트엔드를 구현할 때 **항상 준수해야 하는 공통 규칙**을 정의한다.
>
> 이 문서는 페이지별 기능 명세서나 개발 일정표가 아니다. **개별 기능, 화면별 표시 데이터, 사용자 동작, 구현 우선순위는 매 작업 요청에서 별도로 지정한다.**
>
> 작업 전 `AGENTS.md`, 이 문서 및 현재 소스 코드를 확인한다. 문서 간 지시가 충돌하거나 실제 구현과 다르면 임의로 해석하지 말고 충돌 내용을 보고한다.

## 1. 프로젝트 범위 및 기술 스택

- 서비스: 사내 인트라넷 (직원용 및 관리자용 UI)
- 프론트엔드: **Next.js App Router + TypeScript**
- 스타일: **Tailwind CSS + shadcn/ui**
- 아이콘: **Lucide React**
- 백엔드: 현재 프로젝트의 **NestJS API**
- 작업 범위: `frontend/` 내 UI, 라우팅, 상태 처리, API 연동
- **금지:** 별도 승인 없이 NestJS API, Prisma 스키마, DB, Docker 및 인프라 구성 수정
- 프레임워크 및 라이브러리의 실제 버전·설정은 프로젝트 파일을 확인한 뒤 따른다.

## 2. 디자인 시스템

### 2.1 전체 방향

- **Linear + Attio**를 참고한 차분하고 세련된 **미니멀 B2B SaaS** 스타일을 사용한다.
- **Notion 같은 문서 트리 중심의 UI**를 그대로 모방하지 않는다. 내비게이션은 문서가 아닌 **업무 기능 중심**으로 구성한다.
- LumApps처럼 강한 강조색을 여러 개 남발하지 않는다.
- 여백, 타이포그래피, 얇은 구분선으로 정보의 위계를 표현한다.
- 그라데이션, 장식적인 일러스트, 과도한 그림자·애니메이션·강조 배지는 지양한다.
- 기존 컴포넌트 및 디자인 토큰을 우선 재사용하고, 동일한 요소는 모든 페이지에서 일관되게 표현한다.

### 2.2 폰트

- 기본 폰트: **Pretendard Variable**
- 기본 UI 글자 크기: **14px**, 본문은 문맥에 따라 **14~16px**
- 페이지 제목: 보통 **24~28px** (좁은 화면에서는 적절히 조정)
- 주 사용 두께: **400 / 500 / 600**
- 한글 중심의 가독성을 우선하며, 불필요하게 굵은 글자와 장식체를 사용하지 않는다.

### 2.3 색상 및 테마

| 요소 | Light | Dark |
|---|---|---|
| 메인 배경 | `#FFFFFF` | `#111318` |
| 사이드바/보조 배경 | `#F7F8FA` | `#171A20` |
| 카드/패널 배경 | `#FFFFFF` | `#1B1E25` |
| 기본 텍스트 | `#18181B` | `#F4F4F5` |
| 보조 텍스트 | `#64748B` | `#A1A1AA` |
| 경계선 | `#E5E7EB` | `#30343D` |
| 포인트 색상 | `#5268A8` | `#91A7EB` |

- 위 색상은 **초기 기준 팔레트**이다. 실제 컴포넌트에는 하드코딩을 반복하지 말고 **공통 CSS 변수/시맨틱 토큰**으로 적용한다.
- 강조색은 주요 액션, 링크, 선택 상태에 한정하고 성공·주의·오류 색상은 상태 의미를 전달할 때만 사용한다.
- 테마 선택: **Light / Dark / System**. 최초 기본값은 **Light**로 설정한다.
- `next-themes`를 이용해 선택 상태를 유지하며, 시스템 테마 선택 시 OS 설정을 반영한다.
- 직원용 및 관리자용 화면에 동일한 테마 시스템을 적용한다.
- 최초 렌더링에서 테마 불일치, 깜빡임 및 hydration 오류가 발생하지 않도록 구성한다.

## 3. 공통 레이아웃 및 내비게이션

- **PC:** 좌측 사이드바 + 상단 헤더 + 메인 콘텐츠의 기본 구조를 사용한다.
- 사이드바는 **shadcn/ui Sidebar-07의 아이콘 축소/확장 패턴**을 참고한다. 동일한 외관의 복제는 요구하지 않는다.
- 활성 메뉴가 명확해야 하며, 필요 시 하위 메뉴의 펼침 상태를 구분한다.
- 헤더에는 페이지 맥락과 사용자 메뉴 등을 배치하되, **구현되지 않은 기능을 동작하는 것처럼 표시하지 않는다.**
- **모바일:** 사이드바를 기본적으로 접고 햄버거 버튼으로 Sheet/Drawer를 연다.
- 직원용과 관리자용 레이아웃은 구분하되 **공통 컴포넌트와 디자인 토큰**을 재사용한다.
- 메뉴 항목, 정렬 순서, 해당 기능의 세부 화면은 **매 작업 프롬프트 및 실제 백엔드 기능에 따라 결정**한다.

### 라우팅 기본 원칙

- Next.js **App Router**를 사용한다.
- 인증 화면은 `(auth)` Route Group, 직원용 화면은 `(main)` Route Group을 기준으로 구성한다.
- 관리자 화면은 **동일한 Next.js 앱의 `/admin` 하위 경로**를 사용한다. 관리자 전용 서버·도메인을 추가하지 않는다.
- `(auth)`, `(main)`처럼 괄호로 감싼 Route Group 명칭은 실제 URL에 포함되지 않는다.
- 구체적인 경로는 `AGENTS.md`의 라우팅 설계 및 기존 소스를 우선 확인한다. 이 문서에서 새로운 페이지 경로를 임의로 확정하지 않는다.
- 페이지 라우팅과 UI 권한 제한은 서버의 API 권한 검증을 대체하지 않는다.

## 4. 반응형 및 접근성

- **데스크톱 우선**으로 설계하지만, 직원용 핵심 업무 화면은 **모바일과 태블릿에 반응형으로 대응**한다.
- 카드·목록은 폭에 맞게 열 수를 조정한다. 테이블은 데이터 성격에 맞춰 카드 전환 또는 명시적 가로 스크롤을 선택한다.
- 모바일에서 예기치 않은 가로 넘침, 버튼 겹침, 접근 불가능한 UI가 없어야 한다.
- 입력창·버튼·팝업·날짜 선택기는 터치 조작과 키보드 조작을 고려한다.
- 관리자용 복잡한 관리·편집 화면은 PC 사용성을 우선하되 모바일에서 화면이 깨지지 않게 한다.
- 최소한 **390px(모바일), 768px(태블릿), 1440px(데스크톱)** 너비에서 확인한다.
- 접근 가능한 라벨, 포커스 표시, 적절한 명도 대비, 의미에 맞는 HTML 요소를 사용한다.

## 5. 컴포넌트 및 코딩 원칙

- shadcn/ui 컴포넌트(Button, Input, Dialog, Sheet, DropdownMenu, Table, Tabs, Badge, Skeleton 등)를 가능한 한 재사용한다.
- 동일 패턴은 공통 컴포넌트로 추출하되, 불필요한 추상화는 지양한다.
- 기존 `frontend/` 구조와 `AGENTS.md`에 정의된 아키텍처를 우선한다.
- TypeScript의 타입을 명확히 정의하고 무분별한 `any` 사용을 피한다.
- API 호출 함수는 `services/api/<도메인>.ts`(백엔드 컨트롤러와 1:1)에, 화면·훅은 `features/<기능>/`에 둔다. 기능 폴더끼리 API를 서로 import하지 않는다. (AGENTS.md 12장)
- 조회(`useQuery`)는 처음부터 `features/<기능>/hooks/`에 훅으로 만들고 queryKey를 기능별 객체로 한 곳에서 관리한다. 변경(`useMutation`)은 한 화면에서만 쓰면 컴포넌트 안에 두고, 여러 화면에서 쓰거나 목록 갱신이 필요하면 같은 훅 파일로 옮긴다.
- 기능 폴더 안에서 화면(`components/`)과 접근 제어(`guards/`)를 섞지 않는다.
- 폼에는 명확한 라벨, 필수값 검증, 오류 메시지, 제출 중 중복 요청 방지를 적용한다.
- 데이터 화면은 필요에 따라 로딩·빈 데이터·오류 상태를 구현하고, 생성/수정/삭제 결과를 적절히 피드백한다.
- 라이브러리 추가는 기존 의존성으로 해결 가능한지 먼저 확인하고, 필요 이유를 설명한다.
- 날짜·시간·수치 표기는 동일한 규칙으로 유지하며, 세부 포맷은 기존 프로젝트 설정과 도메인 요구사항을 따른다.

## 6. NestJS API 및 인증 연동 규칙

- **기존 NestJS 구현을 Source of Truth로 취급한다.** 연동 전 해당 모듈의 Controller, DTO, 응답 타입, 인증·권한 정책을 확인한다.
- API 주소, HTTP 메서드, 요청/응답 필드, 사용자 역할, 비즈니스 규칙을 추측해서 확정하지 않는다.
- 인증 토큰의 저장·전송·갱신·만료 처리 방식은 백엔드 정책을 확인하고 적용한다.
- 사용자별 메뉴 노출은 백엔드 권한 정책과 일치하게 구성한다. **프론트의 숨김 처리만으로 보안을 보장하지 않는다.**
- 서버가 반환하는 인가 실패·인증 만료·검증 오류 등을 구분하여 적절한 UI를 제공한다.
- 실제 API가 없을 경우 **임의로 백엔드를 수정하지 않는다.** 차단되는 기능과 필요한 API를 보고한다.
- Mock 데이터는 해당 작업에서 명시적으로 허용한 경우에만 사용하며 실제 데이터와 혼동되지 않게 표시한다.
- API 클라이언트, 캐시 라이브러리 및 환경변수 이름은 기존 구성부터 확인하고, 필요 시 공통화한다.

## 7. Claude Code 작업 방식

1. 작업 시작 전 **`AGENTS.md` → 이 문서 → 기존 `frontend/` 구현 → 관련 NestJS API** 순서로 확인한다.
2. 매번 전달받은 **이번 작업의 기능·화면·제약 조건**을 현재 작업 범위로 삼는다. 이 문서를 근거로 전체 기능을 한꺼번에 구현하지 않는다.
3. 화면 세부 배치, 컴포넌트 구조, 로딩 상태 등 **명시되지 않은 일반적인 UI 결정은 공통 규칙 범위 안에서 자율적으로 수행**한다.
4. [R-PROC-01] 권한, 승인 조건, 데이터 구조, 업무 규칙처럼 **비즈니스 동작에 영향을 주는 결정**은 임의로 확정하지 않는다. 불명확하면 질문하거나 확인이 필요한 항목으로 보고한다.
5. 관련 없는 파일을 광범위하게 수정하지 않는다. 공통 코드 변경이 필요하다면 영향 범위를 확인한다.
6. [R-FE-01] **백엔드/DB/인프라 파일은 수정하지 않고** 필요한 변경을 별도로 제안한다.
7. 작업 후 **변경 파일, 구현 기능, 실제 API 연동 여부, 검증 결과, 미완료 또는 확인 필요 사항**을 간결하게 보고한다.
8. 이 프로젝트는 취업용 포트폴리오이며, 백엔드 개발자가 프론트엔드까지 관리하며 학습해야 한다. 따라서 구현 후 **전체 구조와 각 파일·계층의 역할 등 부가 설명을 `docs/frontend/`에 작업별 파일로 기록**한다.
   - 파일명: `00-setup.md`, `fe-01-auth.md`처럼 작업 순서·ID를 접두사로 붙인다.
   - 내용: 이번 작업으로 생긴 구조(폴더·파일과 역할), 요청이 흐르는 경로, Server/Client Component 구분 이유, 설계 포인트(왜 이렇게 했나).
   - `docs/devlog/`(결정 이유·시행착오, Notion 정리용)와 역할을 나눈다. 같은 내용을 중복해서 쓰지 않고 필요하면 링크한다.

## 8. 공통 완료 기준

- [ ] 요청받은 범위의 화면과 동작이 구현되어 있다.
- [ ] 기존 라우팅·인증·권한 정책을 위반하지 않는다.
- [ ] 공통 디자인 시스템과 Light/Dark/System 테마가 일관되게 적용된다.
- [ ] PC·태블릿·모바일에서 사용성을 확인했다(해당 작업 범위 기준).
- [ ] 로딩·빈 상태·오류·폼 피드백을 적절히 처리한다.
- [ ] 실제 API와 Mock 데이터가 구분되며 미구현 API를 숨기지 않는다.
- [ ] 프로젝트에 설정된 타입 검사·린트·빌드 등 가능한 검증을 실행하고 결과를 보고한다.
- [ ] 요청 없이 백엔드·DB·인프라를 수정하지 않았다.
