# 하네스 설계 구조

> 작성: 2026-11-17 · 구조 그림·설계 판단·사례를 한곳에 모은 문서. 운영 절차·명령은 [harness.md](harness.md)에 있다.
> 이 문서의 수치·사례는 코드와 기록(harness/CHANGELOG.md, devlog, 토큰 측정)에서 확인한 것만 적었다.
> 설명할 때는 이 문서의 문장을 외우기보다, 8장의 파일을 직접 열어 보고 자기 말로 바꾼다.

## 1. 한 문장 요약

**"AI 에이전트에게 지시한 규칙을 문서에만 두지 않고, 규칙마다 무엇이 그것을 강제하는지 대장에 적은 뒤, 가능한 규칙은 hook과 검사로 기계가 확인하게 만든 장치"** 다.

## 2. 왜 필요했나 (문제)

이 프로젝트는 설계(규칙·예외·스키마·API 계약)는 직접 하고, 구현은 Claude Code가 한다(2026-11-05·11-12 결정). 지시 문서(AGENTS.md, skill)는 충실했지만, 가장 중요한 규칙들이 **문장으로만** 있었다.

| 규칙 | 지키지 않으면 | 왜 문장만으로는 위험한가 |
|---|---|---|
| 새 API에는 `@Roles` 필수 | 권한 없는 API가 열린다 | `RolesGuard`는 `@Roles`가 없으면 **통과**시킨다. 빠뜨려도 에러가 나지 않고 조용히 열린다 |
| 핵심 모듈은 애드온을 import하지 않는다 | 애드온을 끄면 앱이 깨진다 | 지금은 모든 애드온을 켜고 개발하므로, 끈 상태로 실행하기 전까지 아무도 모른다 |
| 작업 후 typecheck·lint | 깨진 코드가 "완료"로 보고된다 | 에이전트가 기억해야만 돈다 |

핵심 생각: **에이전트는 규칙을 "대체로" 지킨다. 문제는 한 번 잊었을 때 아무도 모른다는 것이다.** 그래서 잊어도 막히는 구조가 필요했다.

## 3. 전체 구조

```text
                   ┌──────────────────────────────────────────┐
                   │  규칙 대장  harness/rules.json            │
                   │  R-AUTH-01 … R-FE-01 (14개)               │
                   │  규칙마다 enforcedBy = 무엇이 강제하나      │
                   └──────────────┬───────────────────────────┘
          문서의 [R-XXX-00] 태그와 짝 │ (짝이 안 맞으면 rules-registry 검사가 실패)
     ┌───────────────┬──────────────┼───────────────┬──────────────────┐
     ▼               ▼              ▼               ▼                  ▼
 ① 세션 시작      ② 작업 전 가드    ③ 정적 검사       ④ 끝내기 전 검증     ⑤ 판단 (manual)
 SessionStart    PreToolUse       verify --quick   Stop hook           자동화하지 않음
 맥락 주입        파일·명령 차단     문서·구조·권한     typecheck·lint      이유를 대장에 기록
     │               │              │               │
 Plan.md 할 일    .env → 확인 창    route-guards     실패하면 응답을
 마지막 devlog    lock → 차단       import-          끝내지 못하게 막고
 최근 커밋        migrate reset     boundaries       실패 내용을
 하네스 상태      → 차단            doc-links/paths  에이전트에게 돌려줌
```

에이전트의 한 턴을 시간 순서로 보면 이렇다.

```text
세션 시작 ──► [① 맥락 주입] ──► 작업: 파일 수정·명령 실행마다 [② 가드] ──► 응답 끝내려 함 ──► [④ 검증] ──┬─ 통과 → 끝
                                                                                                  └─ 실패 → 에이전트에게 돌려줌 → 고침 → 다시 ④
```

## 4. 구성 요소

### 4.0 규칙 대장 (`harness/rules.json`) — 중심

- 문서에 `[R-AUTH-01]`처럼 태그를 붙인 규칙은 **모두 대장에 있어야 하고**, 각 규칙은 `enforcedBy`(check / hook / test / manual)를 적는다.
- `manual`이면 **왜 자동화하지 않았는지 이유**를 같이 적는다. "강제 수단이 없는 규칙"이 몇 개인지 숫자로 보인다(2026-11-17 기준 14개 중 자동 강제 11개, 판단 3개).
- `rules-registry` 검사가 문서의 태그와 대장의 짝을 확인한다. 문서에 새 규칙을 쓰고 대장에 등록하지 않으면 검사가 실패한다.

### 4.1 세션 시작 hook (`harness/hooks/session-start.mjs`)

- 새 세션이 "이전 세션이 어디까지 했는지" 알고 시작하게 한다. Plan.md "처리할 작업"(앞 2000자), 마지막 devlog 제목, 최근 커밋, 하네스 검사 결과를 맥락에 넣는다.
- 출처: 코드 주석에 적은 대로 Anthropic의 "Effective harnesses for long-running agents"(진행 파일 + 시작 의식) 아이디어.

### 4.2 작업 전 가드 (`guard-edit.mjs`, `guard-bash.mjs`)

에이전트가 파일을 고치거나 명령을 실행하기 **직전에** 걸린다. 규칙마다 `deny`(막음) 또는 `ask`(사용자 확인 창)를 고른다.

| 대상 | 결정 | 이유 |
|---|---|---|
| `package-lock.json` 수정 | deny | `npm install`로만 바뀌어야 한다 |
| `prisma migrate reset`, `db push` | deny | 되돌릴 수 없는 DB 명령은 사람이 실행한다 |
| `--no-verify`, 강제 푸시, `rm -rf .` | deny | 검증 우회·복구 불가 |
| `.env` 수정 | **ask** | 사용자 결정(11/12): 설정 값(`ADDONS`)을 바꿀 때마다 직접 고치기 번거로움 → 확인 창에서 내용을 보고 수락 |
| 이미 있는 `migration.sql` 수정 | **ask** | 사용자 결정(11/11): `--create-only`로 만든 직후 CHECK·EXCLUDE 제약을 직접 쓰는 방식이 있다. 파일이 있다는 것만으로는 적용 전인지 알 수 없어 사람이 판단 |
| `git reset --hard`, `TRUNCATE` | ask | 상황에 따라 필요할 수 있다 |

### 4.3 정적 검사 (`node harness/verify.mjs --quick`, 1초 안쪽)

| 검사 | 확인 내용 | 규칙 |
|---|---|---|
| `route-guards` | 모든 컨트롤러 라우트에 `@Roles`·`@RequireAdmin`·`@IsPublic` 중 하나. 본인 계정용 9개는 설정의 `allowlist`에 **이유와 함께** 등록 | R-AUTH-01 |
| `import-boundaries` | 모듈 간 import 방향: 핵심 → 애드온 금지, common → 업무 모듈 금지, 애드온 → 애드온은 선언한 것만(`allow`). 그리고 모든 모듈이 경계 설정에 분류되어 있는지(`requireClassified`) | R-ARCH-01, R-ARCH-02 |
| `doc-links`, `doc-paths` | 문서의 링크·경로가 실제로 있는지. 아직 없는 파일은 "예정" 표시 | R-DOC-02 |
| `agents-size` | AGENTS.md 30KB 이하(Codex 기본 읽기 한도 32KiB) | R-DOC-01 |
| `rules-registry` | 문서 태그 ↔ 규칙 대장 | R-DOC-03 |

`route-guards`는 줄 단위 정적 분석이라 데코레이터를 변수로 조합하거나 상속하면 놓칠 수 있다. 그래서 실행 중인 앱의 라우트를 전부 훑는 런타임 e2e 템플릿(`harness/templates/roles-coverage.e2e-spec.ts`)을 따로 두었다(아직 프로젝트에 복사하지 않음 — 한계 7장).

### 4.4 Stop hook (`harness/hooks/stop-verify.mjs`) — 끝내기 전 검증

에이전트가 응답을 끝내려는 순간 실행된다.

1. git으로 바뀐 파일을 본다. 감시 대상(`backend/`, `frontend/`, `docs/` 등)에 변경이 없으면 바로 통과 → **질문·설명만 한 턴은 비용 0**
2. 바뀐 파일의 지문(크기·수정 시각)이 마지막 통과 때와 같으면 통과 → 같은 상태를 두 번 검증하지 않음
3. 바뀐 패키지만 검증: backend `typecheck`, frontend `typecheck`·`lint:check`
4. 실패하면 `{"decision":"block"}`으로 응답 종료를 막고, 실패 내용과 **판단 순서**를 에이전트에게 돌려준다
   1. 업무 결정을 물으려고 멈춘 상태면 → 고치지 말고 질문과 함께 "검증 실패 중"이라고 알린다 (**검사를 통과시키려고 임시 값을 정하지 않게**)
   2. 작업 범위 밖이거나 고칠 수 없으면 → 보고하고 끝낸다
   3. 그 외에는 고친다
5. 무한 반복 방지: 이미 이 hook 때문에 한 번 더 일한 상태(`stop_hook_active`)면 통과

## 5. 설계 판단

| 판단 | 내용 | 결정 |
|---|---|---|
| **지시보다 강제** | 같은 규칙을 문서에 더 강하게 쓰는 대신, 대장에 강제 수단을 적고 없으면 숫자로 드러나게 했다 | 설계 방향 |
| **자동화하지 않은 규칙도 대장에 둔다** | "업무 규칙은 묻는다"(R-PROC-01)는 무엇이 업무 규칙인지 판단이 필요해 검사로 못 만든다. 이유를 `manual.reason`에 적었다 | 설계 방향 |
| **deny 대신 ask** | `.env`·기존 마이그레이션은 막으면 정상 작업도 막힌다. 사람이 보고 판단하게 했다 | 사용자 결정 (11/11, 11/12) |
| **질문이 검증보다 먼저** | 검증 실패가 "아무 값이나 넣어 통과시키기"로 이어지지 않게 Stop hook 안내 1순위에 둠 | 템플릿 v0.3 |
| **pre-commit 미설치** | git은 사용자가 직접 한다. hook은 에이전트의 도구 호출에만 걸린다 | 사용자 결정 |
| **backend lint는 Stop hook에서 제외** | 적용 시점 기준선이 eslint 오류 43개(auth 가드·데코레이터의 `no-unsafe-*`)였다. 깨진 기준선을 켜면 모든 턴이 막힌다 → typecheck만 먼저 켜고, 정리한 뒤 올린다 | 사용자 결정 (11/11) |
| **검사 범위 = 문서의 규칙 문장** | 프론트 "기능 폴더끼리 import 금지"를 돌리면 11건이 걸렸지만, 문서는 "서로의 API를 import하지 않는다"까지만 정했다. 검사가 문서보다 넓으면 정상 코드를 고치게 만든다 → 후보로만 남김 | 템플릿 v0.2에서 배운 것 |
| **원본은 `harness/`, 설치는 사용자** | 에이전트가 `.claude` 폴더에 직접 쓰지 않는다. `node harness/install-claude.mjs`로 설치 | 설계 방향 |

## 6. 실제로 잡은 것·놓친 것 (사례)

**① Stop hook이 "통과"라고 보고한 오류를 잡음 (2026-11-17)**
- 과제 관리 백엔드를 구현하며 typecheck를 돌렸지만, **e2e 테스트 파일을 쓰기 전**이었다. 이후 쓴 테스트 파일에 타입 오류 6건(콜백 매개변수 암시적 `any`)이 생겼다. 테스트는 실행 시 타입을 보지 않아 e2e 24개는 통과했다.
- 에이전트는 "typecheck 통과"라고 보고하며 끝내려 했고, Stop hook이 typecheck 실패로 종료를 막고 오류를 돌려보냈다. 에이전트가 고친 뒤 다시 통과.
- 의미: **보고 내용을 사람이 검증하지 않아도 마지막 관문이 기계적으로 걸렀다.** 11/14 측정 때까지 Stop hook은 129번 실행·0번 차단이었다. 그 뒤로는 차단 횟수를 세지 않았으므로, 이것은 "기록으로 남긴 첫 차단 사례"다.

**② 검사가 놓친 것: 새 애드온의 경계 설정 누락 (2026-11-17)**
- 11/16에 `projects` 애드온을 추가했지만 `harness.config.json`의 `boundaries`에 넣지 않았다. 그래서 핵심 모듈이 `projects`를 import해도 검사가 잡지 못하는 상태였다. 검사는 "통과"였다.
- 하네스 문서를 정리하며 설정을 읽다가 발견해 추가했고, 연결 모듈의 결재 import는 `allow: ["projects->approvals"]`로 선언했다. 허용을 빼면 실제로 위반이 잡히는 것도 확인했다.
- 의미: **검사는 "선언한 범위"만 지킨다. 범위 선언 자체가 낡으면 통과가 아무 뜻이 없다.**
- 후속 조치(같은 날): 규칙 **R-ARCH-02**를 추가했다. `import-boundaries`에 `requireClassified` 옵션을 넣어, `backend/src` 바로 아래 모듈이 규칙(from/to)이나 `unrestricted`(이유 포함)에 없으면 오류를 낸다. 설정을 11/16 상태로 되돌려 돌리면 `backend/src/projects`가 잡히는 것을 확인했다.
- 오류 메시지는 "핵심인지 애드온인지 정해 넣되, 정해지지 않았으면 사용자에게 묻는다"로 안내한다. 분류는 설계 결정이라 에이전트가 임의로 정하면 안 되기 때문이다(R-PROC-01).
- 요점: **놓친 것을 발견했을 때 "고치고 끝"이 아니라, 같은 종류의 빈틈이 다시 생기지 않게 규칙으로 바꿨다.**

**③ 적용 전에 실제 코드에 돌려 보고 배운 것 (2026-11-11, harness/CHANGELOG.md)**
- `route-guards`가 8개 라우트를 잡았는데, 모두 문서에만 예외로 적혀 있던 본인 계정용 라우트였다. **문서상의 예외를 설정 파일의 명시적 예외(이유 포함)로 바꾸게 한 것**이 이 검사의 실제 가치였다.
- 처음 "common → auth 금지"로 잡았더니 6건(데코레이터·토큰 타입)이 걸렸다. 코드가 아니라 규칙이 넓었다 → 규칙을 새로 만들면 실제 코드에 먼저 돌려 보고 범위를 잡는다.
- `doc-paths` 오류 16건 대부분이 `backend/audit` 같은 git 브랜치 이름(오탐)이었다 → 경로 판별을 좁혔다.

## 7. 효과와 한계

**효과 (2026-11-14 측정, 세션 기록 jsonl의 중앙값, 하네스 적용 11/11 전후)**
- 세션 시작 맥락: 65.1K → 65.8K 토큰 (+0.7K, 약 1%) — 하네스가 맥락을 거의 늘리지 않는다
- 응답당 출력: 1.2K → 1.1K
- 세션당 토큰은 411K → 545K로 늘었지만 작업이 길어진 영향이고 하네스 탓으로 볼 근거가 없다. 적용 후 세션이 12개뿐이라 표본이 쌓이면 다시 잰다

**한계**
- 정적 검사는 줄 단위라 우회 가능한 형태가 있다. 런타임 권한 e2e(`roles-coverage`)는 템플릿만 있고 아직 적용 전이다(검사 경고로 계속 표시됨).
- backend lint는 아직 Stop hook에 없다(기준선 정리 전).
- 사례 ②처럼 **검사 설정이 코드 변화를 따라가지 못하면** 조용히 빈틈이 생긴다. 모듈 분류는 R-ARCH-02로 막았지만, 다른 설정(예: `routeGuards.allowlist`, 가드 패턴)에도 같은 종류의 빈틈이 있을 수 있다.
- 판단 규칙 3개(업무 규칙은 묻기, 지어내지 않기, 프론트 작업 중 백엔드 수정 금지)는 기계가 막지 못한다. devlog의 출처 표기(사용자 결정 / Claude 결정)로 사후에 확인한다.
- hook은 에이전트의 도구 호출에만 걸린다. 사람이 직접 하는 git·Prisma 명령은 대상이 아니다(의도한 범위).

## 9. 자주 묻는 질문

**Q1. 하네스가 뭔가요? 왜 만들었나요?**
- 답: 에이전트 지시는 확률적으로 지켜진다 → `@Roles` 하나 빠지면 조용히 API가 열리는 구조 → 규칙마다 강제 수단을 대장에 적고, 가능한 것은 hook·검사로. 숫자: 규칙 14개 중 11개 자동 강제.

**Q2. 그냥 CI에서 돌리면 되지 않나요?**
- 답: CI는 커밋·푸시 후에 돈다. 이 프로젝트는 git을 사람이 하므로, 그 전에 에이전트의 "완료 보고" 자체를 막아야 했다 → Stop hook. 같은 검사(`verify.mjs`)를 나중에 CI에서도 그대로 쓸 수 있다.

**Q3. 막기만 하면 작업이 불편하지 않나요?**
- 답: deny와 ask를 나눴다. `.env`·적용 전 마이그레이션은 정상 작업에서도 고쳐야 해서 확인 창. 질문·설명만 한 턴은 검증 비용 0, 같은 상태는 두 번 검증하지 않음. 측정상 맥락 증가 약 1%.

**Q4. 실제로 효과가 있었나요?**
- 답: 사례 ①(보고는 통과였지만 Stop hook이 차단) + 사례 ③(문서에만 있던 예외 8개를 명시적 예외로). 정직하게 사례 ②(설정 누락으로 빈틈)도 말하고, 그래서 다음 개선이 무엇인지까지.

**Q5. 자동화하지 못한 규칙은 어떻게 하나요?**
- 답: 대장에 `manual`과 이유를 남겨 "강제되지 않는 규칙"이 몇 개인지 보이게 했다. 사후 확인은 devlog의 출처 표기.
