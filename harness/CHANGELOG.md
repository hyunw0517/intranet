# 하네스 템플릿 변경 이력

> 이 템플릿(harness-starter) 자체의 버전 기록. 프로젝트의 설계 변경은 그 프로젝트의 docs/design/changelog.md에 쓴다.
> 프로젝트에 복사할 때 이 파일도 함께 복사되므로, 나중에 "어느 버전에서 시작했는지"를 알 수 있다.
> 프로젝트에서 배운 것을 템플릿에 되돌리는 절차는 [docs/harness.md](../docs/harness.md) 8장.

## v0.4 — 2026-11-17 · 모듈 분류 검사, 편집 가드 ask

- **R-ARCH-02 / `requireClassified`**: `boundaries`의 소스 루트 바로 아래 모든 모듈이 규칙(from/to)이나 `unrestricted`(`[{ module, reason }]`)에 있어야 한다. 없으면 오류이고, 메시지는 "어느 쪽인지 정해지지 않았으면 사용자에게 묻는다"로 안내한다(분류는 설계 결정). 끄면 기존 동작 그대로. `"*"` 규칙이 있는 경계는 확인하지 않는다
- **편집 가드 `decision: "ask"`**: `guards.protectedFiles`·`immutableIfExists` 규칙마다 ask를 줄 수 있다(Bash 가드와 같은 방식). 값이 없으면 deny라 기존 설정은 그대로 막는다
- 예시 설정(`examples/intranet.config.json`)을 인트라넷의 현재 설정으로 갱신
- 테스트 4개 추가(분류 3, 편집 가드 ask 1)

**인트라넷에서 배운 것**
- 새 애드온(`projects`)을 추가하고 경계 설정에 넣지 않았더니, 의존 방향 검사가 **아무 오류 없이 통과**했다. 검사는 선언한 범위만 지키므로, 범위 선언이 코드를 따라가지 못하면 통과가 아무 뜻이 없다. 사람이 문서를 정리하다 발견했고, 같은 종류의 빈틈을 규칙으로 막았다(설정을 그 전 상태로 되돌려 돌리면 정확히 그 모듈이 잡히는 것까지 확인)
- 같은 원리로 다른 설정 목록(`routeGuards.allowlist`, 가드 패턴)도 코드 변화를 놓칠 수 있다. allowlist는 이미 "없어진 항목은 경고"가 있지만, "새로 생긴 것이 목록에 없다"는 검사마다 따로 봐야 한다
- `.env`(설정 값 변경이 잦음)와 적용 전 마이그레이션(`--create-only` 직후 CHECK·EXCLUDE 제약을 직접 씀)은 deny로 두면 정상 작업이 막혔다 → 사람이 내용을 보고 수락하는 ask가 맞았다
- 테스트가 예시 설정을 그대로 쓰면, 예시를 갱신할 때 "옵션을 끈 경우" 테스트가 깨진다 → 옵션의 켜고 끔은 테스트 안에서 명시한다

## v0.3 — 2026-11-11 · 인트라넷 적용 준비

- **질문이 검증보다 먼저**: Stop hook이 막을 때 "업무 결정을 물으려고 멈춘 상태면 고치지 말고 질문과 함께 끝낸다"를 1순위로 안내. 검사를 통과시키려고 임시 값을 정하는 것을 막는다. route-guards도 "역할이 정해지지 않았으면 묻는다"를 안내
- `stopHook.scripts`를 패키지별로 지정 가능(`{ "backend": ["typecheck"] }`). 기존 lint 오류가 남은 패키지는 typecheck만 돌리다가, 정리한 뒤 올린다. `verify --stop` 추가, pre-commit도 같은 설정을 쓴다
- `sessionStart` 설정: 일정 파일 경로·섹션 이름·글자 수 상한(기존 프로젝트의 Plan.md를 그대로 쓰기 위해)
- `docs.exclude`: 이력 문서(devlog, changelog)는 그 시점의 사실이라 경로 검사에서 뺀다
- doc-paths는 확장자가 있거나 `/`로 끝나는 토큰만 경로로 본다. 표 머리글·절 제목의 "예정"도 계획으로 인정

**인트라넷에 돌려서 배운 것**
- doc-paths 오류 16건 중 대부분이 `backend/audit` 같은 **git 브랜치 이름**이었다(오탐). 경로 모양 판별을 좁혔다.
- 나머지는 이력 문서(devlog 7, changelog 1)와 "위치(예정)" 표 머리글 아래의 계획 경로였다. 실제로 고칠 문서 드리프트는 0건이었다.
- 기존 프로젝트는 lint 기준선이 깨져 있을 수 있다(인트라넷 backend: tsc 0, eslint 오류 43 — 모두 auth 가드·데코레이터의 `no-unsafe-*`). 적용 전에 기준선을 먼저 재고, 깨진 패키지는 단계를 낮춰서 시작한다.

## v0.2 — 2026-11-11 · 범용 템플릿으로 전환

- 인트라넷 전용 설정(모듈 이름, allowlist)을 [examples/intranet.config.json](examples/intranet.config.json)으로 옮기고, 기본 설정은 비워 둠
- `boundaries`를 배열로 바꿈: 소스 루트마다(백엔드 src, 프론트 features) 경계를 따로 선언. `"*"`(모든 모듈), `allow`(개별 허용) 지원
- 구조 규칙 R-ARCH-01~03을 R-ARCH-01 하나("선언한 대로 지킨다")로 합침. 구체적인 금지 방향은 프로젝트가 설정에 적는다
- 경계를 선언하지 않은 상태는 경고로 알림

**인트라넷 코드로 시험해서 배운 것** (backend 컨트롤러 24개·라우트 134개, 소스 214개, 읽기만 함)
- route-guards가 8개 라우트를 잡았는데, 모두 문서에만 예외로 적혀 있던 본인 계정용 라우트였다. 문서상 예외를 설정 파일의 명시적 예외로 바꾸게 하는 것이 이 검사의 실제 가치다.
- 처음 common → auth까지 금지했더니 6건(데코레이터·토큰 타입 import)이 걸렸다. 코드가 아니라 규칙이 넓었다. 규칙을 새로 만들면 실제 코드에 먼저 돌려 보고 범위를 잡는다.
- 프론트 "기능 폴더끼리 import 금지"를 돌리면 11건(관리자 화면이 다른 기능의 훅을 재사용 등)이 걸렸다. 인트라넷 문서는 "서로의 API를 import하지 않는다"까지만 정했으므로 위반이 아니라 규칙 후보다. 예시 설정에 `$candidateBoundaries`로만 남겼다. **문서의 규칙 문장과 검사 범위가 정확히 같아야 한다** — 검사가 문서보다 넓으면 정상 코드를 고치게 만든다.
