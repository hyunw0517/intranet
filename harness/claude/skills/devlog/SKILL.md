# devlog — 세션 기록

`docs/devlog/`는 Notion 포트폴리오의 **원자료**다. 이 폴더는 GitHub에 공개된다. 커밋에는 "무엇"만 남고 "왜"와 고민한 대안은 대화에만 있는데, 대화는 세션이 끝나면 사라진다. 사용자는 이 프로젝트로 면접을 준비하므로, 여기 남긴 결정 이유와 시행착오가 나중에 면접 답변과 트러블슈팅 글의 재료가 된다. 그래서 정확성(지어내지 않기)과 출처 구분(누가 정했나)이 문장의 매끄러움보다 중요하다.

## 모드

- **세션 기록**: 세션 마무리 요청. 아래 1~6단계.
- **해시 채우기**: "커밋했어", "해시 넣어줘". 아래 [해시 채우기](#해시-채우기)만.

## 세션 기록 절차

### 1. 대화에서 재료 모으기

이번 세션(요약된 이전 부분 포함)을 처음부터 훑어 아래를 뽑는다.

- **결정**: 무엇을 정했고 이유는 무엇인가. 비교한 선택지가 있으면 함께.
- **버그·문제 수정**: 증상 → 원인 → 해결.
- **시행착오**: 처음 판단이 틀렸던 것, 제안이 뒤집힌 것, Claude의 설명이 틀렸던 것. 면접에서 "어려웠던 점"으로 가장 쓸모 있으니 숨기지 말고 남긴다.
- **검증**: 무엇을 어떻게 확인했나(tsc, eslint, 실제 API, 함수 직접 호출). **확인하지 못한 것**도 따로 적는다.

출처를 구분해 적는다. 사용자는 자기가 정한 것과 AI가 정한 것을 면접에서 다르게 설명해야 한다.

| 표기 | 의미 |
|---|---|
| (사용자 결정) | 사용자가 규칙을 정함 |
| (사용자 요구, Claude 구현) | 사용자가 요구하고 Claude가 코드 작성 |
| (Claude 제안) / (Claude 결정, 변경 가능) | 사용자가 따로 정하지 않은 Claude의 판단 |
| (시행착오) | 처음 판단이 틀렸거나 바뀐 과정 |

질문·설명만 오간 내용(개념 질문, 일반 지식)은 기록하지 않는다. 결정이나 코드 변화로 이어진 것만 남긴다.

### 2. 저장소 상태 확인

```bash
git log --oneline -10
git status --short
ls backend/prisma/migrations | tail -5
```

- 이번 세션 작업이 이미 커밋됐으면 해시를 쓰고, 아니면 `(미커밋 — <브랜치>)`.
- 새 마이그레이션 폴더 이름은 `관련 커밋` 줄에 함께 적는다(나중에 스키마 변경 시점을 찾기 쉽다).
- 직전 세션 작업 중 devlog에 빠진 커밋이 보이면 한 줄로 링크만 남긴다(내용을 지어내 채우지 않는다).

### 3. 기존 devlog 확인

devlog는 주 단위 파일이다: `docs/devlog/<그 주 월요일 YYYY-MM-DD>.md`(월~일), 목록은 `docs/devlog/README.md`.

- 이번 세션 날짜가 속한 주의 파일이 있으면 그 파일의 마지막 1~2개 항목을 읽어 형식과 중복을 확인한다.
- 없으면(새 주) 파일을 만든다. 형식은 직전 주 파일의 첫 4줄(제목 `# 개발 일지 · YYYY-MM-DD ~ MM-DD`, README.md로 가는 안내 한 줄, `---`)을 그대로 따른다. README.md 끝에도 직전 주와 같은 형식으로 새 주 제목(그 주 파일로 가는 링크)과 목록을 추가한다.
- 새 `##` 항목을 쓰면 README.md의 그 주 목록에도 제목 한 줄(`- YYYY-MM-DD · <제목>`)을 추가한다.
- 문서 링크는 `docs/devlog/` 기준 상대 경로다(예: `../backend/jwt-auth.md`).
- 같은 주제·같은 날짜 항목이 이미 있으면 새 `##` 대신 그 아래에 `### 이어서: <제목> (YYYY-MM-DD)`로 붙인다.
- 줄바꿈 형식(CRLF/LF)을 확인하고 기존 파일과 같게 쓴다. 파일 전체를 다시 쓰지 말고 끝에 추가한다.

### 4. 항목 작성

```markdown
---

## YYYY-MM-DD · <작업 제목 (핵심 기능 2~3개를 ·로 연결)>

관련 커밋: `<hash>` 또는 (미커밋 — `<브랜치>`) · 마이그레이션 `<폴더명>`

- **<주제> (사용자 결정)**: 배경/문제 → 고민한 선택지 → 결정과 이유. 짧으면 한 줄, 길면 하위 목록.
  - 선택지 비교가 핵심이면 하위 목록이나 작은 표로.
- **<버그 이름> (트러블슈팅) ⭐**: 문제 → 원인 → 해결 → 확인.
- **<주제> (시행착오)**: 처음 판단 → 무엇 때문에 바뀌었나 → 최종.
- **검증**: 통과한 검사, 실제로 확인한 것, **미확인 항목**.
- **설계 포인트**: 설명할 만한 설계 주제를 쉼표로. Notion 등록 여부는 적지 않는다(공개 문서).
```

작성 기준:
- 날짜는 대화 시점 기준 실제 날짜(상대 표현 "오늘" 금지).
- 코드 식별자(함수·필드·파일명)는 백틱으로 정확히. 기억이 애매하면 파일을 열어 확인한다.
- 면접에서 이야기할 가치가 큰 항목(보안 버그, 동시성, 설계 반전)에 ⭐.
- 한 항목은 "읽는 사람이 코드를 안 열어도 결정 이유를 알 수 있는" 정도까지. 코드 전체를 붙이지 않는다(필요하면 3~5줄 핵심만).

### 5. 트러블슈팅 후보 제안

docs/portfolio.md "트러블슈팅 후보 (구현 완료)" 표를 읽고, 이번 세션에서 **문제 → 원인 → 해결**이 분명하고 면접 소재가 될 만한 것이 있으면 1~3개를 제안한다. 표 수정은 설계 문서 변경이므로 **사용자가 동의하면** 추가하고, 그때 AGENTS.md 버전과 docs/design/changelog.md도 갱신한다.

### 6. 보고

- 추가한 항목 제목과 담긴 주제를 짧게 요약.
- 커밋 해시가 비어 있으면 "커밋 후 해시를 채울 수 있다"고 안내.
- 트러블슈팅 후보 제안.
- Notion 면접 Q&A 등록이 필요해 보이면 `interview-qa` skill을 안내한다(요청 없이 Notion에 쓰지 않는다).

## 해시 채우기

1. `git log --oneline -15`로 최근 커밋과 메시지를 본다.
2. `docs/devlog/`의 최근 파일들에서 `미커밋`이 남은 항목을 찾는다(`grep -rn 미커밋 docs/devlog/`).
3. 커밋 메시지·변경 파일(`git show --stat <hash>`)과 항목 내용을 대조해 **확실히 대응하는 것만** 채운다. 한 항목이 여러 커밋이면 모두 적는다.
4. 대응이 애매하면 채우지 말고 사용자에게 어느 커밋인지 묻는다. 아직 커밋되지 않은 항목은 그대로 둔다.
5. 바꾼 항목과 해시를 보고한다.

## 하지 않는 것

- 코드·대화에서 확인되지 않은 내용을 지어내지 않는다. 그럴듯한 이유를 덧붙이고 싶으면 사용자에게 묻는다.
- 공개 문서이므로 개인 일정(구직·지원 시점, 마감 날짜, 주간 계획)과 개인 정보는 쓰지 않는다. 일정은 비공개 `docs/Plan.md`에 둔다. Notion Q&A의 질문·답변 내용도 옮기지 않는다(등록 개수만).
- "바이브코딩"처럼 작업 방식을 깎아내리는 표현 대신 출처 표기(사용자 결정 / Claude 구현)로 사실만 적는다.
- 커밋하지 않는다(사용자가 요청할 때만).
- 이전 항목을 고쳐 쓰지 않는다(해시 채우기 제외). 틀린 내용을 발견하면 새 항목에 "정정"으로 남긴다.
